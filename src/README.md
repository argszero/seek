# src — implementation (not started)

Nothing is written here yet. By rule 1 in `docs/decisions.md`: **settle the data model before the interface.**

## Before the first line of code

- [ ] Every open item in `docs/decisions.md` ("Not decided yet") is closed
- [ ] The on-disk shape is fixed: `bots / agents / principals / rooms / memberships / sessions / messages / observations / turns / memories` — messages sharded by room, observations sharded by bot, sessions by agent. **`bots` and `agents` are separate shards**: the bot owns name/avatar/description, the agents inherit them and own sessions, memory, turns and cost
- [ ] Bot-level and agent-level are not mixed anywhere. **Bot-level**: identity, membership, @-mention, the participant list, the observation queue, the tick, the state machine. **Agent-level**: model, prompt, tools, session, memory, turn, cost. Two failure modes to watch: a UI list built from agents (shows one bot as two contacts) and an inbox per agent (N deliveries and N "already handled" states instead of one)
- [ ] `mentionsMe` / `repliesToMe` are computed **once at delivery, against the bot**, and stored on the observation entry. No agent scans a room for its own name; if an agent-level scan appears, both the delivery cost and the "addressed to me" answer have gone wrong
- [ ] `mentionsMe` is **derived** from `Message.mentions[]` (Feishu's field: `{id, name}` pairs) by finding the bot's own id — and it never goes back onto the message. The bug to catch is a per-reader boolean stored on the shared message: it forces a rewrite or a copy per bot, and it turns a free array scan into stored state that can disagree with the message it describes
- [ ] The work agent's context contains the observation entries and **not** the watch agent's reason. A cheap way to get this wrong: putting the whole observation record — verdict and reason included — into the prompt when only the reference and the hints are needed
- [ ] Both roles use **EMRG's existing tool registry**, with per-agent allowlists in `agents.yml` — no watch-specific, memory or compaction tool is built. If a `memory_write` or `compact` tool appears, that is a departure from the kernel and needs its own ruling
- [ ] An agent is only ever a **runnable** — model, prompt, tools, memory — with no clock, no queue and no state of its own; if an agent starts owning a timer or a queue, that lifecycle belongs on the bot
- [ ] **A bot wakes on a delivered message and nothing else** (ruled 2026-10-23: the clock was designed and deferred the same day). Two things to catch: a timer creeping back in without the ruling it was withdrawn over — what an idle tick may call, and what wakes a bot with an empty queue — and a `snooze` verdict conditioned on *time* rather than on an event, which has nothing to wake it
- [ ] **A direct message that arrives mid-turn is injected at the round boundary, not queued for a second turn and not allowed to interrupt a running tool** (ruled 2026-10-23: same as EMRG). Four failure modes to catch: (a) a drain that reads the queue and *then* clears it — a message appended during the await is lost, so pop the whole list atomically and let the next round take what arrived meanwhile; (b) an injected message that is never written to the history, so compaction rebuilds without it and it disappears from the transcript; (c) a turn that ends with the inbox still holding something it was woken for — a mid-turn delivery stranded by the turn it landed in, which is the hazard EMRG's `queued_requeue` exists for and here is a line of the loop; (d) an unjudged room message injected into a running turn — the injected set is the fast-pass set (@-mention / reply / direct message) and nothing else. **No separate pending list and no requeue contract**: the inbox written at delivery *is* the queue, which is why seek does not need EMRG's client re-send
- [ ] String externalisation is set up before the first screen: no user-visible literal in code (see `docs/design/i18n.md`)
- [ ] The watch agent is **a second row in `agents.yml`**, not a classifier and not a field inside the work agent: its own session, its own memory, its own local model, and a read path to its sibling (and one back). `agents.yml` is a roster of agents, not of bots — a bot may hold more than two, so nothing may assume exactly two. Two things signal the design going wrong: a summary layer built *for the watch agent* (it sends its own history like any agent), and any code path that lets one agent's compaction reach another's store
- [ ] Compaction is **per-agent**, because agents have different windows: verify that one agent compacting can never remove detail from another's history — this is the silent-amnesia defect the two-store rule exists to prevent
- [ ] The watch model is chosen by measurement, not by size alone: it must be **multilingual (zh + en at minimum) and multimodal (it must see images)**, bundled, CPU-viable and fast; scored on real watch cases (a room's chatter that concerns it versus chatter that does not), because a model too weak to tell those apart is not cheaper — it is an agent that either misses everything or answers everything. It is evaluated on latency as much as quality, since its tokens are free but its milliseconds are not. The ≤300 MB target and the multimodal requirement conflict; resolve the trade explicitly, do not quietly drop one
- [ ] The first milestone is **kernel only**: Agent object + watch queue + gate (pure rules, no model) + one room, **no interface**
      — what is being tested is whether "it spontaneously says something" holds up, not how it looks
- [ ] Before any two agents can address each other, the chain arbiter is in place: `caused_by` / `chain` / `depth` written on every message, the depth cap, and the room's consecutive-agent-turn counter (`agent-lifecycle.md` §11). **There is no root rule** — a bot may open a conversation with another bot (ruled 2026-10-23), so nothing bounds the *number* of chains and the two caps are the only bounds on a conversation. All agents run in one process, so this is exact rather than approximate — the moment it is policed per-agent instead, it stops being enforceable
- [ ] **An agent reaches another agent by sending a message — never by calling a tool.** All interaction is IM, group or direct, so a bot-to-bot direct room is an ordinary room and no membership rule excludes it. Two things to catch: a `ask_agent`-style tool reappearing (the kernel has none, and `subagent` is a child session of the same agent), and any code assuming a room necessarily contains a human
- [ ] **Chat mode is stored, never branched on.** Feishu's own field has three values (`group` / `topic` / `p2p`), and a direct chat is an ordinary chat with its own `oc_` id — so `chat_mode = p2p` can be kept for fidelity while the domain still sees one kind of Room. The bug to catch is a p2p branch growing behaviour the group path does not have; and a bot creating a room on its own needs no approval step (ruled 2026-10-23)
