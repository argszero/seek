# src — the kernel

The kernel is written: `store`, `delivery`, `gate`, `chain`, `schedule`, `say`, `turn`, `compact`, `box`, `watch`, `kernel`, the comparator, and a runnable first milestone (`npm start`), with 168 tests over them, and **no interface**. By rule 1 in `docs/decisions.md`: **settle the data model before the interface.**

## Checklist

- [x] Every open item in `docs/decisions.md` is closed — the last three on 2026-10-24, on stated defaults recorded in "Closed by default" (a session keeps no member snapshot; the watch agent is not addressable; a watch turn stays in its own history). Nothing in the design is waiting on an answer
- [x] The on-disk shape is fixed: `bots / agents / principals / rooms / memberships / sessions / messages / observations / turns / memories` — messages sharded by room, observations sharded by bot, sessions by agent. **`bots` and `agents` are separate shards**: the bot owns name/avatar/description, the agents inherit them and own sessions, memory, turns and cost
- [x] Bot-level and agent-level are not mixed anywhere. **Bot-level**: identity, membership, @-mention, the participant list, the observation queue, the tick, the state machine. **Agent-level**: model, prompt, tools, session, memory, turn, cost. Two failure modes to watch: a UI list built from agents (shows one bot as two contacts) and an inbox per agent (N deliveries and N "already handled" states instead of one)
- [x] `mentionsMe` / `repliesToMe` are computed **once at delivery, against the bot**, and stored on the observation entry. No agent scans a room for its own name; if an agent-level scan appears, both the delivery cost and the "addressed to me" answer have gone wrong
- [x] `mentionsMe` is **derived** from `Message.mentions[]` (Feishu's field: `{id, name}` pairs) by finding the bot's own id — and it never goes back onto the message. The bug to catch is a per-reader boolean stored on the shared message: it forces a rewrite or a copy per bot, and it turns a free array scan into stored state that can disagree with the message it describes
- [x] The work agent's context contains the observation entries and **not** the watch agent's reason. A cheap way to get this wrong: putting the whole observation record — verdict and reason included — into the prompt when only the reference and the hints are needed
- [ ] Both roles use **EMRG's existing tool registry**, with per-agent allowlists in `agents.yml`. Exactly **two additions** exist, both named by the host: `schedule` and `say`. No watch-specific, memory or compaction tool is built — if a `memory_write` or `compact` tool appears, that is a departure from the kernel and needs its own ruling, and so does a third addition: two is where the count stops being a coincidence
- [x] **Nothing reaches a room except through `say(room, text)`.** A turn's output is its own record: not posted, not streamed, not summarised into the room, and a turn that ends without the call has said nothing. Four ways this gets broken: (a) posting the agent's final answer to the room that woke it — the reason the tool exists is that the room must be named by the sender; (b) streaming a message into the room as tokens arrive, which produces a message nobody chose to finish; (c) treating "sent nothing" as an error state and nudging the agent to speak; (d) letting the runtime infer the room instead of taking it from the call
- [x] An agent is only ever a **runnable** — model, prompt, tools, memory — with no clock, no queue and no state of its own; if an agent starts owning a timer or a queue, that lifecycle belongs on the bot
- [x] **A bot wakes on a delivery and nothing else** (ruled 2026-10-23; the schedule ruled 2026-10-24 added a second *producer of deliveries*, not a second wake source). What to catch: a timer creeping back in as a per-bot heartbeat, or a bot woken by "it is 09:00" instead of by an entry in its inbox. A `snooze` conditioned on time is now legal and is performed by the loop writing a schedule row — so the old objection is gone, and what replaces it is the check that the row, not the watch agent, is what writes it
- [x] **A direct message that arrives mid-turn is injected at the round boundary, not queued for a second turn and not allowed to interrupt a running tool** (ruled 2026-10-23: same as EMRG). Four failure modes to catch: (a) a drain that reads the queue and *then* clears it — a message appended during the await is lost, so pop the whole list atomically and let the next round take what arrived meanwhile; (b) an injected message that is never written to the history, so compaction rebuilds without it and it disappears from the transcript; (c) a turn that ends with the inbox still holding something it was woken for — a mid-turn delivery stranded by the turn it landed in, which is the hazard EMRG's `queued_requeue` exists for and here is a line of the loop; (d) an unjudged room message injected into a running turn — the injected set is the fast-pass set (@-mention / reply / direct message) and nothing else. **No separate pending list and no requeue contract**: the inbox written at delivery *is* the queue, which is why seek does not need EMRG's client re-send
- [x] **The schedule is one global table, one tool, and due rows arrive as messages** (ruled 2026-10-24). No bot owns a timer: there is a single table and a comparator that reads a clock, and a due row becomes a normal inbox entry of `kind: "reminder"` that wakes its bot exactly as a person's message would. Five failure modes to catch: (a) a per-bot timer creeping back in — the ruling is one table in the process, not N heartbeats; (b) a due row that is not a delivery, i.e. a bot being woken by "it is 09:00" rather than by an entry in its inbox; (c) a firing that is not idempotent across a restart — an instant passed while the process was down must fire once, not zero times and not twice; (d) `text` being rewritten, summarised or translated on the way out — the reminder arrives verbatim, exactly as its author wrote it; and (e) the reminder turning up in a room or on the transcript — it is not displayed (ruled 2026-10-24: no room field, no frame, no line), so a visible system message describing "a note this bot left itself" is the bug, not the feature
- [ ] String externalisation is set up before the first screen: no user-visible literal in code (see `docs/design/i18n.md`)
- [ ] The watch agent is **a second row in `agents.yml`**, not a field inside the work agent: its own model, its own memory, its own read path to its sibling. It is **a decision model** — it answers named questions over a state in one forward pass, generates nothing and calls no tools, so it has **no session and does not compact**. Two things signal the design going wrong: giving it a chat model so that it can write its own summary (a generation on every wake, which is the latency the gate exists to avoid), and a runtime that assembles a prompt for it instead of handing it the room's box. `agents.yml` is a roster of agents, not of bots — a bot may hold more than two, so nothing may assume exactly two
- [x] **A room's standing summary has exactly one writer, and it is the work agent** — the watch side produces no text, so it reads the box and never writes it. And the summary is **per (bot, room), not per agent**: two writers of one summary is a disagreement that shows up only when they differ, which is the silent-amnesia defect in its new form. The two agents' own stores still never touch: the work agent's sessions and diary are its own, and no code path may let one agent's compaction reach another's store
- [x] **Compaction is a runtime action, not a turn**, and the judgement is never asked whether to compact. What to catch: (a) compaction reachable only from a turn end — a busy room that never needs a word said would then never be compacted, since there is no turn to end; (b) a verdict that waits on a compaction, which puts a generation in front of the gate; (c) two compactions over one room at once, where the one that finishes last silently deletes the other's difference — single-flight, committing the new summary and its consumed-to point in one atomic write; (d) a compaction that produces a message or is marked as a proactive turn
- [x] **The box handed to a judgement always fits**, newest observations first up to the model's window, with the unread count carried along. A judgement given more than it can read returns a confident guess, which looks exactly like a verdict — the failure mode has to stay visible (an unread count) rather than being silently truncated
- [ ] **The previous verdict goes into the box as a fact, never as an instruction.** "You kept this twelve observations ago and nothing followed" is a fact; "you should keep this" makes a stale decision self-perpetuating, and it is what would stop `keep` and `snooze` ever being re-opened
- [ ] The watch model is chosen by measurement, not by size alone: it must be **multilingual (zh + en at minimum) and multimodal (it must see images)**, bundled, CPU-viable and fast; scored on real watch cases (a room's chatter that concerns it versus chatter that does not), because a model too weak to tell those apart is not cheaper — it is an agent that either misses everything or answers everything. It is evaluated on latency as much as quality, since its tokens are free but its milliseconds are not. **The ≤300 MB target was withdrawn after measurement** — a 300 MB model scored at chance — so the shipped model is the 3B class (≈1.5 GB, ≈2.1 GB with the projector), and the multimodal requirement is still **unmet**: vision has not been measured, so do not treat images as handled
- [ ] The watch question is put to the model as **one binary act-or-not**, answered from the probabilities of two declared option tokens — `keep` and `later` are written by the loop, never asked for; each option must be a **single token** and masked at the id it takes at the prompt's own end, or it becomes permanently unreachable; the operating point comes from a **labelled set**, never 0.5; the box's tokens are kept **warm per (bot, room)**, because re-reading a full box at a 3B costs ≈1 ms per token
- [ ] The watch prompt is a **versioned artifact the threshold was calibrated against**, not a string built at the call site — measured, rewording alone moved one model's discrimination from 0.09 to 0.77 and inverted it between Chinese and English
- [x] The first milestone is **kernel only**: Agent object + watch queue + gate (pure rules, no model) + one room, **no interface**
      — what is being tested is whether "it spontaneously says something" holds up, not how it looks
- [x] Before any two agents can address each other, the chain arbiter is in place: `caused_by` / `chain` / `depth` written on every message, the depth cap, and the room's consecutive-agent-turn counter (`agent-lifecycle.md` §11). **There is no root rule** — a bot may open a conversation with another bot (ruled 2026-10-23), so nothing bounds the *number* of chains and the two caps are the only bounds on a conversation. All agents run in one process, so this is exact rather than approximate — the moment it is policed per-agent instead, it stops being enforceable
- [x] **An agent reaches another agent by sending a message — never by calling a tool.** All interaction is IM, group or direct, so a bot-to-bot direct room is an ordinary room and no membership rule excludes it. Two things to catch: a `ask_agent`-style tool reappearing (the kernel has none, and `subagent` is a child session of the same agent), and any code assuming a room necessarily contains a human
- [x] **Chat mode is stored, never branched on.** Feishu's own field has three values (`group` / `topic` / `p2p`), and a direct chat is an ordinary chat with its own `oc_` id — so `chat_mode = p2p` can be kept for fidelity while the domain still sees one kind of Room. The bug to catch is a p2p branch growing behaviour the group path does not have; and a bot creating a room on its own needs no approval step (ruled 2026-10-23)
