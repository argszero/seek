# src —— 内核

内核已经在这里了：一个存储、每个机器人一个环、一个比较器、一个房间摘要的写者、一处交给判定的盒子装配、一处把机器人身份（它是谁家的 agent、同门还有谁）在每次 turn 推给它的装配、一份从文件读出并由运行时按文件顺序拼装的版本化提示词、一份按键取用的界面文案表、一个把盒子交给模型并写下判定的第一阶段运行时、一个把盒子经本地 llama.cpp 服务读成选项概率的传输（`src/llama.ts`）、一处把那份传输接成第一阶段运行时的装配（`src/watch-server.ts`，在服务上量好选项 id 再把判定器交出来），以及一个可运行的第一个里程碑（`npm start`），295 个测试覆盖它们，**没有界面**。按 `docs/decisions.md` 的原则：**先定数据模型，再碰界面。**

## 检查表

- [x] `docs/decisions.md` 里没有未决项了 —— 最后三条在 2026-10-24 关闭，按「Closed by default」里写明的默认值（session 不存成员快照；watch agent 不可寻址；watch 那一轮只留在自己历史里）。设计里没有任何东西在等答案
- [x] 落盘形状定死：`bots / agents / principals / rooms / memberships / sessions / messages / observations / turns / memories` —— messages 按房间分片、observations 按机器人分片、sessions 按 agent 分片。**`bots` 和 `agents` 是两个分片**：机器人拥有名字/头像/描述，agent 继承它们，并拥有 session、记忆、Turn 和花费
- [x] 机器人级与 agent 级在任何地方都不许混。**机器人级**：身份、成员、@、成员列表、收件箱、tick、状态机。**agent 级**：模型、提示词、工具、session、记忆、Turn、花费。两种失败形态要盯：用 agent 造出来的界面列表（一个机器人显示成两个联系人）、每个 agent 一个收件箱（N 次投递、N 份「已处理」，而不是一份）
- [x] `mentionsMe` / `repliesToMe` **在投递时对机器人算一次**，存在观察条目上。没有 agent 去房间里扫自己的名字；一旦出现 agent 级扫描，投递成本和「是不是在跟我说话」的答案就同时错了
- [x] `mentionsMe` 由 `Message.mentions[]`（飞书字段：`{id, name}` 对）**推导**而来，方法是找本机器人自己的 id —— 而且它绝不回写到消息上。要抓的 bug 是：把「每个读者视角的布尔值」存到共享消息上，那会逼出每个机器人一份改写或复制，把一次免费的数组扫描变成一份可能与它所描述的消息不一致的存储状态
- [x] 干活 agent 的上下文里是观察条目，**不是** watch 的理由。最容易犯的错：把整条观察记录（含判定和理由）塞进 prompt，而实际只需要引用和 hints
- [x] 两个角色都用 **EMRG 现有的工具注册表**，允许哪些工具是 `agents.yml` 里的普通配置。正好**两处新增**，都是宿主点名的：`schedule` 和 `say`。不造 watch 专用工具、不造记忆工具、不造压缩工具 —— 一旦出现 `memory_write` 或 `compact` 工具，那就是偏离内核，需要单独裁决；第三次新增同样要单独裁决：两个正好是「再多就不像巧合」的那条线。允许清单是从文件里读的：每一行带自己的 `tools`，`src/roster.ts` 把它放到该行描述的那个 agent 上，`say`／`schedule` 动手之前都要过这一关 —— 所以哪个 agent 能说话、哪个能写提醒，是一行配置，而不是代码里的一张表
- [x] **除了 `say(room, text)`，没有任何东西能到达房间。** 一轮的输出就是它自己的记录：不发帖、不流式、不摘要进房间，一轮结束时没有调用它，就等于什么都没说。四种破法要盯：(a) 把 agent 的最终回答发进叫醒它的那个房间 —— 工具存在的理由就是房间必须由发送方点名；(b) 边生成边把消息流进房间，产出一条没人决定收尾的消息；(c) 把「什么都没发」当成错误状态，反过来催 agent 说话；(d) 让运行时自己推断房间，而不是从调用里取
- [x] agent 永远只是**可运行件** —— 模型、提示词、工具、记忆 —— 没有时钟、没有队列、没有自己的状态；agent 一旦开始拥有定时器或队列，那份生命周期就该在机器人身上
- [x] **只有投递能唤醒机器人，没有第二个唤醒源**（2026-10-23 裁决；2026-10-24 的 schedule 增加的是投递的**第二个生产者**，不是第二个唤醒源）。要抓的：定时器以「每机器人一个心跳」的形状偷偷回来，或者机器人被「到 9 点了」叫醒而不是被收件箱里的某条目叫醒。按时间条件的 `snooze` 现在是合法的，由环写一条 schedule 行来执行 —— 所以旧的反对意见作废，替换成一条检查：写那行的是环，不是 watch
- [x] **进行中到达的直达消息在轮边界注入，既不排成第二个 turn，也不许打断正在跑的工具**（2026-10-23 裁决：与 EMRG 一致）。五个失败形态要盯：(a) 先读队列再清空的 drain —— await 期间追加进来的消息会丢，所以要整表原子 pop，让下一轮取走这期间到达的；(b) 注入的消息从不写入历史，于是压缩重建时它不在，从记录里消失；(c) 一个 turn 结束时收件箱里还留着把它叫醒的东西 —— 被它落进去的那个 turn 吞掉的进行中投递，正是 EMRG 的 `queued_requeue` 要防的危险，在这里是环里的一行；(d) 未经判断的群消息被注入进正在跑的 turn —— 注入集合就是快通道集合（@我／回复我／私聊），别的都不算。**没有独立的 pending 列表，也没有 requeue 协议**：投递时写下的收件箱**就是**那个队列，所以 seek 不需要 EMRG 的客户端重发
- [x] **schedule 是一张全局表、一个工具，到期的行以消息的形式到达**（2026-10-24 裁决）。没有机器人拥有定时器：只有一张表和读时钟的比较器，到期的行变成一条普通的 `kind: "reminder"` 收件箱条目，像人发的消息一样唤醒它。五个失败形态要盯：(a) 每机器人一个定时器偷偷回来 —— 裁决是进程里一张表，不是 N 个心跳；(b) 到期的行不是一次投递，即机器人被「到 9 点了」叫醒而不是被收件箱里的条目叫醒；(c) 跨重启不幂等 —— 进程关着时经过的时刻必须正好补发一次，不是零次也不是两次；(d) `text` 在出口处被改写、摘要或翻译 —— 提醒逐字到达，就是作者写下的那行；(e) 提醒出现在房间里或聊天记录上 —— 它不显示（2026-10-24 裁决：无 room 字段、不走帧、不进记录），所以一条描述「这个机器人给自己留的便条」的可见系统消息才是 bug，不是特性
- [x] 文案外置在第一个界面之前就搭好：代码里不许出现任何用户可见的字面量（见 `docs/design/i18n.md`）—— 字住在 `src/i18n/<tag>.json` 里，`src/i18n.ts` 按键取用并渲染；复数类别由 `Intl.PluralRules` 按语言给出（绝不靠 `count === 1`），数字走 `Intl.NumberFormat`。`npm start` 打印的那份报告是第一个界面，所以它第一个被搬走：`--lang zh-CN` 把同一次运行印成中文，而房间日志的每一行一字不动，因为消息是正文，正文永不翻译。仍然留在代码里的那两类是点名留下的，而不是心照不宣：内核的 `throw` 是日志行（§7），参与者的字是数据。防止字面量再长回来的守卫不是「扫描带引号的句子」——那会把正文判成违规——而是断言报告渲染出来的每一行都来自文案表
- [x] watch agent 是 **`agents.yml` 里的第二行**，不是干活 agent 里的一个字段：自己的模型、自己的记忆、对兄弟的一条读路径。它是**一个决策模型** —— 在一个状态上、一次前向里回答点名的问题，不生成、不调工具，所以它**没有 session，也不压缩**。两个信号说明设计走歪了：给它一个对话模型好让它自己写摘要（每次唤醒一次生成，正是门禁要避开的那个延迟），以及运行时替它拼 prompt，而不是把房间的那个盒子直接交给它。`agents.yml` 是 agent 名册、不是机器人清单 —— 一个机器人可以超过两个，所以任何地方都不许假定正好两个。两行都只在这个文件里：`src/roster.ts` 读 store 旁边的它，并用它重建 store 里的 agent；一行的 id 由它所属的 bot 和它的角色推导，所以重建之后会话仍然是它的；哪个机器人写了第三行，就多出第三个 agent，没有任何地方需要被通知（`docs/decisions.md` 默认值 14、15）
- [x] **一个房间的长期摘要只有一个写者，就是干活 agent** —— watch 侧不产生文字，所以它读盒子，从不写它。而且摘要是**按 (机器人, 房间)**的，不是按 agent 的：一份摘要两个写者，就是「只在两者不一致时才暴露」的那种分歧，也就是无声失忆缺陷的新形状。两份存储仍然互不接触：干活 agent 的 session 和日记是它自己的，任何代码路径都不许让一个 agent 的压缩够到另一个 agent 的存储
- [x] **压缩是运行时动作，不是一轮**，而且「要不要压缩」这个问题永远不问判定。要抓的：(a) 压缩只能从一轮结束时触发 —— 一个一直不需要说话的忙碌房间就永远不会被压缩，因为没有轮可以结束；(b) 一份判定在等压缩完成，那等于把一次生成挡在门禁前面；(c) 同一个房间上两次压缩并行，后结束的那次悄悄删掉另一份的差 —— 单飞，把新摘要和它的「已消费到」点在一次原子写里提交；(d) 压缩产出一条消息，或者被标记成一次主动轮
- [x] **交给判定的盒子永远装得下**：最新的观察先说，装到模型窗口为止，未读计数一并带上。给了超过它能读的量的判定，返回的是一个自信的猜测，而它看起来和判定一模一样 —— 这个失败形态必须一直看得见（一个未读计数），而不是被悄悄截断
- [x] **上一次判定作为事实进盒子，永远不作为指令。** 「你在十二个观察之前留了这一条，之后什么都没发生」是事实；「你应该留着这条」会让一个过期决定自我延续，也正是它会让 `keep` 和 `snooze` 再也无法被重新翻开
- [ ] watch 模型靠实测选，不靠体积：它必须**多语言（至少中英）且多模态（必须能看图）**、内置、CPU 可跑、快；用真实 watch 案例打分（房间里跟它有关的闲聊 vs 无关的闲聊），因为一个分不清这两者的模型不是更便宜 —— 它是「要么全漏、要么全回」的 agent。延迟与质量同等重要，它省的是钱，不是毫秒。**≤300 MB 的目标已经在实测之后撤回** —— 那个尺寸的模型得分等于抛硬币 —— 所以随产品装上的是 3B 这一档（约 1.5 GB，带投影器约 2.1 GB），而多模态要求**已经测过、仍未满足**：在 32 条标签只存在于像素里的图片案例上，它在出货的 0.600 切点上答对 **25/32**（AUC 0.891，每条约 1.05 秒）—— 后 16 条是在前 16 条读完之后才写的，两半分别是 12/16 和 13/16，所以这个数不是一组案例在讨好模型。「没什么要处理」的图它一次都没开火（**16/16**），而这个切点上带故障的 16 张漏了 7 张（**9/16**）—— 但探针说明这些漏判大多出在**操作点，不是「看不见」**：模型和案例都不动，把切点放到 0.150、在一半上选再去量另一半，同一个检查点是 **29/32，`act` 13/16、`ignore` 仍然 16/16**；而且两半里没有任何一条 `ignore` 的 p_act 超过 0.134，两类几乎不重叠，0.600 正好横穿 `act` 的中段。0.600 是在文字上标定的（默认值 12），搬到带图消息上不成立；**改问句的措辞没有用** —— 四种问法，没有一个更好，还有一个更差（`calibration/vision/probe.json`）。为选它而写的一组案例有了（`calibration/vision/boundary.json`），而重测它时发现装置一直把图片放在**问句之后**、而不是放在它所属的消息上 —— 所以那些读数、以及上面的 25/32 和 0.891，都已经按内核实际拼出的形状重测（`calibration/vision/remeasured.json`）。这次更正是要紧的：边界集的 AUC 是 **0.840** 而不是 0.701，而且最佳切点上 56 条图像案例里**没有任何一条**反例开火（`ignore` 28/28）。两条路放在同一套装置上，**一个切点就能同时服务两边** —— 在 **(0.3845, 0.3948]** 之间，文字 **24/24**、图像 **48/56**（`act` 20/28、`ignore` 28/28），而这段区间正落在图像平台 (0.3688, 0.4500] 里面；在出货的 0.600 上，同样的两组是文字 20/24、图像 41/56，所以 0.600 在两条路上都被占优，并不需要第二个切点。**多语言那一半也测了，而且它是更弱的一半 —— 但不是切点能修的那种弱。** 那十二条中文案例（`calibration/vision/zh.json`）**本身就是图像案例**：十二张手绘的中文运维大屏，配文故意无信息量（「早上的」「刚出的日报」），标签只活在像素里 —— 多语言这一半与多模态那一半是**同一次测量**，不是两次。它们在出货的 0.600 上是 AUC **0.694**、`act` **1/6**；把每个切点都扫一遍，问的是英文集已经用相反答案回答过的那个问题：**任何切点上最多 8/12**，而且两类是交错的 —— 六张 `act` 里有四张读数低于六张 `ignore` 里的两张（`z-a1` 0.0646、`z-a4` 0.0845、`z-a6` 0.1341、`z-a3` 0.1385 对 `z-i5` 0.2605、`z-i1` 0.2123）。**没有哪个阈值能把它们分开**，而那个 8/12 是靠对六张「没事」的图里的四张开火换来的。英文正好相反：56 条里没有任何一条反例超过 0.3689，`ignore` 在整段平台上都是 **28/28**，41/56 到 48/56 纯粹是线画在哪里。**所以挪默认值 12 能救英文图像，救不了中文** —— 中文的短板是模型的判别力，不是操作点。这条要求因此是因为更窄的理由没满足：不是模型看不见，也不是谁挪一个切点就能解决。图片仍然不能当成已经处理好了
- [x] watch 的问题是**一个二元的「要不要动」**，从两个已声明选项 token 的概率里回答 —— `keep` 和 `later` 由环来写，永远不问；每个选项必须是**单个 token**，并且要按它在 prompt 自己结尾处的那个 id 做屏蔽，否则它永远取不到；操作点来自一个**带标注的集合**，永远不是 0.5；盒子的 token **按 (机器人, 房间) 保持热**，因为在 3B 上重读一个满盒子约每 token 1 ms
- [x] watch 的 prompt 是一个**阈值据以标定的、有版本号的产物**，不是在调用点上拼出来的字符串 —— 实测过：只改措辞就把某个模型的区分度从 0.09 挪到 0.77，并在中英文之间翻了向
- [x] 第一个里程碑**只有内核**：Agent 对象 + 收件箱 + 门禁（纯规则，不接模型）+ 一个房间，**不做界面**
      —— 要验证的是「它会自己冒一句话」成不成立，不是好不好看
- [x] 任何两个 agent 能互相说话之前，链仲裁先就位：每条消息写上 `caused_by` / `chain` / `depth`、深度上限、房间的连续 agent 轮次计数（`agent-lifecycle.md` §11）。**没有根规则** —— 机器人可以主动跟另一个机器人开口（2026-10-23 裁决），所以链的*数量*无人约束，两个上限就是一段对话的全部边界。所有 agent 跑在同一个进程里，所以这是精确的而不是近似的 —— 一旦改成按 agent 各自执法，它就管不住了
- [x] **一个 agent 够到另一个 agent 靠发消息，永远不靠调工具。** 所有交互都是 IM（群聊或私聊），所以两个机器人之间的单聊就是一个普通房间，没有任何成员规则把它排除在外。两个信号要盯：`ask_agent` 形态的工具重新出现（内核没有这个工具，`subagent` 是同一个 agent 的子会话），以及任何假定房间必然有人的代码
- [x] **聊天模式只存不用来分支。** 飞书的字段有三个值（`group` / `topic` / `p2p`），单聊就是一条有自己的 `oc_` id 的普通聊天 —— 所以 `chat_mode = p2p` 可以为了保真而存下来，而领域看到的仍然是一种 Room。要抓的 bug 是 p2p 分支长出群组路径没有的行为；另外机器人自建房间不需要任何批准步骤（2026-10-23 裁决）
