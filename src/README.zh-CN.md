## 写第一行代码之前

- [x] `docs/decisions.md` 里没有未决项了 —— 最后三条在 2026-10-24 关闭，按「Closed by default」里写明的默认值（session 不存成员快照；watch agent 不可寻址；watch 那一轮只留在自己历史里）。设计里没有任何东西在等答案
- [ ] 落盘形状定死：`bots / agents / principals / rooms / memberships / sessions / messages / observations / turns / memories` —— messages 按房间分片、observations 按机器人分片、sessions 按 agent 分片。**`bots` 和 `agents` 是两个分片**：机器人拥有名字/头像/描述，agent 继承它们，并拥有 session、记忆、Turn 和花费
- [ ] 机器人级与 agent 级在任何地方都不许混。**机器人级**：身份、成员、@、成员列表、收件箱、tick、状态机。**agent 级**：模型、提示词、工具、session、记忆、Turn、花费。两种失败形态要盯：用 agent 造出来的界面列表（一个机器人显示成两个联系人）、每个 agent 一个收件箱（N 次投递、N 份「已处理」，而不是一份）
- [ ] `mentionsMe` / `repliesToMe` **在投递时对机器人算一次**，存在观察条目上。没有 agent 去房间里扫自己的名字；一旦出现 agent 级扫描，投递成本和「是不是在跟我说话」的答案就同时错了
- [ ] `mentionsMe` 由 `Message.mentions[]`（飞书字段：`{id, name}` 对）**推导**而来，方法是找本机器人自己的 id —— 而且它绝不回写到消息上。要抓的 bug 是：把「每个读者视角的布尔值」存到共享消息上，那会逼出每个机器人一份改写或复制，把一次免费的数组扫描变成一份可能与它所描述的消息不一致的存储状态
- [ ] 干活 agent 的上下文里是观察条目，**不是** watch 的理由。最容易犯的错：把整条观察记录（含判定和理由）塞进 prompt，而实际只需要引用和 hints
- [ ] 两个角色都用 **EMRG 现有的工具注册表**，允许哪些工具是 `agents.yml` 里的普通配置 —— 不造 watch 专用工具、不造记忆工具、不造压缩工具。一旦出现 `memory_write` 或 `compact` 工具，那就是偏离内核，需要单独裁决
- [ ] agent 永远只是**可运行件** —— 模型、提示词、工具、记忆 —— 没有时钟、没有队列、没有自己的状态；agent 一旦开始拥有定时器或队列，那份生命周期就该在机器人身上
- [ ] **只有投递能唤醒机器人，没有第二个唤醒源**（2026-10-23 裁决；2026-10-24 的 schedule 增加的是投递的**第二个生产者**，不是第二个唤醒源）。要抓的：定时器以「每机器人一个心跳」的形状偷偷回来，或者机器人被「到 9 点了」叫醒而不是被收件箱里的某条目叫醒。按时间条件的 `snooze` 现在是合法的，由环写一条 schedule 行来执行 —— 所以旧的反对意见作废，替换成一条检查：写那行的是环，不是 watch
- [ ] **进行中到达的直达消息在轮边界注入，既不排成第二个 turn，也不许打断正在跑的工具**（2026-10-23 裁决：与 EMRG 一致）。五个失败形态要盯：(a) 先读队列再清空的 drain —— await 期间追加进来的消息会丢，所以要整表原子 pop，让下一轮取走这期间到达的；(b) 注入的消息从不写入历史，于是压缩重建时它不在，从记录里消失；(c) 一个 turn 结束时收件箱里还留着把它叫醒的东西 —— 被它落进去的那个 turn 吞掉的进行中投递，正是 EMRG 的 `queued_requeue` 要防的危险，在这里是环里的一行；(d) 未经判断的群消息被注入进正在跑的 turn —— 注入集合就是快通道集合（@我／回复我／私聊），别的都不算。**没有独立的 pending 列表，也没有 requeue 协议**：投递时写下的收件箱**就是**那个队列，所以 seek 不需要 EMRG 的客户端重发
- [x] **schedule 是一张全局表、一个工具，到期的行以消息的形式到达**（2026-10-24 裁决）。没有机器人拥有定时器：只有一张表和读时钟的比较器，到期的行变成一条普通的 `kind: "reminder"` 收件箱条目，像人发的消息一样唤醒它。五个失败形态要盯：(a) 每机器人一个定时器偷偷回来 —— 裁决是进程里一张表，不是 N 个心跳；(b) 到期的行不是一次投递，即机器人被「到 9 点了」叫醒而不是被收件箱里的条目叫醒；(c) 跨重启不幂等 —— 进程关着时经过的时刻必须正好补发一次，不是零次也不是两次；(d) `text` 在出口处被改写、摘要或翻译 —— 提醒逐字到达，就是作者写下的那行；(e) 提醒出现在房间里或聊天记录上 —— 它不显示（2026-10-24 裁决：无 room 字段、不走帧、不进记录），所以一条描述「这个机器人给自己留的便条」的可见系统消息才是 bug，不是特性
- [ ] 文案外置在第一个界面之前就搭好：代码里不许出现任何用户可见的字面量（见 `docs/design/i18n.md`）
- [ ] watch agent 是 **`agents.yml` 里的第二行**，不是分类器、也不是干活 agent 里的一个字段：自己的 session、自己的记忆、自己的本地模型，以及对兄弟的一条读路径（和一条反向的）。`agents.yml` 是 agent 名册、不是机器人清单 —— 一个机器人可以超过两个，所以任何地方都不许假定正好两个。两个信号说明设计走歪了：**为 watch 造的**摘要层（它像任何 agent 一样发自己的历史）、以及任何让一个 agent 的压缩够到另一个 agent 存储的代码路径
- [ ] 压缩是**按 agent** 的，因为两个 agent 的窗口不同：要验证一个 agent 压缩时绝不可能删掉另一个 agent 历史里的细节 —— 这正是「两份存储」这条规则要防的无声失忆缺陷
- [ ] watch 模型靠实测选，不靠体积：它必须**多语言（至少中英）且多模态（必须能看图）**、内置、CPU 可跑、快；用真实 watch 案例打分（房间里跟它有关的闲聊 vs 无关的闲聊），因为一个分不清这两者的模型不是更便宜 —— 它是「要么全漏、要么全回」的 agent。延迟与质量同等重要，它省的是钱，不是毫秒。≤300 MB 的目标和多模态要求冲突；这个权衡要显式解决，不许悄悄砍掉一个
- [ ] 第一个里程碑**只有内核**：Agent 对象 + 收件箱 + 门禁（纯规则，不接模型）+ 一个房间，**不做界面**
      —— 要验证的是「它会自己冒一句话」成不成立，不是好不好看
- [ ] 任何两个 agent 能互相说话之前，链仲裁先就位：每条消息写上 `caused_by` / `chain` / `depth`、深度上限、房间的连续 agent 轮次计数（`agent-lifecycle.md` §11）。**没有根规则** —— 机器人可以主动跟另一个机器人开口（2026-10-23 裁决），所以链的*数量*无人约束，两个上限就是一段对话的全部边界。所有 agent 跑在同一个进程里，所以这是精确的而不是近似的 —— 一旦改成按 agent 各自执法，它就管不住了
- [ ] **一个 agent 够到另一个 agent 靠发消息，永远不靠调工具。** 所有交互都是 IM（群聊或私聊），所以两个机器人之间的单聊就是一个普通房间，没有任何成员规则把它排除在外。两个信号要盯：`ask_agent` 形态的工具重新出现（内核没有这个工具，`subagent` 是同一个 agent 的子会话），以及任何假定房间必然有人的代码
- [ ] **聊天模式只存不用来分支。** 飞书的字段有三个值（`group` / `topic` / `p2p`），单聊就是一条有自己的 `oc_` id 的普通聊天 —— 所以 `chat_mode = p2p` 可以为了保真而存下来，而领域看到的仍然是一种 Room。要抓的 bug 是 p2p 分支长出群组路径没有的行为；另外机器人自建房间不需要任何批准步骤（2026-10-23 裁决）
