# 长存活 Agent 设计（seek 内核）

> **每个 bot 都是活的。** 它和普通 agent 的区别有三条：**长存活、自己观察、自己行动**。房间里一条没 @ 它的消息照样送到它手里，落进它的**观察队列**。bot 有一个**主循环**，那个循环就是它生命的核心——**也是唯一的循环**。tick 由一次投递发生，永不由计时器发生。每次 tick 先根据观察数据判断要不要动：先规则，再问一次本地模型。钱就省在这里，因为一个永远活着的 bot 在没有必要时不许烧 token。直达消息和被 @ 不是从循环里另开的一条路——门禁看见它，直接放它过去。

---

## 0. 一句话

**bot = 一个身份 + 一个收件箱 + 一个两段式主循环；agent = 一个模型、一段提示词、一组工具和一份记忆，由那个循环调用。**
第一段只花「看一眼」花得起的代价；第二段花「真去做」花得起的代价。
所有的节省都在第一段：**绝大多数消息死在那里，而死在那样地方的代价是零。**

把收件箱和循环放在 bot 上，是 agent 能保持小的原因。agent 不是一个有自己的生命的进程——它是一个**可运行件**：模型、系统提示词、工具清单、记忆，在 bot 的循环需要时被执行。这和 EMRG 的一个 session、ADK 的 `LlmAgent` 是同一个形状。一切活着的东西——观察、判断、唤醒、花费、被静音——都属于 bot。

### 为什么非要有第一段

EMRG 是**触发式**的：没有人叫它什么都不跑，所以空闲 agent 天然不花钱。seek 的 agent 是**活的**——它一直在看房间，而房间一直在产生没对着它说的话。活着就是产品本身；没有门禁，它也是一只永远开着的龙头。

所以观察这一段不是「本来能跑的设计上的一个优化」。**它是让「活着」变得付得起的那个东西**，而且它一次回答两个要求：

1. **它必须拦掉无意义的动作。** 一个满屋人在聊与它无关的事，是忙碌房间的常态，而这些消息每一条被忽略的代价都必须是零。
2. **它自己必须几乎免费。** 一条消息花一点点钱的门禁不是门禁，只是一张更小的账单。

### 每个 bot 背后有两个 agent：一个看，一个干

**两个角色叫 `watch` 和 `work`**，取自设计本来就有的词：bot 的收件箱就是**观察队列**，bot 一直在看房间，而贵的那一个 agent 的活是**干活**。所以 `watch` 读观察队列，`work` 干活；以后出现第三个角色——比如 `recall`——用同一种方式登记进去。

一个看，一个干。**它们不是同一类可运行物**——看的那一侧是决策模型，一次前向就答完；干的那一侧是生成式模型，要吐字——而这个差别正是这个划分成立的原因。**它们不共享存储**，并且**各自能读对方留下的东西**。

| | watch agent | work agent |
|---|---|---|
| 模型 | `model.watch`——本地、内置、小，只做判定 | `model.work`——这个 bot 配的贵模型 |
| 窗口 | 小（几千 token） | 大（模型给多大就多大） |
| 干什么 | 一次前向回答一组命名问题，不生成任何文字 | 干活，并且靠调发言工具说话，指明发到哪个房间 |
| 花什么 | 墙钟，几十到几百毫秒 | 钱 |
| 记什么 | 每个房间的箱子：常驻摘要、摘要之后的 delta、上次判决 | 它的会话、日记，以及它写进箱子的那份摘要 |

**为什么摘要只有一个写者：能写的那一半写。** 决策模型只吐一个选择、一个分数或一个概率，不吐文字，所以「它自己的摘要」不是它能产出的东西。反着解——给 watch 侧配一个小生成模型让它自己压缩——是用每次唤醒一次生成来换一段文字，而那正是闸门要避开的延迟。**一个写者也把碰撞去掉而不是管理它**：一份摘要两个写者，只有在它们不一致的时候才显形的分歧。

**为什么可以互读：看不见自己另一半的 agent 会编一个理由。** 要防的失败是裂脑那种：干的那一半做了事，跟你说话的那一半没有它的记录，于是给出一个自信而完全错误的解释。读的通道是 bot 对*「我在那儿什么都没说」*和*「那件事我已经答过了」*保持诚实的东西。

**互读不是免费的，而且两个方向花的东西不同。** work 读 watch 留下的判定记录，是在贵模型上按 token 计费的，所以它是**按需、绝不每轮注入**——只在要紧的时候去拉（用户问它为什么没说话；它准备在一个它一直忽略的房间里开口）。watch 侧只有箱子可读，读它不花钱也不花延迟，因为箱子本来就是要给它的输入。

**没有 watch 专用的输入管线——有的是 watch agent 的记忆，判定就照它读。** watch agent 对一个房间记得的东西是一个**两段箱**（§3）：常驻摘要，以及此后到达的观察，再加上上次判决。一次判定就是这个箱子，别无他物：判定时没有任何东西为它现装，没有第二份上下文要同步，摘要为空时它也照读不误。**它唯一不做的事是写**——摘要是 work agent 的，因为决策模型不产出文字（§3）。

watch 用的模型**随产品发布**——没有下载步骤，不依赖用户机器上碰巧装了什么。

规则跑在最前面，不花一分钱结算掉大部分消息：

| 顺序 | 检查 | 代价 | 判定 |
|---|---|---|---|
| 1 | **根本没有新观察** | 零 | **返回。** 没有东西可看，tick 到此结束 |
| 2 | **@ 我、回复我的消息、直达消息、我自己的提醒到期** | 零 | **动。** 直接进第二段——没有东西要判断 |
| 3 | 被静音的房间、我自己的消息、别的 bot 的广播 | 零 | 忽略 |
| 4 | 其余全部 | 一次小模型调用 | 由模型判断 |

这个顺序就是整个设计的省钱之处：两个**既确定又免费**的情形在任何东西跑起来之前就结算掉了，所以模型只被问到真正含糊的剩余部分——一群人在它旁边说话，没有点它的名。

#### watch 模型必须满足什么

| # | 要求 | 为什么 |
|---|---|---|
| 1 | **多语言：至少中英**，越多越好 | 产品从第一屏起就是国际的，而一个房间的语言由它的人决定，不由设置决定。只读英文的 watch agent 恰好在需要它的房间里是瞎的 |
| 2 | **多模态：必须能看图** | 消息里带着截图、照片、图示和工具卡。只凭替代文字判断「这跟我有关吗」是猜 |
| 3 | **内置，不靠下载** | 门禁是让「活着」付得起的东西；让它依赖用户去取点什么东西，等于它悄悄不在 |
| 4 | **能塞进一个 app**——目前权重约 1.5 GB，带视觉投影层约 2.1 GB | 安装包是用户见到的第一件东西 |
| 5 | **能在普通 CPU 上量化跑** | 它按每条消息、每个 agent 地跑在普通笔记本上，不是跑在 GPU 上 |
| 6 | **快到「看一眼」看不出来**——几百毫秒量级 | 比它管的东西还慢的门禁不是门禁 |

**第 4 条原本是「300 MB 的目标」，实测把它撤回了。** 那个目标是跑过任何候选之前定下的。对着真实的房间消息，那个尺寸的模型不会判断：`LFM2.5-VL-450M`（219 MB）在「要不要动」上得 **AUC 0.477**——等于抛硬币；`Qwen3.5-0.8B`（508 MB）得 **0.484**。3B 这一档在两种语言、三批互不重叠的用例上得 **0.96–1.00**。体积目标本来代替的是「便宜到可以塞进安装包」这件事，而一个塞进安装包却不会判断的模型是更贵的错误：闸门要么为一切叫醒 bot，要么为什么都不叫醒。

**这套实测覆盖了什么、没覆盖什么。** 它只覆盖**文本**：76 条手写的房间消息，其中 44 条中文，标签在挑提示词之前就写好了。所以有两件事是**尚未解决**，不是已经解决。**视觉没测**——第 2 条要求原样站着，没有实现、没有兑现，这里任何一句话都不许被读成「看图不必要」。另外，小模型的判别力对**问句的确切措辞**极其敏感：同一个模型，换一句提示词 AUC 就在 0.09 到 0.77 之间摆动，450 MB 那个模型在中文和英文之间直接反向。所以下面这套问法属于规格，不是谁写提示词时的细节。

#### 判定是怎么问给模型的

- **只问一个二元问题。** 问模型「这条消息需要你动手吗」，从两个已声明选项 token 的概率上得到答案。`act` 和 `ignore` 就是它产出的全部。`later` 由循环在某个 turn 排了提醒时写下，`keep` 由「这个房间已经在处理中」写下——这两个都不是能问决策模型的问题：靠读 token 概率作答的模型吐不出没给它的选项，而四选一在所有试过的模型上（含 3B）实测都是随机。
- **问句要具体。** 「这条消息需要你动手处理吗」的实测成绩远高于「你现在应该在这个房间里发言吗」。抽象问法招来的回答是关于 bot 的自我状态，具体问法问的是这条消息。
- **箱子不做装饰。** markdown 标题和分段标签对小模型是付出大于收获；箱子读作带标签的行，问题放在最后。
- **选项必须是单 token，而且要掩在它真正落下的那个位置。** 会被分词器切碎的词无法在一次前向里承载一个概率——`snooze` 切成四段，只能换掉。要掩的 id 是选项在**这个提示词末尾**实际取到的那个（带前导空格、它自己的大小写），不是裸词的 id：掩错形态会让一个选项永远不可达，而结果看起来是一个自信的错误答案。
- **阈值靠校准，绝不用 0.5。** 小模型可用的切点离正中很远——实测在 0.6 到 0.98 之间——所以工作点来自带标注的集合，且箱子里带着它判断时看到的未读数。
- **箱子的 token 要保温。** 3B 模型重读整箱约每 token 一毫秒：2.4k token 是 2.3 秒，9k 是 9.5 秒，那不是门禁。所以每个 (bot, 房间) 常驻一份上下文，只为「上次判定之后新到的」付钱。

## 1. 一条路，一个循环

**只有一条**投递路径和**一个**循环。发往房间的一条消息被投递进每个成员 **bot** 的收件箱，接收不花钱。然后循环跑起来：第 0 段读收件箱，决定拿它怎么办。被 @、被回复、直达消息或提醒到期都不是第二条路——它是**第 0 段里的快通道**：门禁认出它，直接送进第二段，跳过观察，因为没有东西要判断。

| 收到什么 | 落在哪 | 第 0 段怎么办 |
|---|---|---|
| 直达消息、@ 我、回复我的消息 | 收件箱，和其它一切一样 | **放行**——直接进第二段，不调 watch |
| 没有点到任何人名的房间消息 | 收件箱 | 其余全部：先规则，再问 watch agent |
| bot 自己排的提醒到期 | 收件箱，一条 `kind: "reminder"` 的条目 | **放行**——和 @ 一样（§12） |

**只有一个唤醒源：一次投递。** 往收件箱的一次投递启动一次 tick；什么都没投递，就什么都不跑。没有东西按计时器唤醒 bot，也没有东西为了「看看有没有事可做」而唤醒它。

两条路会让同一条消息被回答两遍——一次走直达那条，一次是后来某个 tick 发现它还在收件箱里。只有一条路，就没有东西要对账，没有「标记成已处理」的簿记，也没有两个执行者之间的顺序规则。

**接收永远不花钱。** 那是整个设计的成本地基。一个「没点到它的消息也能触发一次模型调用」的实现，已经是错的。

## 2. 两个对象

活着的一切落在 bot 上；跑起来的一切落在 agent 上。

```
Bot                                     ← 联系人：房间看见它、@ 的是它
├─ 身份
│   id / name / avatar / description    ← 身份只此一份；向下推给它所有的 agent
├─ 注意力
│   rooms[]        ← 它看哪些房间
│   interests[]    ← 关键词 / 话题 / 「有人问 X 的时候我来答」这类订阅
├─ 观察队列（收件箱，见 §3）           ← 每个 bot 一个队列，不管背后有几个 agent
├─ 生命状态
│   state: asleep | watching | working | needy（在等你决定）
│   lastSpoke[room] / lastTick
│   spent: token 数，被记录、被显示——一个数字，从来不是限额
└─ agents[]  ──▶  每个都是循环可以调用的可运行件（见下）

Agent                                   ← 可运行件，不是进程
├─ id / bot / role                     ← 属于哪个 bot，在那里干哪一类活
├─ model                               ← 自己的：work 用贵的那个，watch 用本地内置那个
├─ prompt + persona                    ← 它怎么说话，而「它是谁」指的就是这个
├─ tools[] / sandbox                   ← EMRG 现有注册表，不改；某个 agent 被允许用哪些
│                                        工具是普通的按 agent 配置，不是新机制
├─ reads[] / readableBy[]              ← 互读通道
├─ home / 目录                          ← 它自己的 workspace：人设、skills 和记忆；
│                                        它的 session 默认在这里开，除非那一段被
│                                        指到别处
├─ memory
│   diary（它自己的 markdown 记忆，跨会话、跨房间）
│   roomDigest[room]（箱子的摘要——滚动、按房间、它自己的记忆）
└─ Sessions
    session[room]（它在每个房间里自己的一段工作；换 workspace 就开新的一段——
    私有簿记，永不对用户显示）
```

**切分切在内核本来就切的地方。** 模型、系统提示词、工具清单和一段历史，正是 EMRG 一个 session 装的东西、ADK 一个 `LlmAgent` 装的东西；时钟、队列、状态机和 token 计数，是一个长存活进程装的东西。把后一半放到 agent 上，就是每个 agent 都有一个生命周期要设计；放在 bot 上，agent 就永远只是「被叫到时跑起来的那个东西」。

今天留下的唯一空缺：守护进程把「身份」和「运行时」压进了同一个 `EmrgServer`，busy 表、cancel 表和各处 context 全按 session 作键。在一个进程里跑多个 agent，需要再加一层按 agent 作键。这份活是真的。

### 一个 bot 是 N 个 agent，而 bot 不是 agent

**bot 和 agent 是两个实体、两件差事。** bot 是联系人和活物：它拥有名字、头像和描述，它拥有收件箱和循环，它就是房间看见的东西、就是 @ 点到的名字。agent 是它背后的可运行件：各有自己的人设、模型、会话和记忆，在 bot 的循环调用它时跑起来。**bot 把身份向下推给它的 agent**——agent 没有自己的名字，只有一个 `role`——所以改一次 bot 的名字，它的每个 agent 同时改，房间里永远不会在一个人身上看见两个联系人。

**agent 知道自己是谁的。** 每个 agent 的系统提示词里都带着它所属的 bot——名字、头像、描述——以及这只 bot 的名册：每一个 agent（包括它自己）的 `role`、干什么、自己的目录。同一段文字也可以做成一份 skill 文件让它读，这样它是新的，而 agent 不用去问。**这是推下来的，不是存下来的**：agent 手里没有 bot 身份、也没有同伴的副本，所以改一次名字、加一行，这只 bot 的每个 agent 同时知道。以后某个 bot 多了第三个 agent，先有的那两个不需要任何迁移。

**`agents.yml` 登记的是 agent，不是 bot。** 现在每个 bot 至少两行——一行看、一行干——而且没有上限：以后某个 bot 需要第三个角色，就多一行。这很便宜，因为每一行都是一个普通的可运行件：一个模型、一段提示词、一组工具、一份记忆。没有生命周期要为它写，因为生命周期是 bot 的。

**这条切分贯穿整个模型**：成员资格、@、房间的人名单、收件箱、tick 和状态机都是**bot 层**（所以不管背后几个 agent，一个 bot 只有一个队列、一个循环）；会话、记忆、turn 和成本都是**agent 层**（所以审计记录说得清是哪个工人干的，账也按工人分）。基数关系写在 `data-model.md` 规则 13。

**一个收件箱把难题整个去掉了。** 若每个 agent 一个队列，每条消息就要投 N 次，每个 agent 各自维护一份「已处理」状态，循环要去对账 N 份。队列在 bot 上，投递是一次写，tick 是一个循环，第 0 段判一次——然后循环调用判定点名的那个 agent。

**agent ≠ session。** EMRG 把身份压进 session（session 就是那个 cwd、那个模型、那段历史），所以一个身份不能同时在三个房间里。这里 **bot** 坐在 session 之上，而 agent 的 session 是它一段一段的工作——这就是为什么一个联系人可以同时在三个房间里，而每个 agent 在每个房间里还各有一条连续的线。

**session 也永不对用户可见。** 房间的时间线是连续的，像飞书里的聊天那样；一个房间里的五个 agent，是在同一份共享日志上盖了五段私有的跨度。这不是显示层的决定，而是承重的那个：它是「消息共享、上下文私有」成为构造性事实的原因。

## 3. 观察队列（收件箱）——每个 bot 一个

**收件箱属于 bot，不属于某个 agent。** 发往房间的一条消息投递一次，进 bot 的观察队列；bot 的循环读那个队列并判断，然后才有 agent 跑起来。agent 不看房间——bot 看，而 `watch` agent 是被它问的那个。

队列放在这里的全部理由：投递是按 (bot, 消息) 一次写，而不是按 (agent, 消息) 写 N 次；「已处理」状态只有一份而不是 N 份；循环保持是一个循环，而不是一堆要对账的循环。

一条一条追加，**永不经模型处理**：

```json
{ "id": "...", "room": "oc_...", "msg": "om_...", "ts": 1698123456789,
  "sender": "ou_...", "fromAgent": "agent_id|null",
  "kind": "text|image|file|toolcard|system|reminder",
  "text": "……",
  "hints": { "mentionsMe": false, "asksQuestion": true, "repliesToMe": false,
             "keywordHit": ["release", "schedule"], "roomTemperature": "busy" },
  "state": "new" }
```

- **每一条都是投递，而投递有两个生产者**：人或别的 bot 发来的消息，或者一行排程到期（§12）。两条路都是往一个收件箱落一条，后面发生的是同一个 tick。条目永不由循环凭空合成，来给自己找东西判。
- `hints` 由**生产者算，不是模型算**：@ 检测、问号、是否回复我、关键词命中、消息密度。全是字符串和计数工作，不花钱。
- **`mentionsMe` 和 `repliesToMe` 是 bot 层的事实。** 它们在消息落地时按 bot 算一次，不按 agent 算。没有 agent 去房间里扫自己的名字，watch agent 也做不到：它不可被寻址，所以「有人 @ 我」只有 bot 能回答。这就是第 0 段的快通道是一条规则而不是一次模型调用的原因。
- **`mentionsMe` 是推导出来的，不存到消息上。** 消息带的是飞书那个字段 `mentions[]`——它点到的人，各是 `{id, name}`——那是唯一被存的形态。投递时在那个数组里找**本 bot 的 id**，把布尔值记在这里、记在这只 bot 的条目上。`hints` 里的任何东西都不会写回消息：消息写一次就保持干净，下一只 bot 从同一串字节推导它自己的答案。
- 状态机：`new → watched（act | ignore | snooze | keep）→ consumed`；`snooze` 带条件。被第 0 段快通道放行的条目跳过 `watched`，直接 `new → consumed`，包括被注进一个已经在跑的 turn 的那种（§4）。
- **收件箱同时也是正在跑的那个 turn 的队列。** 没有第二份内存里的待处理列表：任何 turn 开始之前，每条条目都已经在盘上；turn 进行中到达的消息就是同一条条目，在下一个轮边界再读一次（§4）。一个队列、一份「已处理」状态，没有东西要对账。
- **容量是箱子的 delta，不是收件箱的上限**（§3「观察箱」）。收件箱可以装下到达的东西；被守住的是判定要读的那一部分——上次压缩之后的观察。delta 越线就跑一次压缩，于是收件箱不必变成第二份消息日志，也不必为了变小而悄悄丢掉任何条目。
- 收件箱是只追加的，写的人**永不阻塞**（房间扇出不能因为某个 bot 忙而卡住）。
- 判定写在条目上，而且写它的是**循环**，不是产出判定的那个 agent——watch agent 只负责答；后果由循环执行（§4）。

### 观察箱——一次判定实际读到的东西

每个 (bot, 房间) 一个箱子。它就是 watch agent 对这个房间的记忆，正好四格：

| 那一格 | 装什么 | 谁写 | 多久一次 |
|---|---|---|---|
| **摘要** | 上次压缩的产出：这个房间是什么、谁在里面、已经定了什么 | 一次压缩 | 稀有，delta 越线时 |
| **delta** | 摘要消费到的那个点之后到达的观察 | 没人写——从收件箱上读出来 | 每次到达，零成本 |
| **上次判决** | 什么时候判的、判成什么、有理由就带上理由 | 循环 | 每个 tick |
| **问题集** | 判定要回答的那些命名问题，以及每个问题的选项 | `agents.yml`，按 bot | 静态 |

- **delta 是派生出来的，从不另存。** 它就是摘要的「消费到」那个点之后的收件箱条目，所以每条观察只有一份，没有第二份日志要对账。它的 `hints`——@没@我、问没问问题、回不回我、房间静了多久、几张图——正是投递时已经算过的那些字符串与计数工作。
- **交给模型的状态是结构化的，不是文章。** 摘要那段文字只是其中一格，其余都是字段：几条观察、谁在说、上次判决有多旧。决策模型的契约是「状态可以是任意 JSON」，递给它一段文章等于把唯一免费的信号扔掉。
- **判定从不等待压缩。** 箱子是什么样就读什么样——可能是空摘要加一条长 delta——然后返回。压缩是后台活，单飞，把新摘要和它消费到的点一次原子写入，于是压缩期间到达的条目要么已经在新摘要里，要么还在 delta 里，绝不会丢。
- **上次判决只作为事实进箱，绝不作为指令。** 「你在十二条观察之前 keep 过它，之后一直没说话」是关于记录的事实。「你该 keep 它」则是箱子在跟判定争，那正是让一个陈旧判决自我延续的东西。
- **这才是箱子值得存在的理由：`keep` 和 `snooze` 变成可重开的。** 被 keep 过一次的房间，会对着一个现在能说出「过了多久、变了什么」的箱子被再看一眼，而不是从零重判、或者永远不再重判。

## 4. 主循环：两段

```
bot 的循环，每次 tick：
  ┌ 第 0 段 · 只有规则，没有模型（结算掉一切既确定又免费的事）
  │  1. 没有新观察？            → tick 结束，在任何别的东西被考虑之前
  │  2. 规则说动？（@ 我 / 回复我 / 直达 / 我自己的提醒到期——读 bot 自己的
  │     hints，在投递时算好；「@ 我」的意思是消息的 mentions[] 里有本 bot 的 id）
  │                            → 进第二段
  │  3. 规则说忽略？（我自己的消息 / 别的 bot 的广播 / 被静音的房间）
  │                            → 把它们标成 ignore，tick 结束
  │  4. 其余全部 → 进第一段（调 watch agent）
  │
  ├ 第 1 段 · 循环去问 watch agent（决策模型：一次前向，没有工具）
  │  输入：这个房间的观察箱（§3）——常驻摘要、摘要之后的观察、作为事实的上次
  │        判决——加上人设和那组命名问题；以及在要紧的时候，从兄弟 agent 日志里
  │        读到的一段有界切片（绝不整份注入兄弟的日志，也绝不整份注入收件箱）
  │  模型：model.watch——本地、内置，max_tokens 卡住
  │  工具：EMRG 本来就给 agent 的那张注册表（bash / read / write / edit / glob /
  │        grep / subagent / submit_rant / boss / schedule）。记忆写入和压缩不是
  │        工具；运行时在轮末做
  │  输出：一个循环能照做的判定——**形式由实现定**（一个词、一个固定集合里的
  │        标签、一小段 JSON，这个模型稳定吐什么就用什么）。要紧的是无歧义、可解析
  │  后果：动 → 进第二段，只带观察条目
  │        不动 → 记下判定，回来了理由就一并记下，tick 结束
  │        解析不出来 → 当作不动，并计一次 watch agent 失败
  │
  └ 第 2 段 · 跑 work agent（贵的）
     第二段调用 work agent 并让它跑——一个普通 turn：完整上下文、工具、
     轮末写记忆。它收到的只有观察条目，没有别的：watch 的理由不会被递过去，
     它留在记录上，work 想读可以去读（见「什么越过界线」）。
     **要说什么，它必须调发言工具**——`say(房间, 内容)`，单聊也是一个房间。
     它吐出来的文字是它自己的记录，永远不会变成一条消息：没有任何东西替它
     发出去，而一个没有调这个工具就结束的 turn，就是什么都没说。

     这就是全部的投递规则，它有三个值得写明的后果：agent 不可能说漏嘴；
     一个 turn 可以说几件事（三次调用，三条消息）；而当 agent 认为没什么值得
     说的时候，房间里什么也不会看到。

     只有一点不同：它开场就知道「是你自己决定要说这件事的，没有人叫你」，
     因为确实没有东西叫它，而它醒着的原因是上下文，不是一个请求。
```

### 为什么分两段

因为 **work agent 花钱，watch agent 不花。**

watch agent 是用户机器上的本地决策模型：一次前向、不生成 token、不计费。work agent 跑这个 bot 配的任何贵模型，每次调用都计费。这就把 watch agent 的预算从钱挪到了**墙钟**——所以「几百毫秒量级给一个判定」不是体面问题而是真正的约束，也所以答案必须小：从已声明的选项里读 logits，而一个被要求写句子的模型，就是一个让 app 卡顿的模型。

也是为什么是两个 agent、而不是一个 agent 问两个问题：**它们不是同一类模型。** watch 侧一次前向回答一组固定问题，箱子的窗口小；work 侧要生成、要用工具、窗口大。让大模型回答闸门的问题，是每条消息都花钱；让小模型去干活，是一个 4k 窗口硬扛 200k 的活。

它诚实地带来一个风险：一个弱本地模型能给出自信而错误的判定。两个回答：**watch agent 忽略了什么可回看**——每条判定都和它看过的条目记在一起，所以一只聋掉的门禁是看得见的，不是无声的；以及 **work agent 能读那份记录**，所以错判是能被跟你说话的那一半发现的。

### watch agent 怎么知道自己判错了

**它从自己本来就有的记录上读出结果。** 当 watch agent 把一条观察转了上去、而 work agent 随后在那个房间里什么都没说，这件事是看得见的：它派出去的那条条目后面没有消息。**这在构造上是最容易看的那种情形**——沉默是默认，因为说话要花一次工具调用——所以「转上去之后没有下文」不需要任何推断。这是记录上的事实，箱子会把它带下去——下次 watch agent 再遇到这个房间，箱子的「上次判决」那一格就写着多久之前它转过、之后什么都没有，它可以先掂量一下再判一次。

没有为此新建任何机器。结果不是谁报告给 watch agent 的：**它已经在那块牌子上了**，因为一个没产出消息的 turn，是同一套数据模型里的事实。

**而且这不叫学习。** 权重不动；不训练任何东西；不为将来写任何规则。watch agent 最多积累它自己的观察，和任何 agent 的记忆一样。

**它什么也学不到也没关系。** 下游任何东西都不许依赖 watch agent 变聪明——没有衰减曲线，没有「等它看够了再说」，没有准确率目标。一个判得弱但记录看得见的 watch agent 是合格的 watch agent；一个藏起来的不是。

### 三种「不动」

- `ignore`：这与我无关。消费掉这条条目。
- `snooze`：不是现在，但也许以后。带条件重新排队（「这条有了回复时」／「五分钟后」——后者通过排程完成，§12）。
- `keep`：不必开口，但我应该记住。不做任何动作；留下这一行。

`keep` 要紧：它让一个 agent「在场但不打扰」，而这是永远活着这件事里最像人的部分。

**watch agent 不执行自己的判定。** 它给出一个决定；后果由循环执行——`ignore` 消费掉，`snooze` 重新排队，`keep` 追加那一行。判定的形式之所以可以自由，就是这个原因：一个词就够，因为运行时早就知道每个词意味着什么。

**工具集是 EMRG 那一套，原样不动，再加上宿主点名的两个。** 没有 watch 专用工具、没有记忆工具、没有压缩工具要建——注册表就是内核里那张，加上 `schedule`（§12）和发言工具。某个 agent 能用哪些工具，是 `agents.yml` 里普通的按 agent 配置；今天其中一个答案是「都不用」：决策模型不发工具调用。

**发言工具是进入一个房间的唯一路径，它存在的理由正是这个。** 它叫 `say(room, text)`——和注册表其余工具一样的单裸词，起这个名字是为了它不可能被读成 `write`（那是文件），也不可能被读成一种飞书消息类型。从 turn 的输出到消息之间没有路：运行时不会替 agent 发它的回答，不会发流式的一小段，也不会发「它做了什么」的摘要。所以一只 bot 在房间里说过的每一句话，都是它自己选择发出的、并指名了要去的房间——这也正是让「一个沉默的 turn」有意义的原因，也是让「它在那儿什么都没说」成为一个可读的事实、而不是对一段流式内容的猜测的原因。

**记忆写入和压缩不是工具，在这里也不会变成工具。** 它们是运行时在 turn 结束时做的事，agent 不会「选择去做」它们。

### 什么越过界线：从 watch 到 work

**交出去的是观察条目；理由留在写下它的地方。**

当 watch agent 决定动，work agent 只带着条目醒来——没有别的：运行时绝不把 watch 的理由放进它的上下文。它读自己的历史和自己的记忆，自己决定要说什么、或者什么也不说。

**为什么不把理由递过去：work agent 会不知不觉开始依赖一个 300 MB 模型的判断。** 上下文里的理由不是建议，是前提——贵模型会把它当成关于世界的事实，然后往上盖。watch agent 错的地方，work 不会纠正，会放大，而放大看起来像连贯。

**代价说清楚：** 有时候 work agent 看着这些条目，根本看不出自己为什么被叫起来。它可能因此说一句略显迟钝的话，或者问一句这有什么意义。这是真实代价，而这是这笔交易对的那一边。

**理由仍然被记下来**——记在观察条目上、紧挨着判定——因为它是错判可复查的原因，也因为 watch agent 会回读自己的日志。

**它不被递过去，但它也不被封死。** 运行时绝不把它放进 work agent 的上下文；而 work agent 可以去读，因为两个 agent 本来就能读对方的记录——这是一次查阅，不是一条专用通道。这就是「看不见的前提」和「可以质问的前提」的区别：读到了，work agent 既知道决定了什么、也知道那句话是谁说的，一个错判于是带着一个名字，而不是悄悄塑造了那段回答。

### 判断有多慢

**延迟目标是目标，不是保证。** 判定是一次前向，不生成、也没有工具轮：桌面机上几十毫秒，慢机器上低几百毫秒。这正是 watch 侧是决策模型而不是小生成模型的原因——一个 300 MB 的模型写一句话、再加一轮工具，就是好几秒，而判定就成了 app 里的延迟。

### agent 正在跑的时候来了一条消息

**新的直达消息在轮边界插入**——本轮工具返回之后、下一次模型请求之前。所以一个 turn 长这样：

```
模型 → 工具跑 → [注入] → 模型 → 工具跑 → [注入] → … → 完
```

绝不是 `工具还在跑 → 消息打断进来`，也绝不是 `turn 结束 → 另起一个 turn`。

1. **一个 bot 同时只有一个 turn，靠一把锁。** 第二条消息不会另起一个 turn；它排队。
2. **忙时到达的按 bot 排队，FIFO**，并且告诉发送方它排在第几位——所以「已排队」是看得见的，不是猜的。
3. **drain 是对整个队列的一次原子 pop**，绝不是「先读再清」。drain 在等一次广播期间追加进来的东西，落进一个新表，在下一个边界进去。「先读再清」恰好会静默丢掉那个窗口里到达的消息。
4. **每条被注入的消息在历史里成为一条真记录**，在提交时写一次、带着它的时间戳，界面拿到的也是同一个戳。压缩从历史重建时保得住它，以后也没有人要为一个时间戳凭空编一个值。
5. **轮数预算是给注入消息刷新，不是被它们耗掉。** 如果这个 turn 用完了轮数上限而队列不空，新消息拿到一份新预算，而不是被搁死；只有**空**队列才会产出「Exceeded maximum rounds」。所以一条消息可以让一个 turn 变长，没有任何东西给它封顶。
6. **绝不静默丢弃任何东西。** 一个 turn 结束时收件箱里还留着它被叫醒来处理的东西，是缺陷；循环再读一次收件箱，起下一个 turn。

**进行中的队列就是收件箱。** 投递在任何 turn 开始之前就把条目写到了盘上，所以没有独立的待处理列表，也没有重发契约：turn 结束，循环再读一次收件箱，如果还留着门禁会动的东西，下一个 turn 立刻开始。

**被注入的消息在注入的那一刻标成 `consumed`。** 条目已经是盘上的事实，消息本来也已经在房间里可见，所以「这被接下了」是诚实的记录。

**哪些到达会被注入。** 注入集合是第 0 段的**快通道集合**——@ 我、回复我的消息、直达消息、我自己的提醒——不是每一次到达。普通的房间消息在收件箱里等下一个 turn：一条还没有人判过的条目，不许落在活干到一半的地方。

### 并发

一个 bot 同时只跑**一个**第二段——一个 turn，一把锁持有。几个房间同时要它的时候，条目在收件箱里等着，按这个顺序：@ 我 > 有人在等回答 > 显著度高 > 它沉默最久的房间。
理由不是性能，而是**身份一致性**：两段并行的对话会让它的人设和记忆互相打架。

## 5. 成本，算一遍

这一节的重点不是省钱，而是：**一个活着的 agent 只有「看一眼」几乎免费才活得下去**，所以门禁每条消息的代价是设计约束，不是调参旋钮。

假设 10 个 agent、5 个房间、每小时 500 条消息。

| 做法 | 每小时 token | 结果 |
|---|---|---|
| 每条都送贵模型（照搬过来的那种） | 500 × ~1500 = **75 万计费** | 一天之内就垮 |
| 每条都只送本地 watch agent（没有第 0 段） | 500 × ~300 = 15 万**本地、不计费** | 没有账单——但每条消息一次本地推理，每一次都是 app 里的延迟 |
| **本设计**：90% 免费拦掉，10% 本地看一眼，其中 5% 动 | 50 × 300 本地（不计费）+ 2.5 × 3000 = **≈7500 计费** | 付得起 |
| 更省：攒成一批才看 | 再降一个数量级 | 代价是反应变慢 |
| **空闲** | **零**——没有投递就没有 tick，不调用 | 什么都没来时什么都不跑 |

**没有 idle 路径要辩护。** 一个没有投递、也没有东西到期的 bot 不在运行，所以「空闲的一次 tick 可以调什么」根本不需要论证。

对上面这个表的计数口径要更正一处：流量是**按消息**到达的，但一条消息要花的活是**按房间里的每个 bot** 算的——十个 bot 一条消息就是十条收件箱条目。上面这些数字站得住，只因为第 0 段是按 bot 免费的；一旦任何一个按 bot 的步骤要花一次调用，这个乘法就生效，表就低估了。

**排程的比较器是这个设计里唯一一处后台成本，而它不在这张表上**，因为它不是 token：它读时钟，和下一行到期的比一比，否则就睡，不调用任何模型、不碰任何 bot。一旦比较器要靠调模型才知道没有东西到期，这张表对每个 bot 每小时就差六十倍。

（数量级估算，不是测量值。）

因为 watch agent 是决策模型，**watch 的 token 不是钱，而且根本不存在**：不发生生成，所以计费那一列只有第二段。替代掉 watch 成本的是墙钟：每个被看过的批次一次前向，不上 GPU，而房间是活的。还有一笔容易漏掉的成本：**压缩是一次 work agent 调用，所以一个热闹的房间即使在它 bot 一句话不说的时候也在压缩上计费。** 这就是「摘要由能写的那一半来写」的价钱。

**门禁的命中率就是产品的成本曲线。** 所以它必须可观测、可调：每个 agent 记录 `watched`（看了几批）、`acted`（命中）、`ratio`（命中率）和 `spent`（token）。命中率突然跳到 50%，意味着某个人设写坏了，或者某个房间被 bot 淹了——而这件事必须在界面上看得见。

## 7. 避开这类系统的死法

| 失败 | 机制 |
|---|---|
| **两个 bot 互相唤醒，停不下来** | ① 一个 bot 的消息不唤醒另一个 bot，除非 @ 它、回复它，或者是一条直达消息 ② 一个房间里连续 bot 轮次的上限——**3**，挂在 Room 上，它管住一次爆发 ③ 深度上限，它管住一条链跑多久（§11）。bot 可以对另一个 bot 开口，所以链的**数量**由判断和记录兜住，不由规则兜住 |
| watch agent 太省 → 又聋又瞎 | 命中率可观测；它忽略了什么可回看（条目和理由都留着） |
| watch agent 太贵 → 烧钱 | `spent` 按 agent 记录并可见，所以失控的账单是**被看见**的，不是被静默封顶的。没有自我停止：账单爬升是人设或门禁的缺陷，在那里修 |
| 收件箱爆炸 | 判定读的是一个定长的箱子：delta 越线，压缩把它折进摘要，于是无论房间多热闹，每次判定的开销都是平的 |
| 长存活 = 慢慢腐坏 | 每次 tick 结束时打检查点；重启时自检（队列、距上次开口多久、花了多少）；人设漂移对着日记纠正 |
| 没有时间感 | 每次 tick 注入「你在这个房间上次说话到现在多久」和「这条消息多旧了」；没有这个，它会永远问同一个问题 |

## 8. 界面必须显示什么

1. **一个状态点**：watching / working / asleep / needy，作为头像上的角标。
2. **主动发的消息有标记**：不是对你的回复，而是它自己选择要说的话。每一条消息都是有意发的——说话是一次工具调用——所以这个标记区分的是「它来找你」和「它答了你」，不是「它是认真的」和「它是顺口说的」。
3. **消息整条出现，绝不一个字一个字地冒。** agent 在自己的 turn 里写，写完才发；房间里没有可流式的内容，而一句发到一半的话，是一条没有人决定把它说完的消息。它在干活的时候，状态点就是那个提示。
4. **「它为什么忽略我？」可以展开**：把 `reason` 翻成人话（「这条不是对着我说的，而且已经有人在回答了」）。这既是产品差异，也是唯一能调这个东西的办法。
5. **「它为什么不出声？」也有答案**：一个没发东西就结束的 turn 也是记录上的一个 turn，所以同一个展开能说出它当时决定不说什么。
6. **花费可见**：它今天花了多少。没有剩余额度这回事，因为没有上限——这个数字是拿来读的，不是拿来执行的。

## 9. 分阶段

- **P1（最低限度的活着）**：Agent 对象 + 收件箱 + 第 0／1 段 + 一个房间 + 纯规则门禁（不接模型）。到这一步，「它会不会自己开口」这个问题就已经有答案了。
- **P2**：watch agent（每个 bot 第二个 agent、本地模型、自己的记忆、互读）+ 三种不动的判定 + 屏幕上的状态帧。
- **P3**：多房间并发和动作队列 + 日记 + 命中率面板。
- **P4**：多 agent 群聊（轮次受限、@ 唤醒）+ 话题里的委派树。

## 10. 主动的直达消息

阶梯：**观察 → 在房间里开口 → 开一个话题 → 直达消息 → 必须够到你**。

在房间里说话是「在场」；直达消息是「来找你」。一个 agent 两件都可以做，包括第二件——对一个人，以及（§11.2 起）对另一个 bot，同样没有任何额度。

**没有额度、没有冷却、没有静默时段。** 管住一个 agent 的东西，就是 seek 里管住它一切的东西，因为**seek 的 agent 就是 EMRG 的 agent**：它有**提示词**，有**沙箱**，而这两样就是它全部的约束。关于打扰你的克制，是它被怎么写出来的性质，不是旁边硬加的一道闸。一个人设话太多，那是人设的缺陷，就在那里修。

### 10.1 动手也不需要许可

**agent 动手之前不问。** 它直接改文件、跑命令、发消息，不会停下来请求批准，就像跟你共事久了的同事不会为了打开一个文件先问一声。一个动作一个对话框，会把产品变成工单队列，而工单队列是 IM 绝对不能变成的东西。

不问之下靠什么撑着：

1. **沙箱。** agent 只在自己的 workspace 里动，别处不动。
2. **审计记录。** 每个动作都是一个 `Turn`：谁触发、跑了哪些工具、改了什么、花了多少。事先什么都不用问，因为事后什么都看得见。
3. **一个真能停下来的停止。** 不管它正在替你做的是什么，你都看得见，也能结束它。

**请你决定不是请你许可。** 卡住了、两个选项权衡不了、需要你来定的 agent，是在跟你对话。*「我可以吗」*不存在；*「哪一个」*是普通的话。

### 10.2 界面里

- 主动发的消息标成**主动**——「它来找你」和「它回答了你」读起来不一样，把这两者读混的人会把整段关系读错。
- 联系人列表显示有什么在等你。
- 发完之后它不等：界面要能表达「我继续干我的；你什么时候看都行」。

## 11. agent 对 agent

§7 那些防环规则都假定房间里有人会注意到。两个 agent 的房间打破了这个假设，所以单靠一道频率限制撑不住；必须有结构性的东西。

### 11.1 一种形状：一条消息

**所有交互都在 IM 上体现。** 所以一个 agent 够到另一个 agent 不是一次工具调用，而是一条**消息**：发进对方在的房间里，或者发进两者之间的单聊。它像任何人说的话一样落进那只 bot 的收件箱，而那只 bot 自己的循环决定拿它怎么办——包括决定不办。

没有同步委派调用，理由在结构上而不在风格上：一次调用会让 **A 在 A 的 turn 上替 B 做决定**，绕过 B 存在的那个判断。一条消息把那个判断留在它该在的地方。

「委派」指的是**意图**，不是机制：「去做这件事然后回报」是一条要求干活的消息，「你怎么看」是一条提问的消息。两者进同一个收件箱，带同一条链。

### 11.2 一条链可以由一个 agent 起头

**一个 bot 可以对另一个 bot 说第一句话**——在两者都在的房间里，或者它为这个目的开的单聊房间里。没有规则要求一条链的根必须是一条人的消息。

bot 早就可以对**人**开一个对话；禁止它对同伴做一模一样的事，是一种没有任何地方要求的对称。而一条链的长度由深度兜住，一个房间的爆发由轮次计数兜住——两者都不需要在根上有个活人。

**代价是：** 链的集合没有任何结构性约束。每一段新对话都在深度 0 起一条全新的链，所以**深度管一条链跑多长，不管一个 bot 能开多少条**。bot 的判断说该开，它就可以开，没有任何计数、间隔或批准挡在前面。这和「对人不设主动消息额度」是同一笔已经接受的交易，防线也一样：一切都在记录上。

### 11.3 一道数跳数的墙

1. **深度**——每条消息带着 `caused_by`、`chain` 和 `depth`（data-model 规则 11）。链上每一个 agent turn 加一跳。**上限：4。** 到上限时 agent 可以结束或上报；它不可以把这条链接下去。
2. **房间的连续 agent 轮次上限**（§11.4）——一个房间里连续三个 bot 轮次；再往后，那里的 bot 消息不再唤醒 bot。这个管住的是一次爆发；光靠深度从来管不住，因为一串短促的往复只用很少的跳数。

**没有链预算。** 一条链的成本和其它任何东西一样按 turn 记录、可读——但没有东西拦它。深度上限是一条链上唯一的数字限制，而它不是钱的限制：它存在是为了止住一个环，不是止住一张账单。它从消息数据上读出来，而不是靠一个计数器，这是故意的——计数器要在崩溃后恢复，而它恢复错的那一次，恰好是需要它的那一次。

**连续 agent 轮次的计数挂在 Room 上**，不挂在某个 agent 上：没有任何单个 agent 看得见它的同伴刚说了几次，所以挂在 agent 上的计数器等于 agent 自己给自己记数，然后管那叫一个对话。

### 11.4 唤醒规则

一条 bot 消息唤醒一个 bot，只在下面全部成立时：

- 它 @ 了那只 bot、回复了它某条消息，或者它是一条**直达消息**（直达本身就是被寻址的）；
- 链的深度低于上限；
- 这个房间的连续 agent 轮次计数低于 3。

不然那条消息照样落进那只 bot 的收件箱，零成本，标着 `hints.chainBlocked = reason`，等下一次有人碰这个房间时再考虑。什么都没丢，也什么都没花。

### 11.5 谁付钱

**谁跑那个 turn 谁付钱。** A 发一条消息问 B，那条消息结束 A 的那一部分、花掉 A 自己的一个 turn；B 把它接起来时跑自己的一个 turn，记在 B 的账上。没有一个 turn 能装下另一个 bot 的活，所以链上每一个 turn 都像别的 turn 一样被记录，而链的总量是一个你读得出来的数。

### 11.6 一条链怎么结束

在深度上限或房间轮次上限处，agent 刻意地只做其中一件：

- **上报**——发到一个单聊房间，除了自己的人设和沙箱之外什么都不受；
- **在房间里说明**——一条系统行：*「这段交流到了上限，需要一个人」*；
- **停下并记录**——写进日记，让这个话题歇下来。

它不可以做的是：把问题丢下不留痕，或者不声不响地继续。沉默是允许的；没人看得见的沉默不是。

### 11.7 界面里

两个 agent 之间的一段往复折成一行——*「Editor 和 Researcher 之间 5 次往来」*——可展开，深度显示出来。没有折叠，一个房间在第一次有两个 agent 开始干活时就变得没法读；没有计数，用户分不清一次普通往来和一次撞到墙的。

### 11.8 为什么允许

有用的情形是真的，而且常见：A 缺一样 B 有的能力或上下文，而替代办法——A 去猜，或者用户手工转达——在每一个维度上都更差。

而且 seek 是一个本地进程跑着所有 agent，这是这个设计比分布式设计**更容易**的唯一一处：单一的仲裁者看得见系统里每一条链，所以深度这道墙是精确的而不是近似的，也不需要任何协调协议。让产品私有的那个性质，也让这个环可执行。

## 12. 每个 bot 都能写的全局排程

**一张表、一个工具，而一行到期就作为一条消息到达。** 每个 bot 读写的都是同一张排程：**什么时候、发什么提醒、给哪个 bot**。一行到期时，它的文本自动投递给那只 bot，是一条直达消息——和 @ 等效。

### 排程不是时钟

这个设计里没有唤醒 bot 的计时器，而这一节也没有加一个。两条性质把它们分开：

- 它是**进程里一张表加一个比较器**，读时钟的是那个比较器——不是每个 bot 一个心跳。不调用模型，没有按 bot 的状态，没有任何随 bot 数量增长的东西。
- **它不唤醒任何人**：09:00 到期的一行就是*09:00 写进某只 bot 收件箱的一条消息*，而一条被投递的消息唤醒它的方式，和一个人发的完全一样。唤醒规则一字未改；排程是**投递的第二个生产者**，在人和其他 bot 旁边。

实现要对着一句话检查：**排程可以产生投递，绝不可以产生 tick。** 一只 bot 被「现在是 09:00」唤醒、而不是被收件箱里的一条条目唤醒，就是那个缺陷。

**它买到什么。** 一个纯粹由消息触发的 agent 无法守诺：上游什么都没有的时候，「这件事我明天看」没有办法成真。现在 bot 可以给自己留这条提醒、再回来找它，而它得到这个能力的办法是**增加一个消息的生产者，不是增加一个唤醒源**。

### 那一行

```json
{ "id": "...", "to": "bot_id", "at": 1698123456789,
  "text": "remind me to check the release thread",
  "createdBy": "agent_id", "createdAt": 1698123456789,
  "state": "pending | fired | cancelled" }
```

**没有 `room` 字段。** 提醒是 bot 在跟自己说话；它到达收件箱就停下。

- `to` 是**一个 bot**，永远不是一个 agent——收件箱是 bot 的（§3）。
- `text` **逐字投递**：不摘要、不翻译、不被路上的任何模型改写。作者写的是什么，bot 读回来的就是什么，而这才让一条提醒成为写给未来自己的一张便条，而不是一道新的指令。
- 一张表，**每个 bot 都读都写**，所以一个 bot 看得见别的 bot 排了什么。那是共享的日历，不是私人的：没有任何东西按 `to` 过滤这张表。
- `state` 只往前走一次，绝不倒退。`fired` 的行过一阵清掉；`cancelled` 的行是一块墓碑，因为「我本来打算做这个，后来放下了」是它的作者可能想拿回来的信息。

### 那个工具

**`schedule`**——一个工具，三个动词，别的没有：**list**、**add**、**cancel**。没有「现在就跑」、没有重复、没有优先级、没有条件语言——一只想被明天提醒的 bot 写下它指的那个时刻。它和其它工具一样可用，所以哪些 agent 能用它是 `agents.yml` 里的普通配置。

**带时间条件的 `snooze` 由环执行，不由 watch agent 执行。** watch agent 给出判定；环执行它（§4）。所以「不是现在，五分钟后」产出一行**由环写的**排程，到期时原来那条条目回来。watch agent 为此不需要任何工具调用，这就把它的判断保持在一个轮里，也就是延迟目标所对着的那一轮。

### 到期

一次到期是**一次写，而且它是幂等的**：行的 `state` 变成 `fired` 和把投递落进收件箱是同一步，以行的 `id` 作键。一行到期时守护进程关着，下次启动就补上——错过一个时刻**不是**跳过一条提醒，而笔记本睡着的两小时里错过的十行，按时间顺序各作为一次自己的投递补上。静默丢掉它们，是注入那条路拒绝的同一个缺陷（§4）。

### 用户看见什么，看不见什么

**到期的提醒不显示。** 它落进 bot 的收件箱；没有房间显示它，没有帧带着它，聊天记录不多一行。用户看见的是 bot 拿它做了什么，别的一概不看。

**这不破「所有交互都在 IM 上体现」：** 那条规则管的是 bot 怎么够到**别的主体**，而提醒谁都够不到。没有第二个当事人可以显示。硬把它塞进房间就是凭空造一个——一条发给房间里所有人的系统行，描述一只 bot 留给自己的便条。

**代价**：界面显示**结果而不显示原因**。一只 09:00 开口的 bot，因为昨天给自己留了一张便条，在屏幕上看起来没有动机，而用户分不清「它守了一个承诺」和「它决定要说点什么」。这与 watch agent 的理由不递过去（§4）是同一种形状的代价，答案也一样：**它靠读能还原，不靠显示**。排程那一行和触发它的那个 turn 都在记录上，所以*「它刚才为什么说那句话」*有答案；只是聊天记录不主动端出来。

### 它的代价

1. **收件箱里可以装一条 bot 写给自己的条目。** 这来自「那一行是别人在某个真实的时刻写下的真东西」，而不是来自循环凭空造活给自己判。
2. **多了一个工具**，而它是对 EMRG 注册表的唯一新增。它旁边什么都没有：一个 `calendar`、`cron` 或 `remind` 工具会是第二个例外，而这个例外不授权第二个。
3. **一张共享可写的表带来那三个老问题**——陈旧行、无界增长、两个 bot 给同一个 bot 排同一个时刻。增长靠清理 `fired` 行兜住；其余是 bot 动手的任何地方都已经接受的那笔交易——它的人设，以及这一切都在记录上。
4. **一只 bot 可以永远把自己叫醒。** 一条提醒走快通道（§4 第 0 段规则 2），所以它不计入房间的连续 bot 轮次上限——那个上限是为了止住两只 bot 在房间里来回换手，而一只 bot 提醒自己不是房间里的对话。一只 bot 可以给自己的下一轮排一条提醒，无限次。这与主动消息没有额度（§10）是同一笔交易，防线也一样。
