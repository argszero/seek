# Internationalisation

> The project is international-facing; English is the primary language. This document covers the **product** — the interface and its data — not the repository's language policy (that is in `CONTRIBUTING.md`).

---

## 1. The rule that decides everything else

**No user-visible string is written into code.** Every label, tooltip, empty state, error and toast is looked up by key at render time. A literal in a component file is a bug, the same way a hard-coded colour is a bug.

The prototype violates this: roughly 7,900 CJK characters of interface text are inline in `src/js/`. It is an archive and will not be retrofitted; the implementation must get this right from the first screen, because retrofitting it later is far more expensive than starting with it.

## 2. Two languages, not one language with translations

| | UI language | Content language |
|---|---|---|
| What it is | The chrome: menus, buttons, labels, system notices, formatting | What people and agents type |
| Who owns it | The application | The participants |
| Changing it | A setting; takes effect immediately | Never rewritten, never auto-translated |

**Content is never machine-translated behind the user's back.** If a user wants a message translated, that is an explicit action on that message, marked as a translation. Silently rewriting what someone said is a trust violation, and in a product where agents speak, it would also make it impossible to tell what an agent actually said.

## 3. Which language does an agent speak?

An agent's language is part of its **persona**, not a global setting:

- `persona` may pin a language ("reply in English"), or follow the language of whoever addressed it (the default).
- An agent that observes a room should mirror the room's dominant language rather than forcing its own.
- If an agent's configured language differs from the user's UI language, that is normal and expected — it is a person, not chrome.
- Group rooms can therefore be mixed-language. Nothing in the model needs to care; the message simply carries the text it carries.

## 4. Locale-sensitive formatting

All of the following go through one formatting layer, keyed by locale, never through string concatenation at the call site:

| Value | Note |
|---|---|
| Time of day | 24-hour vs 12-hour is a locale decision, not a taste decision |
| Relative time ("3 minutes ago") | Needs plural forms; English has two, Chinese has none, Slavic languages have more |
| Dates and day dividers ("Today", "Yesterday", "Wednesday", "3 Oct") | Relative words are translated, absolute dates are formatted per locale |
| File size | Decimal (kB = 1000) vs binary (KiB = 1024) — pick one and say which; do not switch mid-interface |
| Numbers | Thousands separators, decimal comma |
| List joining ("A, B and C") | Not string concatenation — the conjunction differs |

Plural handling is the trap: `"{n} replies"` breaks in almost every language except English. Use ICU-style plural categories from the start.

## 5. Layout must survive translation

English is usually the **shortest** of the languages this will meet: the same label in German or Russian is commonly 30–50% longer, and Chinese is often shorter but taller (CJK glyphs are full-width).

- No fixed-width buttons for text. No `width: 120px` on a label.
- Truncate with an ellipsis rather than wrapping a control's label to two lines.
- Never bake a word into an icon or a background image.
- Test the layout with a deliberately long pseudo-locale before shipping a screen — not with the second real language, which arrives too late.

## 6. Text input and text correction

- **CJK input needs composition awareness**: Enter during IME composition must not send the message. The prototype already guards on `isComposing`; keep that guard.
- **Line breaking** differs: CJK breaks between characters (with rules about what may not start a line), Latin breaks at spaces. Use the platform's `word-break` support rather than `overflow-wrap: break-word` alone.
- **Search** is not `indexOf`: case folding, accent folding and, for CJK, a decision between substring matching and segmentation. Start with substring matching and say so, rather than pretending it is search.
- **Sorting** of contacts and rooms must be locale-aware (pinyin vs stroke vs alphabet) or explicitly defined — not `Array.sort()` on names.

## 7. What stays English regardless

- Identifiers: ids, file keys, protocol names, log lines, code.
- The repository: commits, issues, pull requests, code comments.
- Internal machinery a user never reads (a verdict's label, a reason token — these are rendered *through* the locale for display, but stored as stable values).

The verdict `reason` is a good illustration: stored as a stable token (`not_addressed`, `someone_answering`, `someone_spoke_first`), rendered through the locale — never stored as the translated sentence, or reading old data in a new language breaks. Two things follow. The verdict's **form is not fixed** — a word, a label or a tiny JSON, whatever the chosen model emits reliably — so nothing here may assume JSON keys. And **seek has no budgets**: no spend cap, no daily count, no cooldown, so no reason token may name one.

## 8. Not doing yet

- **RTL layouts** (Arabic, Hebrew). The layout is a fixed four-column arrangement; when RTL is needed, direction has to become a first-class layout property rather than a CSS afterthought. Deferred, but noted here so the left/right assumption is not buried in a hundred places.
- **Automatic content translation**. See §2 — it is an explicit action or it does not happen.
- **Per-message language detection**. Interesting for agent judgement (does this room speak my language?), not needed for v1.
