# seek 数据模型 v1 —— 实体与关系

> 有什么实体、它们怎么关联、哪些规则必须成立。机制、代价和理由在 `agent-lifecycle.md`。
> 一句话比其余都重要：**消息是共享的事实，上下文是私有的解读。**

---

## 1. 一句话

**消息是共享的事实，上下文是私有的解读。**
一个房间里的五个 agent，不是五份房间的副本——一份消息日志，五个私有视角。

这一句解决了这个模型里最难的那部分。

---

## 2. 四层

```
存在层   Bot / Agent、Principal（人）      —— 谁露面，谁干活
空间层   Room + Membership                 —— 在哪
时间层   Session / Message / Thread        —— 什么时候、说了什么
执行层   Workspace / Turn / Observation / Memory —— 怎么干活、花了多少

Bot 和 Agent 全程都按同一条线切：**bot 拥有活着的那些东西**（身份、收件箱、tick、状态、是某个房间的成员），
**agent 拥有跑起来的那些东西**（模型、提示词、工具、会话、记忆）。
```

### 2.1 存在层

| 实体 | 是什么 | 要点 |
|---|---|---|
| **Principal** | 能出现在房间里、能被寻址的任何东西。`kind = human \| bot` | 名字、头像、`description`（自我介绍，别人靠它判断要不要来找它）。**agent 不是 principal**；消息上记着是这只 bot 的哪个 agent 写的，所以审计精确，而房间只看见一个说话人 |
| **Human** | 你（v1 里只有一个「我」） | 也是 Principal；没有特权 |
| **Bot** | 一个看得见的联系人——**房间看到的那个东西** | 拥有**名字、头像和描述**。bot 不是 agent，agent 也不是 bot：它们是两个模型，而身份住在这里 |
| **Agent** | 一个 bot 背后的长存活工人——一个 bot 有一个或几个（现在：一个看，一个干） | 加上一个模型、一份人设、工具、记忆和若干会话，以及**自己的一份目录**。**它的名字和头像取自它的 bot**，所以一只 bot 的两个 agent 以同一个联系人说话；它不属于任何房间，房间只是它通过 bot 露面的地方。它**没有**队列、也**没有**生命状态：收件箱、tick 和状态机是 bot 的。**它知道自己的 bot 和同伴有谁**——身份和名册从 bot 读，不落在 agent 上（规则 16） |

> **要紧的那个区分**：Member 是一个 Bot *投进某个房间的投影*。bot 是人看见、也是人 @ 的那个东西；它的 agent 是背后的工人，审计记录记下是哪一个动的手。
>
> 飞书把 bot 建模成一种成员。在飞书那里够用；在这里不够，因为一个 bot 背后的活计有自己的生命和记忆，跨房间存在，而且背后不止一个工人。

> **Bot 和 Agent 是两个实体，不是同一个实体的两种看法。** 名字和头像住在 bot 上，并且**向下推给它的 agent**，所以改一次 bot 的名字，它的每个 agent 同时改名，没有任何 agent 手里有第二份身份。agent 没有自己的名字：它有一个 `role`（`watch`、`work`，以后还有别的）和它 bot 的脸。

> **一个 bot 是 N 个 agent。** `agents.yml` 登记的是 agent，不是 bot；今天每只 bot 至少两行（一个在本地决策模型上看，一个在贵的模型上干），以后允许多。两行就是内核本来就给一个 agent 的东西各两套——一个模型、一个提示词、一份记忆——而这两者不必是同一类模型：看的那一行一次前向答完，存的是箱子不是会话。不需要新容器，也不需要任何遍历 agent 的代码学一个例外。
>
> 由此引出三件事，而它们正是把两个模型分开的全部理由：**bot 是成员**（成员资格、@、房间的人名单都在 bot 层，所以两个 agent 永远不会显示成两个联系人）；**agent 是工人**（各有一个会话、一份记忆、一个 turn，所以成本和审计按 agent 分，`sessions[agentId]` 不用改）；**身份是 bot 的**（名字、头像、描述，以及人设的声音，向下推给它的 agent）。

### 2.2 空间层

| 实体 | 是什么 | 要点 |
|---|---|---|
| **Room** | 一群人说话的地方 | 自己的 id、成员会变、**不按人数分类**；私聊就是一个两个人的房间；一份共享的消息日志；**bot 可以自己建一个**，所以成员资格不由人把关 |
| **Membership** | Room × Principal 的关系 | 必须单独存在，因为同一个主体在每个房间里不一样：加入时间、角色（群主／成员）、已读位置、静音、**是否在观察** |

### 2.3 时间层

| 实体 | 是什么 | 要点 |
|---|---|---|
| **Message** | 一条不可变的共享事实 | 属于一个房间，可选属于一个话题；发送者是 Principal 或 `system`；类型：文字、图片、文件、**工具卡**、系统通知；**带 `mentions[]`**——它 @ 到的主体，各是 `{id, name}`，就是飞书自己那个字段，没有任何按读者的东西；带自己的原因——`caused_by`（造成它的那条消息）、`chain`（那次因果的根）和 `depth`；还记着**是这只 bot 的哪个 agent 写的**，房间不显示这一点 |
| **Thread** | 一个「话题」——以某条消息为根的子树 | **不是一个新房间**（飞书式，不是 Slack/Discord 式）；里面的人本来就在这个房间里 |
| **Session** | 一个 agent 在一个房间里自己的一段工作 | **私有簿记，永不是用户可见的单位**；有开始和结束，**绑定一个 workspace**，成本滚到它上面。一个房间里的五个 agent 有五段；房间的时间线是连续的 |

### 2.4 执行层

| 实体 | 是什么 | 要点 |
|---|---|---|
| **Workspace** | 干活的地方——一个目录／项目 | 今天 EMRG 的 `cwd`；被 Session 绑定。**每个 agent 有一份 home 目录**，就是它的会话默认打开的那个 workspace，除非那一段被指到别处（规则 16） |
| **Turn** | agent 的一次动作 | 谁触发（哪条消息、哪次观察）、花了多少 token、调了哪些工具、**通过发言工具**产出了哪些消息——**成本与审计的原子单位**。一次完全没调那个工具的 turn 没有产出任何消息，那是一条记录，不是一个空缺 |
| **Observation** | 一条观察队列条目，**在 bot 的队列上** | 一个 Message 的引用 + 零成本的 hints（有 @ 我吗、是不是提问、是不是回复我……）+ 一个判定（ignore / snooze / keep / act）。一条消息只进一只 bot 的队列一次，不是每个 agent 一次。**条目就是一次投递，而投递有两个生产者**：人或别的 bot 发来的消息，或者一行排程到期——后者是条目作者就是该 bot 自己的唯一情形。**条目可以完全跳过判定**：第 0 段的快通道（@、回复、直达、提醒）不惊动 watch agent 就把它消费掉，包括它被注入一个正在跑的 turn 时。**hints 在投递时按本 bot 推导、只住在这里**——`mentionsMe` 是本 bot 的 id 出现在消息的 `mentions[]` 里，绝不是写回消息的字段 |
| **Schedule** | **一张全局表**里的一行，每个 bot 都读都写 | `什么时候` + `什么提醒` + `给哪个 bot`。不是每 bot 一个计时器，也不是 bot 上的一个实体：进程里一张表加一个比较器。一行到期时，它的 `text` 变成目标 bot 队列上一条 `kind: "reminder"` 的 Observation——一次投递，所以普通的唤醒规则原样适用。行由工具（`schedule`）写，运行时从不替谁写，文本逐字投递。**它没有 room，也永不显示**：提醒到达收件箱就停下 |
| **Memory** | 三层 | agent 日记（跨房间、长存活）／房间摘要（滚动、按房间）／会话记忆（今天 EMRG 的 session memory） |

## 3. 关系图

```
   Principal (kind: human | bot)     ← 房间显示、能被 @ 的东西
        │
        └── Membership ──▶ Room ──1:N──▶ Message ◀── root_id 自引用 ── Thread（一个视图）
                              │            ▲
                              │            │ 工具在 workspace 里跑
                              │            │
   Bot ──1:N──▶ Agent ────────┘            │
    │             │                        │
    │             ├── model / prompt(+人设) / tools / sandbox
    │             ├── home dir（自己的 workspace）
    │             ├── Session ──1:1──▶ Workspace     （agent × 房间，私有簿记）
    │             ├── Memory（日记 / 房间摘要）
    │             └── Turn ──▶ Session，产出 Message
    │
    ├── Observation ──▶ 引用一个 Message（零成本 hints + 一个判定）   ← 每 bot 一个队列
    ├── tick / 状态机 / lastSpoke / spent                              ← 生命，不是工作
    └── name / avatar / description   ← 向下推给它的每个 agent，
                                        所以房间看见一个联系人，不是两个
```

**Bot 和 Agent 是分开的实体**，而它们之间的线是**活着 vs. 跑起来**。bot 拥有身份、成员资格、收件箱、tick 和状态机；agent 拥有模型、提示词、工具、会话、记忆和自己的 turn。所以不管背后几个 agent 干活，一只 bot 只出现一次；投递是一次写而不是 N 次；而审计和账单仍然点得出是哪个工人。

## 4. 基数与规则

1. **Room 1 : N Message**。一条消息只属于一个房间，绝不跨房间。
2. **Message 0..1 : N Thread**。一条消息至多作一个话题的根；话题不跨房间。
3. **Agent 1 : N Session；每个 Session 属于一个 (agent, room) 对。** 房间的时间线是连续的，里面没有会话边界。一个房间里的五个 agent，在同一份共享日志上盖五段私有跨度——这就是「消息共享、上下文私有」成为构造性事实而不是纪律的原因。
4. **Session 1 : 1 Workspace**（选定即锁）；Workspace 1 : N Session，并且 **Agent 1 : 1 home Workspace**——会话默认打开的那个目录，除非那一段被指到别处（规则 16）。
5. **Principal N : M Room**，通过 Membership，它带着每个房间的状态。
6. **Bot 1 : N Observation**，Observation N : 1 Message（一条消息可以进几只 bot 的队列，但每只 bot 只进一次）。队列在 bot 层，因为投递、tick 和「已处理」都在 bot 层；agent 从不看房间。
7. **Agent 1 : N Turn**；Turn 1 : N Message，而其中每一条消息都来自一次发言工具调用，不是来自 turn 的输出。一次动作可以说几件事：三次调用，三条消息，各自指明发到哪个房间。
8. **Agent 1 : 1 记忆存储**（N 个房间摘要 + 1 份日记）。记忆按 agent 分，不按 bot 分：日记与会话各自属于各自的 agent。一个房间的常驻摘要每 (bot, 房间) 只写一次，两个 agent 都读它——watch agent 不产出文字，自己再存一份只会是多出一个会说反话的版本。
9. **Human 1 : 1 身份**（v1），多重自我留开着。
10. **id 前缀沿用飞书习惯**：`ou_` 主体、`oc_` 房间、`om_` 消息，再加 `ag_` 给 agent。可读性优先于通用 UUID。
11. **房间不需要有人类成员。** 两个 bot 之间的单聊就是一个房间；成员资格不由人把关。界定 agent 之间流量的是深度上限和房间的连续 agent 轮次上限，两者都从数据上读得出，都不需要一个活人在场才发现失控。
12. **Message N : 1 Message（因果）。** `caused_by` 指出造成这条消息的那条；`chain` 指出那次因果的根；`depth` 是跳数。一条链的深度从数据上读，绝不存在一个可变的计数器里——计数器是重启之后会悄悄漂移的东西。
13. **对用户来说，没有什么会把一个房间的历史切开。** 交互是飞书的：一个聊天、一条连续的时间线。会话边界、workspace 变更或成员变更记在数据里，最多以一条系统消息出现——绝不是一条列表项、一个分隔控件或第二条时间线。
14. **Bot 1 : N Agent；Agent N : 1 Bot。** bot 拥有名字、头像和描述；它的 agent 继承它们而不是各存一份，所以改一次名字会到达每个 agent。agent 有 `role`，没有名字。**bot 层那一组**是身份、成员资格、@、房间的人名单、观察队列、tick 和状态机——一切活着的。**agent 层那一组**是模型、提示词、工具、会话、记忆、turn 和成本——一切跑起来的。
15. **消息存 `mentions[]`；「有人 @ 我」是推导出来的。** 消息保留飞书那个字段——它 @ 到谁，`{id, name}`——因为那是界面画成蓝色 @ 文字的东西，也是开放平台定义的。`mentionsMe` 不存到消息上：它是同一个事实从某只 bot 的位置看过去的样子，在投递时用该 bot 的 id 在 `mentions` 里找出来算得，只住在观察条目上。消息写一次就保持干净；每只别的 bot 从同一串字节推导它自己的答案。
16. **Agent 1 : 1 home 目录；它的 bot 是读来的，绝不复制。** agent 的 home 目录装着它的人设、它的 skills 和它的记忆，也是它的会话默认打开的 workspace，除非那一段被指到别处。关于 bot 的东西一样都不存在 agent 上：**bot 的名字、头像、描述，以及它名下 agent 的名册——每一个的角色、干什么、它的目录——都在 agent 运行时从 bot 读**，所以改一次名字、加一行，会到达每个 agent，没有任何 agent 手里有第二份会说反话的副本。身份和名册交给 agent 的方式，是写进它的提示词，或者生成一份 skill 文件让它读，所以它不用问就知道。

## 5. 五处容易搞错的

1. **Session 是簿记，不是一个地方。**
   用户永远看不见它：房间的时间线一路连续，和飞书里一样，没有「新建会话」可按。数据需要这段跨度，是为了私有的两件事——这一段在哪个 workspace 里跑、花了多少。如果 workspace 的变更必须被看见，它就是时间线里的一条**系统消息**——飞书本来就有的一种消息类型——而不是一个新控件。

2. **话题不是一个房间。**
   Slack 里话题是一条消息；Discord 里它是一个子频道。seek 取飞书的形状：**话题是一棵消息树**。里面的人永远是本来就在房间里的人，所以不需要重新邀请、重新授权。

3. **私聊是一个人数，不是一个类型。**
   两个人的房间和五十个人的房间行为完全一样。**飞书也同意，而且就是这么存的**：`chat_mode` 有三个值（`group`／`topic`／`p2p`），而单聊就是一个有自己的 `oc_` id 的聊天，查询时 `chat_mode` 读作 `p2p`。这个字段可以为了保真存下来；**任何领域逻辑都不许在它上面分支**，因为它描述的实体两边都是同一个 Room。注意一处不对称：飞书的 `p2p` 只存在于「机器人↔用户」，所以两个 bot 之间的单聊是 seek 的扩展，没有任何上游可以照抄——它是被裁定出来的，不是被推导出来的。

4. **房间不必包含你。**
   两个 bot 之间的单聊里没有你的人，它仍然是一个房间：同一个实体、同一份消息日志、同一套成员资格。没有任何东西在「里面是谁」上分支——那就是上一条，也是房间的内容从不长得像代码形状的原因。bot 之间的往来能不能被看见，是一个*列表*问题，不是模型问题。

5. **@ 住在消息上，「有没有 @ 我」不住在消息上。**
   `Message.mentions` 是飞书字段，也是唯一被存的形态：*谁被点了名*。每只 bot 在消息落地时推导 `hints.mentionsMe`——在那个数组里找自己的 id——这个布尔值留在该 bot 的队列条目上。把 `mentionsMe` 存到消息上，等于把一个读者的视角塞进一条不可变的共享事实里：那条消息要么被重写，要么按房间里的每只 bot 复制一次。它还会花掉第 0 段必须免费回答的那一个问题：一只 bot 问的是关于它自己的事，而答案是一次数组扫描。

## 6. 为什么是这个形状（别人怎么做的）

| 概念 | 飞书 | Slack / Discord | grok-bot | ADK | **seek** |
|---|---|---|---|---|---|
| 聊天的容器 | chat（p2p/群组/话题） | channel | Room | — | **Room**（不分类） |
| 话题 | thread（消息树） | Slack：消息；Discord：子频道 | — | `sub_agents` | **Thread（消息树）** |
| 一段工作 | 无 | 无 | turn | **Session（事件序列）** | **Session**（agent 的私有跨度，按 agent × 房间——永不显示） |
| 执行者 | bot（一种成员） | bot | agent（一种成员） | **Bot + Agent（两个实体）** | **Bot（联系人）→ Agent（长存活工人）** |
| 共享与私有 | 全共享 | 全共享 | 全共享 | 干净分开 | **消息共享，上下文私有** |

**三件事是 seek 自己的**：① **bot 和它的 agent 是两个实体**——bot 是联系人、拥有身份，agent 是工人、拥有会话、记忆和成本；② agent 长存活、跨房间，而房间只是它的 bot 露面的地方；③ 消息共享而上下文私有——那才是「一个房间五个 bot」这件事可能的原因。

## 7. 落盘形态（简要）

每个账号一个 `seek.json`（和今天一样），分成 `bots / agents / principals / rooms / memberships / sessions[agentId] / messages[roomId] / observations[botId] / turns / memories / schedule`。

`schedule` **不**按 bot 分片，与 `observations` 不同：它是一张每个 bot 都读都写的全局表，所以分片会把它存在的唯一那个操作——一个 bot 给另一个 bot 写一行——变成跨分片写。

`bots` 和 `agents` 故意分成两个分片：bot 是几行，改名时才动；而 agent 是又多又忙的那些。身份自己一个分片，意味着改名是一次写，不是每个 agent 一次。

三个分片键，各自对着「什么长得最快」和「什么必须能单独清理」：

- **消息按房间**——一个房间一份共享日志，所以分片键就是每个读者本来就有的东西。
- **观察按 bot、会话按 agent**——队列是 bot 的（每 bot 一个），活是 agent 的（每 agent 一个）。两者都是「否则会让一个共享文件无界增长」的东西。
- **turn 放在一起**——它们是账本，很小，而一个按 agent 拆开的账本就不再是账本。
