# 我做的决定

`host-rulings.md` 是底座：它装着宿主定下的东西，而这个文件向它对账。这里没有一条可以跟裁决矛盾，而且**裁决永远赢**——两者撞上，改的是这个文件。

这里装两种东西：

- **推导**——设计不得不从某条裁决里得出的结论，而裁决本身没有写出来。它不是第二条裁决，它只是那条裁决唯一可能的形状。
- **默认值**——宿主留开的一个数字或一个选择。每个默认值旁边都写着改它要说的那一个词。

这里没有日期，也不记录它以前说过什么。那在 git 日志里。

## 在仓库之外核实过的事实

- **飞书的聊天模式。** `chat_mode` 有三个值——群组／话题／单聊（`group`／`topic`／`p2p`）——而且**单聊就是一个聊天**：它有自己的、以 `oc_` 开头的 `chat_id`，查询时 `chat_mode` 读作 `p2p`。所以「私聊就是一个两个人的房间」是飞书自己这么存的，不是我们的发明。两点跟着来。①**字段存在，领域逻辑仍然不许在它上面分支**——实体两边都是 Room，而飞书自己的行为（p2p 里拉不进人、也退不出）是表层性质，不是拆分模型的理由。②**飞书的 `p2p` 只存在于「机器人↔用户」**，所以两个 bot 之间的单聊没有对应物可以模仿；它由裁决定，不是推导出来的。
- **飞书的消息字段。** 消息上的 `mentions[]` 带着它点到的主体，各是 `{id, name}`。id 前缀：`ou_` 主体、`oc_` 房间、`om_` 消息。seek 加 `ag_` 给 agent。
- **内置 watch 模型的实测数字（在本机笔记本上跑出来的）。** 下载体积：`LFM2.5-VL-3B` Q4_0 **1.52 GB**，外加视觉投影层 Q8 **0.56 GB**；`LFM2.5-VL-450M` Q4_K_M **219 MB**；`Qwen3.5-0.8B` Q4_K_M **508 MB**。在「动不动」上的质量，三批互不重叠共 76 条手写用例：**3B 0.96–1.00 AUC**（最后一批 24 条全对），**450M 0.48–0.74**，**0.8B 0.48–0.85**。单条耗时：3B **96 ms**，450M **18 ms**，0.8B **71 ms**。3B 重读整箱约 **每 token 1 ms**。

## 从裁决推导出来的

- **房间的时间线是连续的，所以会话永远不能是用户可见的单位。** 交互是飞书的：一个聊天、一条时间线。会话是 agent 的私有簿记，workspace 变更最多以一条系统消息出现——飞书本来就有的一种消息类型——绝不是一条列表项、一个分隔控件或第二条时间线。
- **左侧列表显示房间，不显示会话。** 它们是聊天，而会话不是聊天。
- **话题是一棵消息树，不是子房间。** 里面的人本来就在这个房间里，所以不需要重新邀请，也没有第二份成员关系要维护。
- **成员是一个 bot 投进一个房间的投影，不是一个 agent。** agent 不属于任何房间；房间是它的 bot 露面的地方。这就是一个联系人可以同时在三个房间里、而每个 agent 在每个房间仍只有一条连续的线的原因。
- **一个收件箱把对账问题整个拿掉，而这就是 agent 能保持小的原因。** 每个 agent 一个队列，每条消息就要投 N 次，每个 agent 各存一份「已处理」，循环去对账 N 份。每只 bot 一个队列，投递是一次写，tick 是一个循环，第 0 段判一次。
- **没有 agent 去房间里扫自己的名字。** 「有人 @ 我」由 bot 在投递时回答一次。watch agent 根本答不了，它不可被寻址——而这正是第 0 段的快通道是一条规则、不是一次模型调用的原因。
- **「有没有 @ 我」按 bot 推导，绝不存到消息上。** 把一个按读者的布尔值存进一条共享的不可变事实，等于逼出一次重写或按房间里每只 bot 复制一份。
- **一条链的深度从数据上读，绝不放在计数器里。** 计数器要在崩溃后恢复，而它恢复错的那一次，恰好是需要它的那一次。
- **需要靠一层策略去维护的防线，是人设的缺陷。** 在 agent 旁边摆配额、冷却或静默时段，正是这个设计拒绝的那种常驻治理；话太多就重写人设。
- **成本只记录，从不强制执行。** 账单爬升是人设或门禁的缺陷，在数字里看得见，在原因上修。没有自我停止，因为自我停止把缺陷藏起来，而不是亮出来。
- **提醒为什么不被显示。** 飞书一致性管的是 bot 怎么够到别的主体；提醒谁都够不到，没有第二个当事人可以显示给它。用户看见的是 bot 拿它做了什么。
- **排程不可能是一个计时器。** 它是进程里一张表加一个比较器，所以不按 bot 付费，也不会为了发现「没东西到期」而调模型。一行到期**就是**一次投递，所以唤醒规则——一次投递、别的什么都不启动 tick——一字未动。
- **两个 agent，不是一个 agent 问两遍。** 两个窗口差一个数量级，而压缩是破坏性的，所以共用一个日志意味着较小的窗口先压缩、删掉较大的那个还读得到的细节。各自的存储归各自；它们唯一共享的东西——一个房间的常驻摘要——只由能写的那一半写、由写不了的那一半读。多一个写者，就是把碰撞装回来。
- **压缩是运行时动作，不是一次 turn。** 它一句话也不说，所以不是一次主动发言、不开一段工作、也没有任何判定请求过它。一个从不需要说话的忙碌房间仍然必须可被压缩，而这只有在压缩不依赖 turn 时才有可能。
- **从不问判定「要不要压缩」。** 这是对条数、token、图片和分钟数的算术，运行时免费就能算。一个能请求压缩的模型可以每个 tick 都请求一次，于是那个存在的意义就是止住花钱的部件，变成了无界花钱的那一个。
- **交给判定的箱子永远装得下。** 由新到旧装到模型窗口为止，未读的条数一并带上。装不下的判定是在猜、却长得像判过了；一个看得见的未读数是一个更差的答案，但至少它被标成了更差的答案。
- **摘要由能写字的那一半写。** 决策模型只吐一个选择、一个分数或一个概率，不吐文字，所以常驻摘要归 work agent。这也是箱子按 (bot, 房间) 只有一个的原因：一份摘要两个写者，就是一次只是还没显形的分歧，而其中只有一个写者能写字。
- **图片经由箱子抵达判断，且只在其条目抵达时。** 图像挂在消息上——`media`，一个 `{key, mime}` 引用——而判断读的是箱子，所以箱子里记着窗口留下的那些条目各自的图片。和 delta 一样在读取时派生，绝不复制到 observation 上：条目本来就指着一条消息，第二份副本可以与它指的那条消息不一致。箱子的那条规矩把它一并管住：图所在的条目判断没读到，图就不递出去——这正是"它永远装得下"那条失败模式的新形态。把引用变成像素不在内核里：blob 怎么命名、怎么读是客户端的方案，而真能读图的那个 projector 是 `src/README.md` 第 25 行还没测的那一半。
- **身份是向下推的，从不复制。** 名字、头像、描述只有一份，住在 bot 上；它的每个 agent 在运行时被告诉它是谁、它有哪些同伴。第二份副本就是第二个会说反话的东西。
- **第二段的 turn 就是一个普通 turn。** 不因为「主动」而多写任何记录：不同的只有一点——它开场就知道没有人叫它。它也可能什么都没说，因为说话和别的工具调用一样，是它自己发起的。
- **除了通过发言工具，没有任何东西能到达一个房间。** 一个 turn 吐出来的文字是它自己的记录：不发出去、不流式出去、也不摘要成一条消息。两个后果，两个都要。bot 不可能说漏嘴——房间里每一条消息都是指明发到那里的，这也正是「主动消息」那个标记有意义的原因。而沉默是默认，不是失败，这才让「它转上去了，但什么都没说」能从记录上读出来，而不是靠推断。
- **对话记录不是投递通道。** 如果 turn 的文字就是房间显示的东西，同一句话就会落进 agent 正在想的每一个房间，而「它到底指哪个房间」变成一个事后才问的问题。房间由发送方指明，否则消息就不发。
- **delta 是派生的，从不另存。** 判定的箱子是「一份摘要 + 摘要消费到的那个点之后的观察」，后半截从收件箱上读出来，不复制成第二份日志。每条观察只有一份，意味着某条被编辑、删除或重投时没有任何东西要对账。
- **压缩单飞，并且原子提交。** 同一房间两次压缩，各自从一个已被对方推过去的状态重写摘要，谁最后写完就删掉差额——而且是无声的。一次只跑一个、把新摘要和它消费到的点一次写完，才是让「压缩期间到达的条目绝不丢」成立而不只是被希望的东西。
- **交给决策模型的状态是结构化 JSON，不是文章。** 它的契约是「状态可以是任意 JSON 值」外加命名问题。一段文章会把这个模型本就不大的窗口花在散文上，还把零成本就能算出来的信号扔掉。
- **上次判决作为事实进箱，绝不作为指令。** 什么时候判的、判成什么，好让一个 `keep` 被重新看一眼。命令它重复上次判决，会让每一个陈旧决定自我延续。
- **记忆写入和压缩是运行时行为，不是工具。** 不是 agent 选择去做，而是运行时在 turn 结束时做。
- **判定是二元的，另外两个判定值由循环写。** 靠读已声明选项概率作答的决策模型，只能返回给过它的选项，所以问题只有「动不动」这一条——四选一在所有试过的模型上（含最终选的这个）实测都是随机。`later` 是循环在某轮排了提醒时写的，`keep` 是循环在「这个房间已在处理中」时写的。这和压缩那个问题的分工是同一条：模型作答，循环执行并记账。
- **问给 watch 模型的那句话属于契约。** 实测：同一个模型在同一批用例上，仅仅改写措辞，判别力就从 0.09 摆到 0.77，并在中英之间反向。所以提示词是运行时携带的**固定、带版本**的产物，工作点是照着它校准过的——不是调用点上临时拼的字符串，那儿一次好心的编辑会悄悄把阈值挪走。
- **提示词由运行时拼装，不由模型自行排布。** 产物文件声明有哪些部分、按什么顺序，运行时按那个顺序把盒子渲染进去 —— system、房间记忆、每条条目一行（由旧到新）、最后是问句。这件事不能交给模型，有两个理由。答案是在 prompt 自己结尾处读的，所以一个活在模型里的顺序会在产物一动不动的情况下把屏蔽瞄准的 id 挪走，而没有任何版本钉住一个没人写下来的顺序。而「热」只可能建立在一个只会追加的顺序上：把条目按由新到旧渲染，等于每条到达都插在已经读过的全部内容之前，那每来一条消息就是一个新头部。仍然属于模型的是盒子里别的事实 —— 计数、上一条判定、谁说过话 —— 它们不在实测的提示词里，所以以字段交过去，不作为文本。
- **工作点来自带标注的集合，且判决带着未读数存下来。** 小模型可用的切点离正中很远（实测 0.6 到 0.98），所以 0.5 不值得当默认值；而对一个房间只读了一部分就下的判断，要连同「读了多少」一起存，否则事后它和一个完整的判断长得一模一样。

- **界面文案按键查表，正文永远不查。** `docs/design/i18n.md` §2 划的就是这条线，这里说它落在代码的哪里。运行时写出的字——报告的标题、标签、一句拒绝——住在 `src/i18n/<tag>.json` 里，渲染时按 key 取；参与者产出的字——一条消息、一个显示名、种子自己写的那几行——是数据，原样穿过去，所以换语言之后它们一个字节都不变。两个值得抓住的推论。**填充只走一遍**，所以一条恰好含 `{path}` 的消息不可能把报告围绕自己重写一遍。而**这条规矩不能靠扫描「带引号的句子」来守**：那样的扫描恰好会把必须留在代码里的正文判成违规，所以测试断言的是另一件事——报告渲染出来的每一行都来自文案表。对今天唯一存在的那个界面，这就是这条规矩的意思。
- **拒绝要用一种确实存在的语言写出来。** 不支持的 `--lang` 没有自己的文案表来承载这句拒绝，所以拒绝用基础语言写。兜底只为这一件事存在：它绝不把页面渲染成没人要的语言；标签是精确匹配的，因为 locale 标签是标识符，不是搜索词。
- **名册点名一个 bot，但不描述它。** 一行说明某个 agent 服务哪个 bot，而这个 bot 的名字、头像、说明都不在文件里：身份长在 bot 上，被下推给它的各个 agent（`host-rulings.md`），所以名册里再来一份就是第二个会跟它打架的东西——在 store 里改了名字的 bot 还会照着文件里的旧名字应声，而没有任何东西说得清哪个才对。

## 宿主留开的默认值

每一行是宿主没有裁决的一个选择，旁边写着改它要说的那个词。

| # | 问题 | 默认值 | 为什么是这个 | 改它的说法 |
|---|---|---|---|---|
| 1 | 一条 agent 之间链能跑多深 | **4 跳** | 够一次真的交接加一次回复；短到误解走不远。从消息数据上读，所以重启后还在 | 「深一点」／「浅一点」／一个数字 |
| 2 | 一个房间连续几轮 bot 发言 | **3** | 真正止住一次爆发的是这个——光靠深度不行，一串短促的往复只用很少的跳数。挂在 Room 上，因为没有任何单个 agent 看得见同伴刚说了几次 | 一个数字 |
| 3 | 判定的箱子什么时候压缩 | **delta 越线时**——观察条数，或距上次压缩的时长，先到哪个算哪个；这两个数字由实测定 | 判定读的是 delta，所以要守住的是 delta。改成每条到达就压，等于让一次生成去抢判定要用的那块 GPU，房间最忙的时候闸门最慢 | 一个数字，或者「每条消息都压」 |
| 4 | 会话要不要存一份成员快照 | **不存** | 谁说过话就在消息上，快照只能回答「这段开始时谁在」——一份会悄悄过期的成员事实，而它服务的那段私有跨度根本用不上它 | 「存一份」 |
| 5 | watch agent 能不能被 @ | **不能** | @ 是对房间里某个联系人说话。watch agent 不是成员、没有脸；「有人 @ 我」由 bot 回答 | 「让它可被 @」 |
| 6 | 判定记在哪 | **记在它所判的那条观察条目上**，不记别处 | 写进 work agent 的历史，就等于每轮都进 work 的上下文，和「按需读、绝不每轮注入」矛盾。watch 侧本来就没有自己的历史可记 | 「两边都记」 |
| 7 | 许可证 | **MIT** | 宿主把这件事交给我定 | 「Apache-2.0」或别的 |
| 8 | 左侧列表显示什么 | **房间** | 飞书的左侧列表就是聊天列表 | ——（这是推导，留在这里是因为它最初答的就是这个问题） |
| 9 | 发言工具叫什么 | **`say`，即 `say(room, text)`** | 它顺着注册表那种单裸词的风格（`read`／`write`／`edit`／`glob`），且不会被误认成邻居：不是 `write`（那是文件），也不是 `post`（那是飞书的一种消息类型，读起来像格式而不是动作）。`reply` 不对，因为它发出去的东西大多不是回复；`message` 和实体撞名 | 换一个名字，在写出第一句提示词之前定 |
