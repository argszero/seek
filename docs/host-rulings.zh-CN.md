# 宿主的裁决

**这个文件是什么**：宿主自己做出的每一个决策，每一条都按它现在成立的样子陈述。设计文档里混着三种陈述——宿主裁定的、我从裁定里推导的、我自己发明的——第三种已经不止一次被当成第一种用。这里只出现第一种，其它文档要向它对账。

**这个文件不是什么**：不是设计。机制、代价和理由在别处推演。推导和我自己的取舍不是裁决，不写在这里。

**这个文件是底座。** 它不对任何文档负责：别的文档要向它对账，它一份都不引。

## 三条规矩

1. **只有宿主自己的话能成为一条。** 追不到他发的某条消息上的陈述，是推导或提案，标出来，而不是写进这里。
2. **同一个问题他再次裁决时，老的删掉、新的写进来。** 这个文件只放现在成立的。它以前说过什么，在 git 日志里。
3. **不写日期，不写时刻。** 条目按它回答的问题归位，不按它被回答的时间；带它的那次提交就是日期。

引号里是宿主原话，会话记录是原件。没有引号的条目，是把他的裁决陈述出来，原话见会话记录。我对他提问的回答从不引用，只引他的。**他只答一个字的，旁边用方括号补上我问的那句话，并标明是我问的**——一句「A」在日期被拿掉之后什么也不指。

## 产品

**seek 是多 Agent 产品。**
决策：IM 外壳只是外壳。一个联系人是 bot，agent 是它背后的东西。

**名字，以及名字带来的形状。**
决策：名字、标语，以及对产品手感的一条约束——它是 IM，不是任务面板，也不是工作流编辑器。

**设计先于代码，旧实现是原型。**
决策：更早的 Electron 实现归档为 `prototype/`；文档收口之后才写内核；仓库公开。

**英文是项目语言。**
决策：英文是仓库一切对外内容（issue、PR、提交、代码注释）的语言，产品文案永不硬编码在组件里。

**飞书一致性管的是"交互"。**
决策：一个设计问题有两个答案时，飞书里看得见的赢。边界：一致性管的是 bot 怎么够到**别人**，不管 bot 怎么处理写给自己的一条便条。

**你自己做。**
原话：「为什么要我去做，你不能做吗？」
决策：我能做的工作——出图、上传、工具——不递回给宿主。

## Agent

**bot 之所以是 bot。**
决策：三条性质——长存活、自己观察、自己行动；一个 per-bot 收件箱；两段式主循环，贵的后面先有一道便宜的门禁；以及逼出这套结构的成本理由，因为活着的 agent 在没事的时候不许烧钱。

**bot 可以来找你。**
原话：「可以。」［我问的是：agent 能不能主动给你开一个直达消息。］
决策：bot 可以主动开一个直达消息。设计里没有任何配额、冷却或静默时段。

**bot 只有两个约束：提示词和沙箱。**
决策：一个 seek agent 就是 EMRG agent，它全部的约束是提示词和沙箱。没有配额、没有冷却、没有静默时段、没有说明理由的行、没有逐动作限制。话太多的 bot 是人设缺陷，在人设里修。

**agent 动手前不问。**
原话：「不要。」［我问的是：agent 动手前要不要停下来问一声。］
决策：处处没有审批步骤。撑住的是三样：沙箱、完整审计、停得下来。「我可以吗」没了；「你要哪个」留着——在两个选项之间选，是对话，不是许可。

**不设花钱上限。**
原话：「A。」［我问的是：bot 要不要带一个花到这个数就停的预算。A＝不要，记录花费并显示出来。］
决策：花钱上没有上限——没有预算字段、没有「因为花光了所以安静」这个状态、没有它会停下来的限额。花费是**记录**下来的（一个 turn 带着自己的 token）并且可见。花太多的 bot 是人设或门禁的缺陷，就在那里修。设计里另有的几个界都不是花钱的界：一条链能跑多长、一个房间连续几轮 bot 发言、收件箱能长多大。

## 门禁

**门禁存在，且必须近乎免费。**
决策：门禁是架构，两条要求：它拦掉无意义的动作，它自己几乎不花钱。它不是对 agent 行为的约束——它只问一个问题，这个 agent 到底要不要跑，而它是"一直活着的 agent 才养得起"的原因。

**内置、够小、规则先行。**
原话：「一定要内置——找一个足够小的模型内置在本地（模型文件 300 MB 以内，越小越好）。再配一些规则：如果没有新的观察，立刻返回；如果 @ 了我，直接返回『去做』。只有剩下的才给那个小模型。」

决策：watch 模型随产品一起装上，两条免费规则跑在它前面。**300 MB 这个数字是在跑过任何候选之前定下的目标，现已撤回**：那个尺寸的模型没有可用的判断力，所以数字让路给它本来要代替的那条要求。

**暂时用哪个模型。**
原话：「好吧，那暂时先使用 3B 的吧，等以后有新的更小的模型时再换。」
决策：内置的 watch 模型目前就是 3B 这一档。**更小的模型是通过同一套实测之后才换上，而不是一出现就换**——撤回体积目标的原因正是「目标达到了、但模型不会判断」，仅凭体积就换上下一个小的，等于重犯一次。

**多语言，多模态。**
原话：「因为要国际化，所以这个模型必须支持中文 + 英文 + 多模态。」
决策：两条都是要求。体积目标撤回之后，它们不再和任何东西互相拉扯，而且**两条都不靠辩论定**：多语言已经测过，只有在两种语言上都过线的模型才算合格；多模态还没测，在那之前这条要求算「尚未兑现」，不算被丢掉。

**先写要求，以后再选。**
原话：「先把要求写下来，以后再选。现在不用去找。」

**判定不需要固定形式。**
原话：「不要限制成 JSON——只要满足我刚才说的要求就行。」
决策：一个词、一个标签、一小段 JSON——所选模型稳定吐什么就用什么。解析不出来，算作不动。

**判官不另做输入管线。**
原话：「不需要专门设计，因为 Agent 本身就有 session history、memory、compaction。判官的请求和 Agent 真跑的时候发出的那个请求基本一致——它拿到 agent 的 session history、memory、compaction。」
决策：判定时不为它现装任何东西——它对一个房间的记忆就是那个观察箱，照现状读。**它唯一不做的事是写**：判官是决策模型，按命名问题作答、不产出文字，所以箱子里的摘要是 work agent 写的，watch 侧不留自己的会话。

**判定读的是一个两段箱。**
原话：「观察箱里分为两部分，一部分是上次压缩的结果，一部分是上次压缩后新的观察。每次判断时，将上次压缩结果和压缩后产生的新消息以及上次判断时间和结果，发送给 system one，完成快速判断。」
决策：按 (bot, 房间)，判定的输入就是这个箱子和别无他物——常驻摘要、摘要之后的 delta、上次判决。上次判决作为事实进箱（多久以前的、判成什么），绝不作为指令。

**压缩由一条线触发，不是每条消息。**
问的是压缩该在 delta 越线时跑、还是每条新消息都跑，宿主答「A」——越线。
决策：delta 越线就起一次压缩，而判定从不等待压缩。压缩单飞：同时只跑一个，把新摘要和它消费到的点一次原子写入，所以并发到达的条目要么已在新摘要里、要么还在 delta 里，绝不丢。**压缩是运行时动作，不是一次 turn**——一个从不需要说话的房间仍然必须可被压缩——而且**从不问判定要不要压缩**：那是对 delta 的算术，一个能请求花钱的模型可以每个 tick 都请求一次。线本身是默认值，由实测定，不是裁决。

## 一个 bot 背后的两个 agent

**判官也是 agent。**
原话：「就算判官也是一个 Agent，只是用本地模型。」

**每个 bot 两个 agent。**
原话：「其实每个 bot 有两个 Agent：一个做快速判断，一个真正干活。」
决策：切分切在两个 agent 之间，不是一个 agent 的两种模式。

**两个角色名：`watch` 和 `work`。**
原话：「那就 B 吧。」［我问的是：两个角色叫什么。B＝`watch`／`work`。］
决策：名字取自设计里本来就有的词——watch 队列、干活。

**存储各自独立，彼此可读。**
原话：「不要共用一个记忆。各自独立，各自知道对方存在，能读对方的历史、记忆等等。」
决策：各自的存储归各自——work 的会话与日记，watch 每个房间的箱子。**它们只共享一样东西，而那样东西只有一个写者**：一个房间的常驻摘要，由 work agent 写（因为它是能写字的那一半），由 watch agent 读（§3）。**这条读通道覆盖两边写下的任何东西，包括一条判定和它背后的理由**——work 想知道自己为什么被叫醒，靠的就是它，而不是靠有人把理由递过去。

**工具集是 EMRG 那套，不新增，它归 work agent。**
原话：「它有工具——否则它怎么读写记忆、怎么压缩自己的会话？」［我问的是：watch agent 到底给不给工具。不给：决策模型一次前向答完、不产出文字，它没有工具调用可发。那句话要的三件事在别处兑现——记忆是箱子，压缩是 work agent 的。］／「就用 EMRG 那套吧。」
决策：work agent 的工具就是内核的注册表（bash / read / write / edit / glob / grep / subagent / submit_rant / boss），某个 agent 能用哪些是 `agents.yml` 里的普通配置。没有 watch 专用工具、没有记忆工具、没有压缩工具：在 EMRG 里记忆写入和压缩**不是工具**——不做成工具——所以这里也一样是运行时行为。**例外有两个，都是宿主点名的：`schedule`（§12），以及那个在房间里发言的工具**——第二个不是给 agent 多一件能做的事，而是唯一能让任何东西到达房间的路。两个就是「再也不是巧合」的条数：第三个意味着注册表正在被一个一个例外地重建。

**watch agent 从记录里读自己的结果，且不指望它变聪明。**
决策：不建反馈通道，不做任何训练。结果读自记录，并由箱子的「上次判决」那一格带下去；下游任何东西都不许假设它会变好。

**交出去的只有观察条目，理由留在写下它的地方。**
原话：「A。」［我问的是：watch 判它要动的时候，work 收到什么。A＝只有收件箱条目。］
决策：work agent 醒来时只有条目，没有别的——运行时绝不把 watch 的理由放进它的上下文，因为进了上下文的理由不是建议而是前提：watch 错的地方，work 不会纠正，会放大，而放大看起来像连贯。**但它不是被封死的**：理由在记录上，而两个 agent 本来就能读对方的记录，所以 work 可以去读——读到了就知道决定了什么、那句话是谁说的。被禁止的是「悄悄递过去」，不是「去查」。

## bot 与 agent 是两个对象

**两个数据模型，身份落在 bot 上。**
原话：「bot 是 bot，Agent 是 Agent——两个数据模型。名字和头像落在 bot 上，bot 把名字传给它下面的两个 Agent。」
决策：agent 只有 `role`，没有自己的名字；改一次 bot 的名字，它的每个 agent 同时改，房间永远不会在一个人身上看见两个联系人。

**agent 知道自己是哪个 bot 的，以及关于这个 bot 的一切。**
原话：「work agent 在自己的系统提示词或者 skill 里，能知道自己属于哪个机器人，以及这个机器人的一切信息（名字、有哪些 agent，分别是干什么的，每个 agent 的目录等等）」
决策：bot 的身份和名册交给它的每一个 agent——写进系统提示词，或者生成一份它读得到的 skill 文件：bot 的名字、头像、描述，以及这只 bot 每一个 agent（包括它自己）的角色、干什么、自己的目录。这些不落在 agent 身上，所以改一次名字、加一行，所有 agent 同时知道。

**`agents.yml` 是 agent 名册。**
原话：「每个 bot 有两行没关系——`agents.yml` 里装的是 agent，不是 bot。以后可能某个 bot 需要更多行。」
决策：行数不设上限；文件登记的是 agent，bot 是那个分组。

**收件箱落在 bot 上。**
原话：「照现在看，收件箱可以放在 bot 上，这样 agent 的设计就简单——接近 EMRG 或 Google ADK 的样子。」
决策：一个队列、一个「已处理」状态、一个 tick，全在 bot 层；agent 保持是个可运行体。

## 消息与投递

**说话是一次工具调用。**
原话：「work agent 只有调用发言工具（发给谁（群、单聊）、发送的内容）才会发消息，不能 work agent 吐消息就发到 im。」
决策：一个 turn 结束时没有调那个工具，就是什么都没说，它产出的文字留在 turn 自己的记录里。没有任何东西替 agent 发到房间：不是它的最终答案，不是流式的一小段，也不是「它做了什么」的摘要。

**一条路，一个循环。**
原话：「直接不是跳过判断，是判断看到 @ 就放过去。其实只有一条路。」
决策：一条投递路径、一个循环。@ 我、回复我、私聊是**第 0 段内部的快通道**，不是第二条路；「同一条消息回两遍」的问题不存在。

**只有投递才唤醒 bot。**
决策：没有计时器、没有时钟 tick、没有 `kind: "clock"` 条目。往收件箱的一次投递是唯一能起一个 tick 的东西；什么都没投递就什么都不跑，所以没有 idle 路径要辩护，也没有退避要算。

**进行中到达的直达消息，接到它打断的那个 turn 上。**
原话：「和 emrg 一样，收到新的直达消息后，等工具执行完成后插入新的信息。你查看一下 emrg 的机制。」
决策：进行中的 turn 保留它的锁，消息在**轮边界**接进去——本轮工具返回之后、下一次模型请求之前。不是第二个 turn，不是打断正在跑的工具，也不是压到 turn 结束。从 EMRG 保留：整表原子 pop、提交时打一次时间戳、给注入消息刷新轮数预算、绝不静默丢弃。这里不需要的，因为 seek 的收件箱在投递时就落盘、它**就是**进行中的队列：客户端重发协议和第二份待处理列表。

**第二段的 turn 就是普通 turn。**
决策：它不额外多写任何记录。它是普通 turn，只有一点不同——它开场就知道没有人叫它。而且和任何 turn 一样，它也可能什么都没说：说话是一次工具调用（见上），所以当 agent 认为没有值得说的话时，沉默正是会发生的事。

## 数据模型

**数据模型先做。**
决策：先把大块头定清楚——Agent、房间、聊天、会话、话题，以及它们怎么关联；这个阶段不抠细节。

**@ 和回复是 bot 层的事实。**
原话：「A。」［我问的是：`mentionsMe` 是投递时按 bot 算一次，还是每个 agent 各算一次。A＝按 bot 算一次，落进收件箱条目。］
决策：在投递时推导，落在那只 bot 的收件箱条目上。没有 agent 去房间里扫自己的名字：bot 知道一次，然后告诉它的 agent。

**消息上只存 `mentions[]`，不存任何按读者算的东西。**
原话：「A，看 `mentions` 里有没有我自己的名字。」
决策：消息保留飞书自己那个数组；`mentionsMe` 在投递时推导、按 bot、只落在该 bot 的收件箱条目上。把 per-reader 的布尔值存到共享消息上，要么逼出一次重写，要么每个 bot 存一份副本，把一次数组扫描变成一份会和它描述的东西不一致的状态。

## agent 找 agent

**agent 可以找到 agent。**
原话：「可以。」
决策：agent 之间可以接触。形式见下一条。

**所有交互都在 IM 上体现。**
原话：「A，所有交互都在 IM 上体现，可群聊可私聊。」
决策：一个 agent 够到另一个 agent 的方式是**发一条消息**，绝不是调一个工具。没有同步委派调用：那会让 A 在 A 的 turn 上替 B 做决定，绕过 B 存在的意义。谁跑这个 turn 谁付钱，所以被委派方的工作记在它自己的账上，永远不会藏进调用方的账里。

**bot 可以和另一个 bot 开房间。**
原话：「可以。」［我问的是：bot 能不能和另一个 bot 开一个房间。］
决策：可以，且没有审批步骤；成员资格不由人把关。照录代价：左侧列表会长出用户从没开始过的对话，而这件事的答案是人设，不是门禁。

**bot 可以对另一个 bot 说第一句。**
原话：「A。」［我问的是：一条链的根可以是另一个 bot 的消息吗，还是必须由人起头。A＝bot 可以主动开这个对话。］
决策：一条链的根不要求是人类消息，也不要求是排程 tick。bot 可以对同伴开一个对话——在两者都在的房间里，或者它为此开的单聊房间——和它对一个人早就可以做的事完全一样。**链的数量没有任何结构性约束**，这个代价照录，不做平滑。一条链能跑多长、一个房间一次爆发多少，仍然是有界的，但界是两个数字，不是宿主给的——那是我的默认值，不写在这里。

**链不设预算。**
原话：「删掉。」［我问的是：链用什么兜住——留着链预算，还是删掉。］
决策：链没有钱上的上限。它的成本按 turn 记录、可读。拦住失控往复的不是钱而是结构：一条链能跑多长、一个房间连续几轮 bot 发言。

## schedule

**一张全局排程、一个工具，到期就是一次投递。**
原话：「提供一个全局 schedule 吧，提供工具给所有机器人，每个机器人都通过这个工具读写这个 schedule（包括什么时候、发什么提醒给哪个机器人）。schedule 事件到期后，自动发送提醒给对应的机器人（属于直达信息，和 @ 等效）。」
决策：一张所有 bot 都读写的表；一个工具 `schedule`，三个动词——list、add、cancel——除此之外没有别的；到期的一行变成一条普通的收件箱条目，`kind: "reminder"`，走快通道。**这是多了一个投递的生产者，不是多了一个唤醒源**：一张表加一个比较器，而不是每 bot 一个心跳；而且它不叫醒任何人——一行到期**就是**一次投递。检查实现的那条线：**schedule 可以产生投递，绝不能产生 tick。** 它让 bot 能兑现承诺——「这件事我明天看」能真的发生——也还掉了时间式 `snooze`：由环写一行来完成。

**到期的提醒不显示。**
原话：「不用显示。」
决策：提醒进 bot 的收件箱就停下——行上没有 `room` 字段、不进帧、聊天记录不多一行。用户看见的是它对此做了什么，别的什么也看不见。**飞书一致性在这里止步**：一致性管的是 bot 怎么够到别人，而提醒够不到任何人，没有第二个当事人可以显示。照录代价：界面显示结果不显示原因；它靠读记录就能还原，而不是靠显示。

## 分发

**权重先问镜像，再问官方站。**
原话：「甲」（问题是实现者提的：「默认从官方 `huggingface.co` 取 `LFM2.5-VL-3B`，而那台主机从这台机器连不上——可测的：40 秒超时，而 `hf-mirror.com` 对两个文件都回 `206` 且 `content-length` 对得上。默认该走哪边？甲：先问镜像、再问官方——对谁都不吃亏，反面是每次首启先等掉一段超时才知道没戏。乙：默认仍是官方，连不上的人自己去设变量。」）
决策：先问 `hf-mirror.com`，之后再问 `https://huggingface.co`。后备主机不是第二次下载——`.part` 里存的是字节，不是某一台主机的承诺，所以在某一台上停下的文件会在下一台上接着取。显式设了 `SEEK_WEIGHTS_BASE` 就只有那一台。

## 怎么干活

**一次一个问题。**
原话：「问我问题要说完整，所清楚，说重点，逻辑性和不废话，每次一个问题。记住了吗」
决策：每个问题自足——要定的到底是什么、每个选项各自的后果、一句推荐加一句理由。要让宿主反问回来的问题，等于没问。

**他没说过的话不许安在他头上。**
原话：「什么时候定过这条规则的？」
决策：任何陈述都不许说成是他说的。追不到出处的规则是提案，并且标明是提案。这个文件就是为这件事存在的。

## 文档

**每份文档都出中英两版，并保持同步。**
原话：「所有文档都是中英文版本，并保持两份文档同步更新。」
决策：两份都要维护，用 `.zh-CN.md` 后缀放在同级，而不是开一棵平行目录树；**两半没有高低**——不一致是这一对的缺陷，立刻修。改完英文文件不算完，中文孪生必须在同一次提交里一起改。两个例外：`LICENSE` 只出英文，因为翻译过的许可证不是那个许可证；带日期的 review 保留译文作为那一日的快照。

**文档只放结果，不放过程。**
原话：「review 不要放到文档里，文档只放最终结果，不需要包含过程。（比如之前是什么改造后是什么原因是什么，这些都不要，不要体现历史，历史从 git 提交记录里有）」
决策：文档陈述现在成立的东西，写成实现者能照着建的样子。一条规则以前是什么、改成了什么、为什么改，都不出现；日志里存着。

**这个文件不写日期，也不留被取代的条目。**
原话：「host rulings 不需要写时间。我每次对某个问题有新的决策时，就删除老的，写入新的就行。」
决策：条目按它回答的问题分组。它取代的那条就没了；要找回旧决策，看带这次改动的那次提交。
