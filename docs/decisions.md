# Decisions

One line each, dated. What is written here is **not casually overturned** — overturning it requires explaining why the earlier reasoning no longer holds.

## Naming and license

- **The name comes from ICQ's original line: I Seek You.** Seeking *a person* is the point of IM — not opening a tool. seek keeps that point and only swaps the person for a long-lived agent. Tagline: *Typed like ICQ, shaped like the characters you know.*
- **License: MIT.**
- **English is the project language**, and it is the language of everything that leaves the repository — issues, pull requests, commits, comments.
- **Every document ships in both languages and the two are kept in step** (ruled 2026-10-24: *"all documents come in Chinese and English versions, and the two are kept in sync"*). This **supersedes** the earlier rule that translations were references, never authoritative, and might be allowed to lag or be deleted — the host has asked for two maintained versions instead. The convention is a `.zh-CN.md` suffix beside each file, never a parallel tree. **Neither half outranks the other**: a disagreement is a defect in the pair, fixed at once. A change to an English file is unfinished until its Chinese twin changes in the same commit. Two exclusions: `LICENSE` stays English only, because a translated licence is not the licence, and dated reviews keep translations as snapshots of that date.
- **The product is international from the first screen**: no user-visible string in code; content is never machine-translated behind the user's back; an agent's language belongs to its persona, not to a global setting. Details in `docs/design/i18n.md`.

## Rooms and time

- **Rooms are not classified by headcount.** There is no "1:1" or "direct message" type: a room with two people and a room with fifty behave identically. A branch on headcount in the code means the model is broken.
- **A bot may open a room on its own** (ruled 2026-10-23: *"yes"*). No approval step and no user action is required for a bot to create a room, including a room with only itself and one other bot in it. This follows from the two rulings above it rather than being a separate privilege: all interaction is IM, group or direct, so opening a chat is ordinary speech, and an agent's only constraints are its prompt and its sandbox. The cost is accepted and recorded: **the left-hand list can grow with conversations the user never started**, and the fix for that is the persona, not a gate — the same way a badly-behaved agent is fixed.
- **What Feishu actually has here, since it sets the vocabulary** (checked 2026-10-23 against the open-platform docs, *chat_id* page, last updated 2026-02-02): a chat's mode has **three** values — 群组 / 话题 / 单聊 (`chat_mode` = `group` / `topic` / `p2p`) — and **a direct chat is a chat**: it has its own `chat_id` beginning `oc_`, and `chat_mode` reads `p2p` when you query it. So "a direct message is a room with two people" is not our invention; it is how Feishu stores it. Two caveats worth keeping straight. **①The field exists; our domain logic still must not branch on it** — the entity is a Room either way, and Feishu's own behaviours (you cannot invite into a p2p, you cannot leave one) are properties of the surface, not reasons to split the model. **②Feishu's `p2p` is bot-to-user only**, so a direct room between two bots has no Feishu counterpart to imitate. That is the one place in this design where "the answer visible in Feishu wins" cannot decide, because Feishu has nothing there to show; it was settled by the host instead (see the ruling above).
- **A room is not a session.** The room is the container (persistent, membership changes); a session is one stretch of work inside it (its own timeline, bound to one workspace).
- **A workspace is bound to the session**, fixed once chosen; changing it means starting a new session.
- **A thread is a message tree, not a new room.** Everyone in a thread is already in the room; no re-inviting. Feishu-style, not Slack/Discord-style.

## Agents

- **seek is a multi-agent product.** Behind each avatar is an agent, not a person. The IM shell is only a shell.
- **An agent is long-lived, observes on its own, and acts on its own.** Those are the three differences from an ordinary agent.
- **A bot wakes on a message — and the schedule is a second producer of messages, not a second wake source** (clock deferred 2026-10-23; the schedule ruled 2026-10-24). A delivery into the inbox starts a tick; with nothing delivered, nothing runs. **The clock was considered and deferred, not rejected**, and both shapes worked out that day — a timer as a second wake source, and a timer writing its own `kind: "clock"` entry — were withdrawn as more machinery than the design needed yet. **The schedule that was ruled the next day is neither of them**, and neither of the two reasons the timer was withdrawn survives it: it is **one table in the process plus a comparator**, not a heartbeat per bot, so nothing is paid per bot and no model is called to find out that nothing is due; and it leaves nothing to answer about *"what wakes a bot whose queue is empty"*, because **nothing wakes a bot** — an entry coming due at 09:00 is a message written into one bot's inbox at 09:00, and a delivered message wakes it exactly as a person's would. So the rule stands word for word and this is what it now says: the only thing that wakes a bot is a message, and a message may come from a person, from another bot, or **from the schedule that bot itself wrote**. What the deferral had cost is now partly repaid and partly still owed: ①*proactive outreach is no longer trapped inside a tick someone else started* — a bot can leave itself a reminder for tomorrow morning and come back to find it, which is the "keeping a promise" ability the 2026-10-23 argument said a purely message-triggered agent could not have; ②*time-based deferral now has something to fire it* — a `snooze` conditioned on time is performed by the loop writing a schedule entry (§12). What stays true is the part the deferral was protecting: an awake bot in an idle moment costs nothing, and a bot with an empty inbox and nothing due is not running at all.
- **One path, one loop.** Every message is delivered into the inbox at zero cost; the loop's gate then decides. A direct message, an @-mention or a reply to its own message is not a second road — it is a **fast-pass inside the gate**, skipping the watch because there is nothing to decide. Two roads would let the same message be answered twice; one road has nothing to reconcile.
- **Three ways to decide not to act**: ignore, defer (re-queue with a condition), or keep silent but remember. The third is "present but not interrupting".
- **An agent may open a direct message to you**, with no quota, cooldown or quiet-hours rule. A seek agent *is* an EMRG agent: **its whole constraint is a prompt and a sandbox.** Restraint about interrupting you belongs in how the persona is written, not in a gate beside it. (Earlier drafts of this rule carried a card of invented limits — a five-case whitelist, a four-case blacklist, three a day, thirty minutes apart, silence 22:00–08:00. All of it was the implementer's, none of it was decided; withdrawn 2026-10-23.)
- **An agent does not ask permission before acting** (ruled 2026-10-23). It edits files, runs commands and sends messages without stopping for approval — a per-action dialog would turn an IM into a ticket queue. What holds instead is the sandbox, a complete audit trail (every action is a `Turn`), and a stop that works (you can always see it and end it). Asking *"may I?"* is gone; asking *"which one?"* remains — needing a decision is a conversation, not a permission.
- **Messages are shared; context is private.** Five agents in one room means one message log and five private interpretations.
- **A member is a projection of an agent into a room, not the agent itself.** An agent belongs to no room; rooms are only where it appears.
- **Aliveness needs a gate, and that is why the gate exists** (ruled 2026-10-23). EMRG is trigger-driven, so an idle agent costs nothing; a seek agent is alive, so without a gate in front of it, it spends continuously for no reason. The gate answers two requirements: it must stop meaningless work (a busy room's chatter that has nothing to do with it must cost nothing to disregard), and it must itself be almost free.
- **Bot and Agent are two entities, not one entity seen twice** (ruled 2026-10-23). **The bot is the contact**: it owns the name, the avatar and the description, it is what a room shows and what an @-mention names. **The agents are the workers behind it**, each with its own persona, model, session, memory, state machine and line in the cost ledger. The bot **pushes its identity down to its agents** — an agent has a `role`, not a name — so a rename reaches every agent at once and the room never shows two contacts where there is one.
- **Behind every bot there are two agents: one watches, one works** (ruled 2026-10-23). **`agents.yml` registers agents, not bots**; a bot is the grouping they belong to, and nothing caps it at two — a bot that later needs a third role gets a third row. Two rows is two of everything the kernel already gives an agent (a model, a session, a memory, a state machine), so no new container is invented and nothing that iterates agents learns an exception.
- **The split runs through the whole model, and the line is alive vs. runs** (ruled 2026-10-23). **Bot-level**: identity, membership, @-mention, a room's participant list, the observation queue, the tick and the state machine — everything that is alive. **Agent-level**: model, prompt, tools, session, memory, turn and cost — everything that runs. A message record keeps the producing agent even though the room does not show it.
- **Only the observations cross from the watch agent to the work agent — never its reasoning** (ruled 2026-10-23). The work agent wakes with the entries and nothing else; it reads its own history and memory and decides for itself. A reason placed in its context is not advice but a **premise**, and the expensive model would build on it as fact — so where the watch agent is wrong the work agent would amplify it, and the amplification would look like coherence. The cost is accepted: sometimes the work agent will not see why it was called and will say something flat-footed. The watch agent's reason is still recorded on the observation entry, so a bad call stays reviewable and the watch agent can read its own log back.
- **Both agents get EMRG's toolset, unchanged** (ruled 2026-10-23: *"just use the EMRG set"*). No watch-specific tool, no memory tool and no compaction tool is invented: the registry is the one already in the kernel (bash / read / write / edit / glob / grep / subagent / submit_rant / boss), and which tools a given agent may call is ordinary per-agent configuration in `agents.yml`. **One exception was named by the host: `schedule`** (2026-10-24, see the schedule ruling below) — and a second one appearing beside it means the exception was read as a licence rather than as the single addition it is. Note the fact this settles: **memory writes and compaction are not tools in EMRG** — the runtime does them at the end of a turn — so they stay runtime behaviour here too. Consequence recorded: the low-hundreds-of-milliseconds figure is a target for the common no-tool judgement, not a guarantee; a judgement that calls a tool costs a second round, and a 300 MB model reaching for `bash` is rarely worth it, so the expected shape is that the watch agent almost never uses its tools.
- **The watch agent gets no feedback channel; it reads the outcome off the record** (ruled 2026-10-23). A forwarded observation followed by silence from the work agent is already visible in the data — the entry has no message after it — so the watch agent sees its own miss next time it meets that room, in its own memory. Nothing reports anything to it, and **it is not learning**: no training, no rule-writing, no accuracy target. **It is fine if it never gets better**; what keeps it honest is that the record is reviewable and the work agent can read it.
- **"Was I addressed?" is a bot-level fact, and it is derived — not stored on the message** (ruled 2026-10-23: *"look at `mentions` and see whether its own name is in there"*). The message keeps the Feishu field `mentions[]`: the principals it @-mentions, id and display name, which is what the interface draws and what the open platform defines. `mentionsMe` is not a second stored fact — at delivery the producer finds the bot's own id in that array and records the boolean on **that bot's** observation entry. So the message is written once and stays clean, several bots derive their own answers from the same message, and nothing in `hints` is ever written back onto it. No agent scans a room for its own name — and the watch agent could not: it is unaddressable, so an @-mention is a question only the bot can answer. This is what keeps stage 0's fast-pass a rule instead of a model call.
- **The inbox lives on the bot, not on an agent** (ruled 2026-10-23: *"the inbox can sit on the bot — that way the agent design stays simple, close to EMRG or Google ADK"*). One queue per bot, one "already handled" state, one tick. Delivery is one write per (bot, message) instead of one per (agent, message), so nothing has to reconcile N queues. **This is what keeps an agent small**: an agent is a runnable — a model, a prompt, tools and a memory, called by the bot's loop — the same shape as an EMRG session or an ADK `LlmAgent`, with no lifecycle of its own to design. The watch agent runs a local, bundled model; the work agent runs the expensive one. **They do not share memory** — each has its own session history and its own memory store, because their windows are an order of magnitude apart and compaction is destructive: a shared log means the small-window agent compacts first and deletes detail the large-window agent can still read. That is silent amnesia, so the two stores are separate rather than managed by one policy. **Each knows the other exists and can read the other's history and memory** — the work agent reading the watch agent's log costs billed tokens, so it is on demand and never injected into every turn; the watch agent reading the work agent's log costs nothing in money but costs latency, so it reads a bounded slice. The read channel is what keeps the bot honest about *"I said nothing there"*: without it the half that talks to you invents a reason for the other half's silence. **There is no watch-specific input pipeline** — each agent sends its own history, memory and compression, because each is an agent and not a classifier. Because the watch agent is local, its tokens cost wall-clock rather than money, which makes latency, not price, what the watch model is chosen against. It must be **multilingual (Chinese and English at minimum) and multimodal — it has to see images**, because a room's messages carry screenshots and photos, and a watch agent that reads only English or only text is blind exactly where it is needed. The size target is ≤ 300 MB of weights; that target and the multimodal requirement pull against each other (a 500M multimodal model publishes at 2 GB in bf16), and the trade is settled at selection time against real cases rather than by dropping either requirement. Rules run ahead of it and settle everything that is both certain and free: **no new observations means return at once; an @-mention, a reply or a DM means act at once**; the model is asked only about the ambiguous remainder.
- **An agent runs one action at a time.** When several rooms want it to speak at once, they queue — for identity consistency, not for performance.
- **A direct message that arrives mid-turn is injected at the round boundary, as in EMRG** (ruled 2026-10-23: *"same as EMRG — when a new direct message arrives, wait for the tool run to finish and then insert the new information"*). Neither a new turn nor an interruption: the running turn keeps its lock, and the message joins it after the current round's tools return and before the next model request (EMRG `daemon.py:4574-4578`). Four things EMRG does around that are kept rather than reinvented: the drain is **one atomic pop of the whole queue**, so a message arriving during the drain is injected next round and never lost; each injected message is written **once, with its timestamp at commit**, so compaction keeps it and the interface has a time to show; the **round budget is refreshed for the injected messages** instead of stranding them; and **nothing is dropped silently**. **Two things are deleted, because seek's queue is already on disk** — the inbox written at delivery *is* the in-flight queue, so there is no `queued_requeue` for a client to re-send and no second list to reconcile; and an injected entry is marked consumed when it goes in. **The injected set is stage 0's fast-pass set** (@-mention / reply / direct message), not every arrival: an inbox entry nobody has judged must not land in the middle of a job. Cost accepted: one turn can grow without a cap, since seek has no quota anywhere else.
- **An agent may address another agent, and may open the conversation** (approved 2026-10-23; extended the same day). Finding another agent is a normal part of work. **A bot may say the first word to another bot** — in a room both are in, or in a room it opened for that purpose. **The root rule is withdrawn**: it held that a chain's root is a human message or a scheduled tick and that an agent never opens a conversation with another agent. It was withdrawn because a bot may already open a conversation with a *person* (proactive outreach, §10), and nothing anywhere asked for the asymmetry — note that with the clock deferred, the bot can only do so while a delivered message has it awake, but the rule is not what limits that; and because the bound it protected — the *set* of chains — is not a bound the rest of the design leans on. **Recorded cost**: the set of chains is now bounded by nothing structural. Depth caps how long a chain runs, not how many a bot may start, and a new conversation starts a fresh chain at depth 0. What bounds a burst inside one room is the consecutive-agent-turn cap; what bounds a bot's decision to start another conversation is its persona and the fact that everything it does is on the record. This is the same trade already accepted for proactive messages to people, which carry no quota either.
- **All interaction is IM — group chat and direct messages** (ruled 2026-10-23: *"all interaction is expressed in IM — group chat and direct messages"*). There is no second channel, and no tool call stands in for one. So **an agent reaching another agent posts a message**: into a room the other bot is in, or into a direct room between the two. It lands in that bot's inbox like anything a person says, and that bot's own loop decides whether to take it up. What "delegation" means is the intent, not a mechanism — "do this and report back" and "what do you think" are both messages, entering the same inbox and carrying the same chain. **The synchronous `ask_agent(B)` tool is withdrawn**: it is a tool the kernel does not have (EMRG's registry is fixed, and `subagent` opens a child session of the *same* agent, not another bot), and it inverts what makes a bot a bot — a synchronous call has A deciding for B, on A's turn, bypassing the judgement B exists to make. Who pays is then trivial and correct: whoever runs the turn pays, so the delegate's work is on the delegate's ledger and can never hide inside the caller's. **This withdraws "every room has at least one human member"** — a rule the implementer invented at 20:12 and never ruled, and one this ruling contradicts outright: a direct room between two bots has no human in it. Agent-to-agent traffic is bounded by depth and the room's consecutive-turn cap instead, neither of which needs anyone present to notice.
- **An agent-to-agent chain is bounded by depth, not by money.** Every message carries the message that caused it, so the depth is read off the data rather than kept in a counter someone has to restore. At the cap the agent escalates or stops — it never silently drops the question. There is no chain budget and no chain count: the depth cap exists to stop a loop, not a bill.

## Interaction

- **The interaction is Feishu's, and the model serves it — not the other way round.** Where a design question has two answers, the one that is visible in Feishu wins; a concept that Feishu does not show the user does not appear on screen here either, however useful it is internally.
- **The left list shows rooms, not sessions.** They are chats. (Closes an item that had been open since 18:42.)
- **A session is an agent's private stretch of work in a room, never a user-visible unit.** One room's timeline is continuous; five agents in it have five private spans over one shared log. A workspace change surfaces at most as a system message. This is not a display preference: it is what makes "messages shared, context private" true by construction.

- **The schedule is one global table, one tool, and a due row is a delivery — not a tick** (ruled 2026-10-24: *"provide a global schedule — a tool for every bot to read and write it; when an entry comes due, send the reminder to that bot automatically, as a direct message, equivalent to an @-mention"*). Every bot reads and writes the same table through one tool, `schedule`, with three verbs (list / add / cancel) and nothing else. A row says **when, what reminder, which bot**, and its `text` is delivered verbatim — not summarised, not translated, not rewritten. **This is why it is not the clock the design withdrew twice on 2026-10-23**: it is one table plus a comparator rather than a heartbeat per bot, and it wakes nobody — a row coming due writes an ordinary inbox entry, so the existing wake rule stands unchanged. **The line the implementation is checked against: the schedule may produce deliveries and may never produce ticks.** What it repays is the deferral's first cost — a bot can now leave itself a reminder for tomorrow morning and come back to it, so "I will look at this" can come true without a message from somebody else upstream. It also closes the time-conditioned `snooze`: the loop performs it by writing a row, so the watch agent still emits a verdict and calls no tool. Costs recorded: the inbox may now hold an entry the bot wrote to itself (retiring the 2026-10-23 claim that it never could, while keeping the reason it existed); one new tool exists against the standing "EMRG's set, unchanged" rule; a shared writable table brings stale rows and unbounded growth, bounded only by pruning `fired` rows; and **a bot can call itself awake indefinitely** by scheduling its own next round — the same trade as the absent quota on proactive messages, defended by the persona and the record, not by a gate.
- **A reminder is not displayed** (ruled 2026-10-24: *"no need to display it"*). The schedule row carries no room, and when it fires the reminder goes into the bot's inbox and no further — the user sees what the bot does about it, never the reminder itself. **This is the one place the design deliberately does not follow "all interaction shows up in IM"**, and the reason it does not conflict with that rule is worth stating: the reminder is not interaction. It is the bot talking to itself, and the rule governs how the bot reaches *other principals*. The cost, recorded rather than smoothed: **the interface shows an effect without its cause** — a bot that suddenly speaks at 09:00 looks unmotivated on screen unless someone reads the schedule table, so the audit path (the row, the turn that fired it) has to stay readable rather than the transcript carrying it.

## Closed by default (2026-10-24)

These three were the last open items. They are closed **on the implementer's defaults, at the host's instruction to finish the design** — recorded as defaults rather than dressed up as rulings, and revisable by one word from the host.

- **A session does not keep a member snapshot.** Whoever said what is already on the message (rule 15), so a snapshot could only answer *"who was here when this stretch began"*, and it would be a second fact about membership that silently goes stale. A private bookkeeping span has no use for it.
- **The watch agent is not addressable.** Only bots are: an @-mention names a contact in a room, and the watch agent is not a member and has no face. Another agent cannot reach it directly — it reaches the *bot*, whose loop decides whether the watch agent is asked at all.
- **A watch agent turn stays in the watch agent's own history.** The alternative was writing it into the work agent's history, which would put it in the work agent's context on every turn — and that is already ruled out by the read direction: the work agent reads the watch agent's log **on demand and never by injection**. Writing the line in would be the injection the ruling forbids.

One thing in this list was never a question and stays as a standing constraint rather than an open item: nothing about the watch agent improving over time is assumed anywhere (see the ruling on the watch agent's feedback above).
