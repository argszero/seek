# 按测量选出来的 work 模型

`calibration/work/` 存在，是因为**内核里负责说话的那一半，从来没有被套用负责判断那一半已经遵守的规矩**。`src/README.md` 第 25 行说 watch 模型要按测量选、而不是按体积选；work 模型没有人这么要求过，而随包发的那个模型从未被问过唯一真正重要的问题：**它会调用 `say` 吗？**

issue #89 量到的答案是「不会」。在已发布的 `v0.1.3` 上、对着真实的 `llama-server`，用随包的工件以 `tool_choice: 'auto'` 提问，**30 次请求 30 次**只产出散文、没有调用；换成 `required` 则是散文加 `finish_reason: length`。随后三项读数排除了两个「问题在请求而不在模型」的解释：改写工件的各部分没有改变任何结果，而同一台服务器、同一个 body，在不带工具的普通回合上是正确作答的。

于是问题从**怎么问**变成了**问哪个模型**。本目录就是这个答案，而且是量出来的。

## 案例是什么

**九条手写案例**，为本测量在项目自己的会话（`seek-opensource-task`）里于 2026-10-26 写出，用的框架与其余语料一致：一个支付运维团队的房间，房间里有一个叫 Echo、盯着夜间批处理的 bot。它们不是从真实聊天里采集的，也不来自任何第三方。

| 标签 | 含义 |
|---|---|
| `speak` | 这个回合应当以一次带文字的 `say()` 调用结束 |
| `quiet` | 这个回合应当在什么都没说的状态下结束 |

六条想要回答（三条英文、三条中文，其中两条指名 @ 了 bot），三条想要安静（`ok`、`thanks!`、`好的收到`）。

**两个方向都进集合，是因为这两种失败互为反面、而且都是缺陷。** 该说话却什么都没发出去的回合让房间空着，那就是 #89。该安静却开口的回合，是 bot 在一个没人问过它任何事情的房间里作答——整个闸门存在的理由，只是晚了一个阶段才出现。只放前一种的集合，会给「永远说话」的模型满分。

## 台子

旁边这个文件 `measure.mjs` 就是驱动本身。它接受 `MODEL=<gguf>`，跑的是内核**自己的**装配——`assembleWorkPrompt(loadWorkArtifact(), …)` 套在随包的 `src/prompts/work-v1.json` 上——不是它的转述，所以两行之间唯一的差别只可能是模型。它从自己所在的那个检出里 import 这套装配，所以重跑量到的就是读者手上这一份；`LLAMA=<路径>` 指向另一个 `llama-server` build。

| | |
|---|---|
| 服务器 | `llama-server` 0.7.0-dev（build 1，commit `701fd25`），AppleClang 17，Darwin arm64 |
| 参数 | `-c 4096 -np 1 -ngl 99`，只有带投影器加载的模型才加 `--mmproj` |
| 工具 | 工件的 `tools`（`say`），原样送出 |
| `tool_choice` | **`auto`**——`src/llama.ts` 里随包发的那个值 |
| 温度 | 0 |
| 端点 | `POST /v1/chat/completions` |
| 重复 | **每条案例 3 次**——每个模型 27 次请求 |

**任何一行都没有动过工件。** `src/prompts/work-v1.json` 一个字符都没改，这正是各行可比的原因：剩下的唯一变量就是模型。

**这棵树现在发布 `work-v12.json`，而下面每一行都是在 `work-v1.json` 上量的。** 提示词是版本化的东西，不在原地改，所以 v1 以它被量时的样子留在树里。v2 加了两段——这个机器人在它的组织里做什么、它怎么说话和做事——机器人的资料卡空着时两段都跳过；v3 加了一段，是它上次写给自己的那间房的注，房间还没压过时跳过；v12 让每一行说出它是从哪间房来的——箱是一台机器人一份的，不是一间房一份，所以里面读到的可能来自好几间房——其余照 v11。所以卡上什么都没填、房间也从没压过的机器人，在 v2／v3 发布期间拿到的就是 v1 的逐字原文（`src/prompts.test.ts` 曾把两次装配直接对比，那条断言里写着为什么现在不能这么比了）。

**v4 是这份记录第一次没有覆盖的版本，而这里明写这一点，而不是让它看起来被量过。** 它重写了 system 那句、开头和最后那问；加了两段，让机器人像是会上一个人，而不是一个助手——它自己付出和得到的东西，以及它这一轮只出的那一招；并且给 `say` 添了 `mentions`，于是机器人可以点名其他人，一屋子机器人能自己接着谈。下面没有任何一行是在 v2、v3 或 v4 上量的：驱动只交一句描述、不交资料卡也不交注，所以它装配出来的仍是 v1 的文本；在任何更新的版本上重跑，都是新的一组行。

**v5 是同一类改动，也是这份记录没有覆盖的最后一个版本：条目那一行现在说出它是什么时候到的。** 它渲染 `[{at}] {sender}: {text}`，也就是 `watch-v3` 早就在用的、给同一个事实的写法；值是观察自己的 `delivered_at`，不是「一周前」——那需要在拼装的时候读一次钟。相隔一周的两条消息从前到的是同形的两行，所以回答那半分不清一句回复，和一句对七天前说过的话的回答；而 `work-v5` 从 v4 继承的那几段，正要求它说出什么时候会知道一件事行了、什么时候再看。驱动的那些行根本不交时间，所以它们装配出来的仍是 v1 的文本；这份记录关于 v5 什么都没量。

**v6 是同一种缝，只是补在图片的另一头。** 判定那半被交到消息里的图、并且拒掉它（`box.ts`，`docs/host-rulings.md`：随包模型自己声明 `modalities.vision: false`），而回答那半从前什么都没拿到——在请求体上量到的：一条整个内容就是一张图的消息，到提示词里是 `me:`，和一条空消息一模一样的一行，而把整份请求体搜 `picture`、`image`、`media` 和那个 blob 自己的 key，一个都没有。v6 多了 `pictureLine`，也就是文件自己给这个事实的那句话，条目那一行用 `{picture}` 说明它放在哪：带图的条目说出来，不带图的就是 v5 那一行、逐字节相同，而一张没有说明的图不再是一行空的条目。驱动的那些行根本不交图，所以它们装配出来的仍是 v1 的文本；这份记录关于 v6 什么都没量。

**v7 只改一句、一段都不动，而它是这份记录没有覆盖的最后一个版本。** v6 那句话底下的事实变了：回答那半现在真的拿到箱子里的图（`TurnBox.media`，加上由客户端提供的字节 loader），所以「一张图来了，你看不到它」会变成一句不实的话——请求里明明带着那张图。v7 的 `pictureLine` 说的是这张图跟着请求来了，并写明没有来的那种情形：一行没有对应的图，就是这一轮看不到的某张图。其余每一段、每一句话和 `say` 那个工具都和 v6 逐字节相同。驱动的那些行根本不交图，所以它们装配出来的仍是 v1 的文本；这份记录关于 v7 什么都没量。

**每一行里工具都真的送到了模型面前。** 这个 build 默认开启 Jinja 引擎（`--help` 报的是 `--jinja, --no-jinja … (default: enabled)`），所以每个 GGUF 自带的 chat template 负责渲染工具列表；随包模型的模板会把 `List of tools: […]` 追加进 system 消息。本目录没有任何一行是在工具被扣下的情况下量的、再被读成「模型不肯调工具」。

## 三行读数说明了什么

**1. 调用 `say` 是模型的属性，不是请求的属性。** 两个模型在完全相同的提示、body 和 `tool_choice` 下调用了它，而随包的那个在同样的条件下回以散文。这就结掉了 #89 开题时的问题：让房间空着的不是运行时的任何东西、不是 schema、也不是工件。是模型。

**2. 交付随容量上升，散文随之消失。** 0/6 → 5/6 → 6/6；2B 唯一剩下的那条散文是中文——它回答 `I am in the room oc_… . The agents behind this bot are: …`，把自己的系统提示读回来，而不是说话。到 4B，每条该说话的都在该说的语言里说出来了。

**3. 被测的模型没有一个安静下来，而随包的那个也并不安静。** 这一列正是这个集合存在的目的，而且它与「只测一列」时会得到的结论相反。随包模型的「该静时静」是 **0/3**——它对那三条全都写 `I'm sorry, but I can't help with that.`；按内核自己的规矩（除了 `say` 没有任何东西进入房间）这等于**没有消息**，但它并不是「一个什么都没说的回合」的那个行为。所以今天的模型在一侧彻底失败、同时也没做到另一侧；候选模型则在另一侧彻底失败。**「沉默」是没有任何模型哪怕做到过一次的那一列。**

**4. 回合既不会碰巧沉默，也不能被一次采样定案。** 每条案例重复三次、温度 0，三个模型各自 0/9 改判。这确立的是确定性，不是质量：它说这些不是掷硬币，它对换一种采样会怎样一字未答。

## 闸门拿这九条怎么办

work 模型是第二阶段。一条消息能到它面前，要么是第 0 阶段的规则直接放行，要么是第 1 阶段在随包切点上读出 `act`；否则就在那里被消费掉、什么都不花。所以上面那张表，只有在这九条真的走到那一步时才是代价。旁边这个文件 `measure-gate.mjs` 是驱动。记录有两份，因为判断那一半已经换过了：

- `gate.json` —— 本目录最早的那份读数，用的还是当时随包的 watch 模型（`LFM2.5-VL-3B`，读的是一个 token 的概率，并按选项的每种写法求和）。它按它本来的样子留着，文件自己的 `superseded_by` 指向下面这份。
- `gate-d1.json` —— 同样九条，走今天随包的判断：一次调用 `/v1/systemone`，问 `d1-2B`，它按每个声明的答案回一个标定过的概率，一个 token 都不生成。测法与本目录其余部分一致：用内核自己的 `classify` 和 `watchAs`、随包的 `0.600`，一次一条消息。

| 案例 | 想要 | 第 0 阶段 | 第 1 阶段（`act`） | 到达第二阶段 |
|---|---|---|---|---|
| the nightly batch failed again — can you look at it? | 说 | judge | **0.9638 → act** | **是** |
| @Echo what is the retry queue doing right now? | 说 | **act（指名）** | 没问 | **是** |
| did you finish the reconciliation you mentioned yesterday? | 说 | judge | **0.9585 → act** | **是** |
| 今天的对账跑完了吗？ | 说 | judge | **0.9385 → act** | **是** |
| @Echo 那条重试队列现在什么情况？ | 说 | **act（指名）** | 没问 | **是** |
| 批处理又挂了，你能看一眼吗？ | 说 | judge | **0.9359 → act** | **是** |
| ok | 静 | judge | 0.4371 → ignore | 否 |
| thanks! | 静 | judge | **0.7418 → act** | **是** |
| 好的收到 | 静 | judge | 0.5875 → ignore | 否 |

**该说话的六条全部到得了 work 模型；该安静的三条里有一条也到了。**

由此有两条读数，它们与判断那一半还是旧模型时写的正好相反。

**1. 「该静却说」这一列现在有代价了，代价是一条。** `thanks!` 读到 0.7418，越过切点，于是到达第二阶段。另外两条是 0.4371 和 0.5875，在切点之下。所以两个 Qwen 候选在这一列的 `3/3`，在房间里会花掉一次回答而不是零成本：拿到 `thanks!` 的 work 模型有权决定答不答它。这是用户真会遇到的缺陷，不是闸门能挡住的缺陷。

**2. 那张表原来的天花板没有了。** 上一份读数里，该说话的六条中有三条在第 1 阶段就被消费掉，所以一个交付 6/6 的 work 模型在房间里最多只能交付三条。换成 `d1-2B` 之后六条全部到达：交付这一列是 work 模型自己丢不丢的问题，而 4B 的 6/6 就是房间里六次回答，不是三次。

这就把那张表的用途还回来了。它问的是「哪个模型会**对它收得到的那些消息**说话」——而这个集合里现在是六条。

**一个条件，而且不是房间的条件。** 每条案例都是单独判的，`window` 为 10。运行时判的是一个 delta——一段 summary 加若干条 entry——盒子不同就是提示不同，所以这些数字是对案例的受控读数，不是对真实房间的回放。上一版那句「两条被拒的『该说话』案例是中文」已经不成立了：两条中文案例在这里都判 `act`（0.9385、0.9359），而现在唯一越过切点、本不该被答的那条是英文。

## 这份记录不决定什么

**发哪一个模型。** 那是成本与视野的问题，是宿主的话，不是测量的话：

- 六条全部交付的那个 4B 是 **2,497,281,664 B**，判断那一半的模型是 1,846,240,576 B（`d1-2B-Q8_0`），所以首启权重会从约 1.72 GiB 涨到约 2.3 GiB；
- 判断那一半读的是**一个标定过的概率**，来自一个决策端点，它的 `0.600` 切点是对着 `d1-2B`、在 `../set4-d1.json` 的二十四条上标定的（在出货的 `watch-v4` 上那个切点是 23/24）。换一个模型就是换一个分布，所以一个同时承担第一阶段的 work 模型，需要把那个切点重新标定——那是第二次测量，不是改一行；
- 两半接的是两台服务（`SEEK_SERVER` / `SEEK_WORK_SERVER`），所以把随包模型留在判断那一半、把 Qwen 放在写话那一半，今天就能做到，代价是**两份**权重下载（约 1.72 GiB ＋ 约 2.3 GiB）而不是一份。

## 没有量什么

- **把这几条放在一起判的第一阶段。** `gate-d1.json` 一次只判一条，上面那一节就是它逐条说的话。一格装若干条 entry，或者带 summary，或者换一个 `window`，都是另一个提示——而运行时判的是 delta。那份读数不在这里。
- **0.600 以外的切点，以及随包模型以外的 watch 模型。** 唯一越过去的那条该安静的案例读 0.7418，没过的那两条读 0.4371 与 0.5875，切点落在这个区间里就会改变哪几条到得了；挪它是宿主的话，不是本文件的话。
- **图像。** 每条案例都是文字，两个 Qwen 行都没有带投影器加载。本目录里没有任何东西说它们看得见。`src/README.md` 第 25 行的多模态要求是对 watch 模型说的；work 模型是否也必须看得见，是本集合不回答的问题。
- **一格装多条消息的盒子。** 每条案例都只有一条 entry，与 `../provenance.md` 为判断记录的那条限制相同。
- **温度 0 以上的任何情况**，以及任何采样。
- **用这个问法到底能不能达到沉默。** 它是所有行里唯一没有正面读数的那一列。
