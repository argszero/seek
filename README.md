# seek

<img src="assets/icon.png" width="104" align="right" alt="seek: a speech bubble holding a pupil" />

> **I Seek You** — the original spirit of IM.
> Typed like ICQ, shaped like the characters you know.

The name comes from the line that started ICQ. Twenty-odd years ago the point of instant messaging was to *find a person* — not to open a piece of software, not to launch a task, but to reach one specific being.

seek keeps that point and swaps the person: your contacts are no longer human, but long-lived agents. They have names, tempers and their own work. You talk in a room; they listen from the side; they speak up when they judge it worth it, and they come to you when something genuinely needs your call.

This is not a Feishu clone. It is a multi-agent product wearing IM clothes.

## Status

**The kernel exists; the interface has begun.** Three design documents are settled (`docs/design/`), the kernel is written in `src/` (56 TypeScript files, ~20,742 lines, 392 tests), and the previous runnable version is kept as a reference prototype (`prototype/`). The interface is a separate package under `ui/` — Electron running the kernel in its main process, with a React renderer — and it runs: it builds into a downloadable macOS app, and on a fresh install it makes the world it opens on — one room, its bot and the roster beside it — and from then on it reads a room, its members and its messages out of the kernel, draws them, and takes what you type. The window writes as well, and only through the kernel: the `+` beside the room list makes a room — a name, and who starts in it — through the kernel's own `createRoom()`, and the member count in a room's header opens the list that puts one more person in through `addMember()`, each refusal drawn beside the form in the kernel's own words. A message names the people it addresses, the open platform's `mentions[]` being the only form of *who was named* the store keeps, and the window draws them under the text. A picture goes further than a name: chosen from a file rather than typed, its bytes are written beside the store and the message carries only a `{key, mime}` reference to them — present exactly when the message is an image — so what a room with pictures in it is, is a store plus a directory of files, never one file with the bytes inlined. A message goes in through the kernel's own `deliver()`, the bot in the room is woken by the entry it received, and it answers. Whether it answers is a model's judgement and what it says is a model's words, each half bound separately to its own model server — the `llama-server` you name, or the one the download carries, which a launch that names nothing starts over weights it fetches, and, for the half that writes the words, a hosted endpoint you point it at; a half with no server behind it is the kernel's own placeholder, and the window says which half is on which. Who is in this organization has a view of its own, beside the rooms: every row says whether it is a bot or a person, a row opens a card holding what the store actually knows about them — no field the kernel does not keep — and `Message` opens the conversation with that one, entering the room the two already share or making it through the kernel's own `createRoom()`. The same rooms have a second lens: the groups view lists the ones whose membership is not exactly two people — a direct message in this kernel is a headcount, not a mode — a card says what it is and who is in it, and a group is made through the same `createRoom()` with you already among its members. Threads get a lens of their own too: the topics view gathers every thread in the store, whichever room it started in — a thread being the kernel's own `chain`, so a message nobody answered is not one — says which room each belongs to and how much was said in it, and opens it in the room it came from. A thread is the kernel's own record, not a second conversation: a reply goes in through the same `deliver()` with the message it answers named, and the panel shows the chain the store already holds. A window holds more than one world: the settings page lists the organizations on this machine, `Create` adds one from a name alone, `Rename` changes that name and nothing inside it, `Switch` opens that organization's own store — moving and deleting nothing — and `Delete` removes the row and moves its directory to the trash, refused for the organization being shown and for the last one, since one has to stay open. A name is a label for the list and never the name of the person inside: renaming an organization renames no room, no message and no self.

The prototype exists to prove one thing: that a desktop-messenger interface can be carried by purely local data. It can. But its data model is single-user — one account, a cast of fake people, messages owned by conversations — which is not the model this version needs, so it cannot be refactored into it.

## Why not another IM clone

| | Feishu / WeChat / Slack | seek |
|---|---|---|
| Behind an avatar | a person | a long-lived agent |
| Nobody @-mentions it in a group | it never knows | **it knows** — the message lands in its watch queue, at zero cost |
| When it speaks | only when called | when it judges it should — cheaply, not by running a frontier model on every message |
| Its cost | — | **recorded, never capped** — a turn carries the tokens it read and wrote, and the window shows them; nothing goes quiet because it spent |
| Context | fully shared | **messages are shared, context is private** — five agents in one room is not five copies of the room |

## Run the kernel

**Nothing to install**: no dependencies and no build step, so a clone runs where it stands. It needs Node 22.18 or newer — the code is TypeScript, and Node strips the types itself.

```bash
npm start                      # the first milestone
npm start -- --lang zh-CN      # the same run in Chinese
npm start -- seek-data/b.json  # a second store, beside the shipped roster
```

What it prints is one room, a person saying something that names nobody, and whether the bot answered on its own. **Both halves of the bot are placeholders** — the decision to act, and the words said — and the report says so in as many words. What a run demonstrates is the kernel: delivery into one inbox per bot, the gate, the turn. What it cannot demonstrate is whether the design holds up; that needs a model.

State lives in `seek-data/seek.json`, and a second run appends to the room the first one made — the data outliving the process is the product's own thesis, so the room grows instead of resetting. Delete that file to start over.

To ask the measured watch model instead of the placeholder, point the run at a `llama-server` you have started yourself:

```bash
npm start -- --server http://127.0.0.1:8080 --window 24
```

`--server` is the origin of a process **seek does not start, supervise or stop**, and `--window` is how much one judgement may read — the caller's number, because the runtime does not know a model's window. The two go together: either one alone is refused rather than half-guessed. **No weights ship with this repository**, so this is the one command here that needs something you provide.

A store outside `seek-data/` needs a roster beside it. `agents.yml` is read from the store's own directory every time the store is opened, and the store's agents are rebuilt from it. **Two states are not one.** A store with no roster file beside it keeps the agents it already has — a missing file says nothing about the store, so an install whose roster was deleted goes on answering with the workers it had — while a roster that is present and holds no rows is the one that says this bot has no agents. Editing the file is how a bot is given a different set of workers; deleting it is not. What refuses is `npm start`: a run whose bot has no watch agent and no work agent stops and says so, rather than inventing one.

## Install the app

The [releases page](https://github.com/argszero/seek/releases) carries the current build in two shapes: `Seek-<version>-arm64-mac.pkg`, which installs `Seek.app` into `Applications`, and `Seek-<version>-arm64-mac.zip`, the same bundle to unzip and drag. It is macOS on Apple silicon. Releases **up to `v0.1.1`** were built unsigned; a build cut from this tree is signed with a `Developer ID` certificate and notarized by Apple, which is what the rest of this section is about.

**An installer is built from now on, beside that zip.** `npm run dist:pkg` in `ui/` cuts `ui/release/Seek-<version>-arm64-mac.pkg` out of the same bundle with macOS's own `pkgbuild` (`packaging/make-pkg.mjs`), and installing it puts `Seek.app` in `Applications` without the drag. It is a `.pkg` rather than a `.dmg` because electron-builder's `dmg` target ends in `hdiutil create`, which the environment this repository is developed in refuses outright (`the operation is not permitted`), while `pkgbuild` is not refused — the same reason the neighbouring EMRG project ships its macOS download as a `.pkg`. And a release should not be something one machine has to be able to build: pushing a `v*` tag runs that same `npm run dist:pkg` on a macOS runner (`.github/workflows/release.yml`) and attaches both the `.pkg` and the `.zip` to the release.

**A build from this tree installs and opens without an argument.** `release.yml` imports two certificates from repository secrets into a keychain that exists for one run: `Developer ID Application` signs the bundle, `Developer ID Installer` signs the package (`packaging/make-pkg.mjs` calls `productsign` and then reads the chain back with `pkgutil --check-signature`), and `packaging/notarize.mjs` submits the package to Apple with an App Store Connect API key, waits for the verdict, staples the ticket to the file, and has Apple read that ticket back out of it. The last two of those go to Apple, so a network failure there is retried rather than believed: a ticket already written does not stop existing because a host is unreachable, so the final re-read reports an unreachable Apple as a warning, and only a package that really carries no ticket fails the release. The two certificates are not interchangeable — an installer and a bundle are assessed by two different parts of the system, and `productsign` refuses an Application certificate outright. On a laptop the **installer** identity is the one that decides whether the package is signed, and `npm run dist:pkg` without it still builds, says the package is unsigned, and skips `productsign` instead of failing. The **bundle** is not gated that way: electron-builder signs it with an identity it finds in the keychain by itself, so a machine holding any certificate — a development one is enough — produces a signed bundle, and `CSC_IDENTITY_AUTO_DISCOVERY=false` is how that machine asks for an unsigned one instead. The release never depends on discovery: `CSC_LINK` names the certificate the runner uses.

**Releases up to `v0.1.1` will object, because nothing up to there is signed.** Those downloads carry no signature and no notarisation, so Gatekeeper refuses them. The two shapes are refused at different moments, and the `.pkg` first: it is assessed when it is opened, before there is any `Seek.app` to right-click, so the fix that belongs to the installed app cannot be followed by a reader who chose the installer. Measured on the published `v0.1.1` `.pkg`: `pkgutil --check-signature` answers `no signature`, and `spctl -a -t install` answers `rejected` for `no usable signature`. What follows is what those releases need.

The `.pkg` asks you to clear the flag on **the file you downloaded**, and then to open it again — or, in the hour after the refusal, to take **Open Anyway** in System Settings → Privacy & Security:

```bash
xattr -d com.apple.quarantine ~/Downloads/Seek-<version>-arm64-mac.pkg
```

The `.zip` asks for the app: unzip, drag `Seek.app` into `Applications`, then right-click it and choose **Open** — or clear the flag on the installed bundle:

```bash
xattr -dr com.apple.quarantine /Applications/Seek.app
```

**Signing leaves one asymmetry inside a signed release.** The ticket Apple issues is stapled to the installer, and a `.zip` is not something a ticket can be stapled into: the app inside it is signed by the same certificate but carries no ticket of its own, so whether its first launch passes depends on that machine reaching Apple. The `.pkg` is the shape that needs nothing.

**What is inside the download, and what is not.** The kernel is *in* the app, not beside it: `Contents/Resources/src/` holds this repository’s own kernel (26 TypeScript files at `v0.1.3`, which is every source file that is not a test), and `Contents/Resources/app.asar` holds the built page and the main process. **It carries the model server, but not the model.** `Contents/Resources/server/` holds `llama-server` — 18,692,864 bytes, tracked in this repository rather than fetched at build time — and a launch that names no server starts it over the two weight files a first run fetches, so naming a `llama-server` is no longer required; a name you do give still wins. What no package carries is the weights themselves, which arrive on that first launch, so a first launch with no network stays on the kernel's own placeholder line until they do. **`v0.1.4` is the first download that carries it**: `ui/resources/server/` was empty in every tag up to `v0.1.3`, so those packages could only reach a model through a server you named yourself. **Which of those two halves a download reaches depends on when it was cut.** Releases **up to** `v0.1.0` were cut before the two halves were wired, so those carry only the placeholders. `v0.1.1` and `v0.1.2` wire both halves in their code and still carry no artifact either half reads — `prompts/` and `i18n/` are in neither package — so naming a server on one of those is refused in the kernel's own words rather than answered. `v0.1.3` is the first download that carries them, and anything built from this tree does too, through the variables the section below names. A first launch makes its world the same way the run below does — one room, its bot, and the roster beside the store — and the room's `created_at` is the kernel's seed constant rather than the moment you installed it, which nothing draws yet.

The app keeps its data under Electron's own user-data directory for the app, and `SEEK_DATA_DIR` moves it elsewhere.

## Run the interface

```bash
cd ui
npm install     # first time only
npm run build
npm start
```

For work on the page itself there is `npm run dev`: Vite serves `index.html` with hot reload, and with `SEEK_UI_DEV_URL` set to that server's address — `http://localhost:5173`, the port Vite listens on when `ui/vite.config.mjs` names none — the window loads the served page instead of the built one, so an edit arrives without a `npm run build` in between.

An Electron window over the same kernel: pick a room, or make one — the `+` beside the list takes a name and ticks who starts in it, and `Create` hands it to the kernel's `createRoom()`, whose refusal of an empty room lands beside the form in the kernel's own words; the member count in a room's header opens the list of who is in it, with `Add` beside everyone who is not, and that button is `addMember()` in the kernel. A bot is made in the window rather than only in the seed: `Add bot` beside the bots list takes the four things a bot is — its name, its gender, what it does here and how it talks and works — and `Add` hands them to the kernel's own `createBot()`, whose one refusal is a bot with no name, since a bot named nothing would be drawn under its own id in every member list. Naming somebody is required and the other three are not: a bot whose card says nothing yet is drawn as not said rather than left blank. The same click also writes the two roster rows the bot needs into `agents.yml` beside the store — the file **is** the roster, read on every open, and a bot with no `work` row cannot answer at all — appended rather than rewritten, so rows a person edited by hand survive, and naming the bot by id rather than by name, because two bots may share a name and a roster that cannot tell them apart refuses whole. Where there is no `agents.yml` beside the store at all, the store keeps the agents it already has and no file is invented: the new bot is mute until one is written, and the window says so rather than leaving a person with a bot that is silently deaf — while a file that is there and holds no rows says this bot has no agents. Then type, and press Enter, and the bot in that room answers. Naming someone is a choice about the message rather than characters in it: the `@` beside the box opens the people in the room, works with the box still empty, and stays chosen as the words are typed. The message stores the people it named, the window draws them under the text, and each bot finds its own id in that list — so naming a bot is how a message addresses it. That is a fast pass **inside** the judgement's first stage and not a second road past it: the judgement notices the `@` and lets the message through (`docs/host-rulings.md`). A picture is chosen rather than typed: the `Picture` button beside the box opens a file dialog and sends what you pick, with whatever is in the box as its caption — and the box may be empty, since a caption is optional where a text message is not. The bytes are written to a file beside the store **before** the message that names them is posted, because `deliver()` refuses an `image` whose reference points at nothing; the message itself carries one `{key, mime}` reference and never the bytes, present exactly when its `kind` is `image`, since the store rewrites its shards whole on every save and an inlined picture would be re-serialised by every unrelated turn. The window draws it back from that reference alone, so a store moved without its `media/` directory says the picture is missing rather than drawing an empty one. What it will send is a closed set — `png`, `jpeg`, `gif`, `webp` — read off the extension, because a file dialog hands back a name with no type on it; a file it cannot type is a sentence in the composer rather than a guess, and a dialog you close is nothing to draw. **Whether it answers** is stage 1, and it is a real model as soon as a server is in use — yours, or the one the app starts when you name none: set `SEEK_SERVER` to a running `llama-server` and `SEEK_WINDOW` to how much one judgement may read, and the verdict comes from the watch model — bound over that server by the kernel's own `watch-server.ts`, against the question `src/prompts/watch-v1.json` declares — so the bot speaks when it judges it should rather than on every message. A server that asks for a credential is given one by `SEEK_API_KEY`, sent as `Authorization: Bearer …` on every request — `/props` included — and it belongs to the origin rather than to a half, so two halves on one server carry one key; a variable set to nothing is no credential at all rather than an empty `Bearer`, because the 401 that earns reads like a wrong key instead of a missing one. With neither set the app starts the `llama-server` it carries, over the weights a first run fetched, and binds both halves to that one origin; the judgement is the kernel's placeholder only where no server is in use — a named one that was refused, or a download that did not finish — and a strip at the top of the window says which of the two you are looking at. **What it says** is stage 2, and it is a second server: point `SEEK_WORK_SERVER` at another `llama-server` and the reply is the model's own words, made through the `say` call `src/prompts/work-v2.json` gives it, whose parts also quote the card a person fills in when adding a bot — what it does in this organization and how it talks and works, each said only when the card says it — so the roster's **work** row has to name the model that server serves, since a server serves one model and the two rows may name two. That server does not have to be a `llama-server`: an OpenAI-compatible endpoint takes the same chat call, so point `SEEK_WORK_SERVER` at the `base_url` your provider gave you and name its model in `SEEK_WORK_MODEL`, and the reply is that model's words. Naming a model is what marks the endpoint as one of those, because it is the only thing such an endpoint can answer — there is no `/props` to ask it, so the one fact checked before the first turn is that its own `GET /v1/models` lists the name you gave; a name it does not list is one sentence at start-up rather than a turn that fails all afternoon. **That is where a prompt leaves this machine, and it is the only place it does**: the store is local and the judgement is local, and what a turn says is assembled from the store here and then sent to the server you configured. Leave `SEEK_WORK_MODEL` unset and that half is a `llama-server` as before; set it with no `SEEK_WORK_SERVER` and the half refuses rather than guess, since a model name is a fact about a server. **And a downloaded app reaches that endpoint with no terminal at all**: a double-click sets no environment variable, so with none of the three set, the words half is read from the endpoint this machine already has configured — `~/.emrg/config.toml`, its `[llm]` table's `base_url`, `api_key` and `model` — which is the config the host's own agent runtime runs on. The environment always wins where it says anything, no two of these sources ever merge, and a `[llm]` naming only some of the three is refused in one sentence rather than half-used; that sentence names the missing key and never the credential's value. **And the window can now say it itself**: the gear at the foot of the rail opens Settings, and the settings page writes this app's own `settings.json` — beside `seek-data/`, at mode 0600, moved by `SEEK_SETTINGS_FILE` — so the endpoint is chosen inside the app rather than in another program's file or in a variable a double-click cannot set. The foot of the rail also carries a moon and a sun: pressing it turns the window between the two palettes the stylesheet already carries, and the one you chose is saved in that same `settings.json`, so the next launch opens in it instead of painting light and repainting. Three sources are read in the order a person would expect: the environment, then `settings.json`, then `~/.emrg/config.toml`. Each is used whole and no two of them merge, so a settings file naming an address and no model is refused in its own sentence rather than filled in from the config next door. A saved endpoint is in use from the next turn without restarting the app: the host is re-opened around it, and the judgement half is left running, because it is a server this app already started. `List models` asks the endpoint which models it serves — from the main process and not from the page, because a request from the page's own origin to an arbitrary endpoint comes back as `Failed to fetch` with no status and no body, while from there it is a plain request whose refusal can be quoted in the endpoint's own words. An endpoint saved with no key is a whole endpoint, since a model on this machine takes none; and the key is never drawn back into the page, which is told only that one is saved, its last four characters and its length. Naming the endpoint does not move the judgement: it stays on the model the package carries, because it reads token probabilities and a hosted endpoint reports text. Left unset, and with the app's own server running, the words come from that same origin; `stubDecide`'s line from `src/main.ts` is what you get where no server is in use at all. The two halves take their own origins on purpose, and `SEEK_WINDOW` stays with `SEEK_SERVER` because it is how much one *judgement* may read, while a turn's prompt is re-checked per turn against the work server's own window. Both strips refuse on their own, so a store whose watch row is served and whose work row is not opens, answers in the placeholder, and says both things at once. A server you named and the app did not use (unreachable, serving another model, or given without its pair) does not stop the window opening: the strip names it and says why, in the error colour, because the store is local and its messages do not depend on that server. Under every message there is `reply in thread`: the panel that opens is the chain the store already records, and a reply posted there is the same call with the message it answers named. The placeholder's answer to a threaded reply lands in the room rather than in the panel, because `stubDecide` says its line without naming what it answers; a model's answer is linked to the message that woke it, so it is drawn in the panel. A toolbar is hovered into view over a message, at the sizes measured off the reference screenshots: a white square 26×26 for the emoji and, 2px away, a white pill 26 high holding four 24-wide cells — reply, forward, thread, more — with a 1px rule between them, drawn against the right edge of that message's own words rather than at the end of the column, which is why a message body leaves a gutter on its right. Five buttons, and each one does something. The emoji offers the six a person may pick and writes the one they press through the kernel's own `toggleReaction()`, one call in both directions — a second press on the same emoji is the undo — so the store keeps `operators[]` rather than a count, the number beside a glyph is that list's length, and the tint is this person being in it. Reply puts a message into the next thing you send as a quotation: `deliver()` snapshots the quoted sender's name and the first 160 characters of their words at the moment of sending, and the reply draws that above its own words, so a reply goes on quoting what it answered after the message it answered is gone. Forward copies a message's words, kind and picture off the stored original into **another** room — the call names both the room the original is in and the message itself, because forwarding is sending it somewhere else — and the forward says whose words they are. The thread glyph opens the panel the store already records. And *more* holds the one platform action this build has, `Copy text`, which reaches the clipboard from the main process because a page's own copy is gated on a user gesture: a scripted press on the prototype reported a failure where a real one worked. The first launch has no store yet, so it makes one: the kernel's own seeded room, a bot called Echo whose card is filled in rather than blank — `男`, `研发`, and 实事求是、老实听话, the host's own words, stored as written because a bot's card is content and no catalogue translates it — and an `agents.yml` beside the store holding the two agents that bot speaks through — so the window opens on something you can talk in rather than on an empty list, and the file is there to edit afterwards. It opens `seek-data/seek.json` under Electron's own user-data directory, and `SEEK_DATA_DIR` points it elsewhere — which is how to open the repository's `seek-data/`, roster and all. `npm run dist:mac` builds the app this repository publishes: electron-builder packs the page and the main process into an arm64 bundle under `ui/release/`, signed with the `Developer ID Application` identity on a machine that has one and left unsigned on a machine that does not.

**A launch that finds no weights fetches them, and says how far it has got.** The app carries the model server but not the model: `LiquidAI/LFM2.5-VL-3B-GGUF` is fetched into `~/Library/Application Support/Seek/weights/` on the first launch, both files, 2.2 GB, with the two strips above the room showing `1.2 GB of 2.2 GB — <file>` while it runs. A download that stops leaves what arrived in `<name>.part` and the next attempt continues from there, so a lid closed halfway costs the rest of the file rather than the whole of it. The hosts are tried in a ruled order: the mirror `https://hf-mirror.com` first and the canonical `https://huggingface.co` after it, because the canonical host is not reachable from every network — measured, it times out where the mirror answers, and an order that tried it first would spend that timeout on every first launch. A download that stopped on one host continues from its own bytes on the next, so the fallback is not a second download. `SEEK_WEIGHTS_BASE` names one host and only that one, and a variable set to nothing is refused rather than silently replaced by a default. Offline, or short of bytes, the strips say so in the same standing line they use for a server that was not used, and launching again is the retry.

## Run the prototype

```bash
cd prototype
npm install     # first time only
npm start
```

An Electron desktop client with a four-column messenger layout: messages, threads, contacts, groups and accounts. Everything is stored locally (`~/Library/Application Support/Seek/seek-data/`), including image and file attachments. See `prototype/README.md`.

## Two foundations

1. **Messages are shared facts; context is a private interpretation.** A room has exactly one message log, but each agent has its own view, memory and budget.
2. **The saving happens in the first stage.** Every tick, an agent decides whether to act using zero-cost rules and one cheap judgement; only then does it enter the real agent loop. The part that spends nothing is what makes a permanently alive product affordable.

## Assets

The mark is a speech bubble holding a pupil — it speaks, and it watches. `assets/icon.svg` is the only source; `node assets/render-icons.js` regenerates every PNG from it. That script needs nothing beyond Node: it evaluates the shapes per sample and writes the PNGs itself, because the icon is simple enough that a rasteriser dependency would cost more than it saves.

`assets/social-card.html` is the 1280×640 link preview; `assets/render-social-card.js` screenshots it with the Electron binary from the prototype, since laying out text is the one thing plain Node cannot do.
